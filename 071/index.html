Lists as Arrays in hazel-jit

Matthew, 2026-11-28, on Gnome world in Hazel: “ideally, the game state would stay in post JIT form -- native JS arrays form for lists, and objects for records, in particular”; “we want arrays for lists, whenever possible”; “We introduced a hybrid representation, IIRC, so that lists can be represented by arrays, but still support efficient cons pattern matching”; and “let’s write a report about this issue (representing lists as arrays), including the current status and next steps” (^ticket(909)). He also asked how to close the rest of the gap between JavaScript and Hazel: “is this all because of precise numbers? Step counts? Some other cost (conversion into and out of JIT code)?”

Outline#

  1. How a list crosses today: a page’s array becomes a chain of cells, and back, at every call.
  2. What crossing costs Gnome world: from 5% to 70% of a call’s time, most where the lists are long or the work small.
  3. The rest of the gap: exact integers are most of it in the creatures; fuel checks are not.
  4. The hybrid, as prototyped: cells for ::, array segments for literals and a page’s arrays (11-23, not merged).
  5. What has changed since: the converters cross by declared type, so a list’s conversion is now the cost left at the edge.
  6. Exact integers, taken out: Gnome world’s creatures, way and rivers in Floats; an insect’s step 4.7 µs → 0.37 µs.
  7. Lists as segments, built and measured: a water step 2.38 → 1.60 ms, a search for the way 4.3 → 2.6 ms, every answer the same; the squirrels still slower.
  8. The conversion that is left, and how to take it out: type checks, not copies.
  9. Next steps, each marked done or open, and how this was put together.

In short. In hazel-jit’s compiled code a record is already a plain JavaScript object, and one whose fields are all plain values crosses as the page’s own object, with nothing copied. A list is not: compiled code holds it as a chain of cells, {$h, $t}, so each call turns the page’s array into cells and the answer’s cells back into an array. In Gnome world that crossing is 5% to 70% of a Hazel call’s time: most for the water’s and the rivers’ short calls (53% of Water.down, 70% of Rivers.hold), and a third of the calls over the 897 columns. A hybrid built on 11-23 (branch hazel-jit-lists) lets a list be an array segment as well as cells: a page’s array goes in as a segment with no copy, and :: still makes cells. It was 4% to 8% slower on the games then, when every value still crossed through Hazel’s own values and the arrays saved little. Since then, crossing goes by declared type, which leaves the lists’ conversion as the cost at the edge. The next steps are to bring the hybrid up to date, let the converters hand segments over, and measure it on Gnome world. The other big cost is exact integers. With Folk.hz’s integer operations replaced by plain JavaScript arithmetic, an insect’s step takes 2.3 µs instead of 5.9. Matthew and Cyrus’s JSNum type (^ticket(910)) was to answer that one.

Since, the same day (revised 2026-11-28 10:47). Matthew chose plain Floats instead of a new type (“Float, use Float in”). Gnome world’s creatures, way and rivers now write their numbers as Floats under use Float in, with every answer the same. An insect’s step in Hazel takes 0.37 µs where it took 4.7, against about 0.11 µs in JavaScript. Lists as segments are built on a trial branch of hazel-jit with the converters to match (steps 1 to 3 below). In one browser, against the build the page loads, a water step takes 1.60 ms instead of 2.38, a search for the way 2.6 ms instead of 4.3, and the order of the things 76 ms instead of 93; every twin’s answers are the same. The squirrels, which walk the same short lists again and again, are still slower (0.052 ms a step against 0.031). What crossing is left is checking each value’s type, not copying.

How a list crosses today#

A page calls a compiled Hazel function with its own values, and the library converts each argument by the function’s declared type, then converts the answer back: a record of plain values passes as it is, but a list is rebuilt both ways. These are the converters of hazeljs’s package branch (hazelgrove/hazel hazeljs, 0f24cea171), which Gnome world loads from build.hazel.org; its ahead-of-time file was compiled with the same compiler. For each type:

a value of typethe page holdscompiled code holdscrossing
a number, a boolean, a stringthe samethe samea check of its kind
a record of plain valuesan objectthe same objecteach field checked, nothing copied (^ticket(847))
a record holding a list or a suman objecta new objectits fields converted, remembered by a link
a listan arraycells {$h, $t}, null for []rebuilt both ways; remembered when 16 elements or more
a constructor{tag, value}{$c, $v}renamed both ways

A list is the one shape that must be rebuilt. Compiled code walks a list by x :: rest, so it keeps cells: the tail of a cell is already there, and a pattern match is a property read. The page keeps arrays. So $Lin builds a cell for each element of the page’s array, last to first, and $Lout walks the answer’s cells into a new array. A list of 16 elements or more is remembered by a hidden link on the page’s array, so the same array handed over again costs one lookup (^ticket(681), ^ticket(795)). A game that builds its arrays fresh each step, as Gnome world does, pays the full conversion every call.

What crossing costs Gnome world#

Over 400 steps of the speed run with every Hazel option on, crossing was 5% to 70% of a call’s time. It was most where a call is small, as in the water’s per-block calls and a river’s hold, and about a third where the lists are long but the work is too, as in the rivers’ 806 and 897 elements. Each call was replayed twice: through the converters around a stub that returns the compiled answer (the crossing alone), and as the compiled code alone, given exactly what the converters gave it.

The rest of the gap#

In the creatures, exact integers cost the most. With hazel-jit’s integer operations replaced by plain JavaScript arithmetic, Folk.bug’s compiled step for an insect takes 2.3 µs where it took 5.9, and 0.8 µs where it took 2.2 when no random numbers are drawn. Taking out the check at each function’s entry changes it by less than the noise. The page’s own JavaScript takes about 0.11 µs an insect.

The page’s own JavaScript: about 0.11 µs an insect. Plain-number Ints are for this measurement only: past 253 they are not exact.

Hazel’s Int is exact, so compiled code adds and multiplies through the runtime’s $R.iadd, $R.imul and the rest. Each checks that both are numbers and that the answer is a safe integer, and goes to a BigInt past 253. Folk.hz works out the page’s random numbers in Ints, and their products pass 253, so BigInts flow through the same helpers that the counters use. In the generated code, equality on Ints goes through the generic $R.eq, a builtin such as sqrt is looked up by name on each call, and a helper defined inside a function is a new closure on each call. Floats, by contrast, are JavaScript’s own numbers in compiled code, with plain + and *.

So the gap has three parts that can each be closed. Crossing is the lists’ conversion (this report). Exact integers can be avoided by numbers that are JavaScript’s own: Matthew and Cyrus’s JSNum, ^ticket(910), which the drawing and physics ports will use (Matthew, 2026-11-28). The rest is in the generated code: Int equality, builtins by name, and closures made per call. Step counts matter where a list stands in for an array, such as an nth walk, a tree for a table, or a 32-point chunk for a squirrel’s graph (^report(70)). Lists as arrays give length and nth in one step.

The hybrid, as prototyped#

On 2026-11-23, branch hazel-jit-lists (bba0a9c005, f4a3e3b082) made a list one of three things: null, a cell {h, t}, or a segment {a, i}, the elements of a shared JavaScript array a from index i on. A literal, or a page’s array, is a segment, made with no cells, and x :: xs still makes a cell. A pattern reads a head and a tail through $R.hd and $R.tl, and a segment’s tail is the segment from i + 1. A cell’s tail can be any list, so a list built by :: onto a page’s array ends in that array, with no copy. The runtime’s list walks (append, equality, string_join and the rest) take both shapes, and the agreement tests read both.

^report(54) measured it two ways. In a microbenchmark, recursion through x :: rest came within 15 to 40% of cells’ time, length and nth took constant time, and a page’s array crossed in and out with no copy:

On the seventeen games of ^report(63), the hybrid was about 8% slower ahead of time and 4% through the jit (geometric means over 45 operations), all answers the same. Each head and tail had one more test, a segment’s tail was a new small object where a cell’s tail was already there, and the two shapes meeting in one hot loop cost the JavaScript engine more than one shape would. The games’ lists were short and rarely asked for length or nth. Through the jit, every value still crossed through Hazel’s own values whatever its shape, so the segments saved nothing at the edge. The branch was not merged, and it was kept as an experiment off hazel-jit.

What has changed since#

Two things make lists as arrays worth taking up again. The library now crosses by declared type, with converters generated once for each function (^report(54)’s converters), so nothing goes through Hazel’s own values. And Gnome world hands its Hazel code long lists fresh every step. With the old crossing gone, a list’s conversion to cells and back is what is left at the edge, and the table above shows it at a third to three quarters of a call. Records already cross as the page’s own objects (^ticket(847)). Lists are the one shape that still has to be rebuilt.

The prototype is five days behind hazel-jit. Since then hazel-jit has gained the converters by declared type, calls with their arguments written out ($d, ^ticket(853)), exact Int division by Math.trunc and integer arithmetic folded when compiled (^ticket(891)), and the agreement tests against the interpreter (^ticket(903)). The prototype’s cells are {h, t}; today’s are {$h, $t}. And the converters, which are new, know nothing of segments.

Exact integers, taken out#

A Hazel Float is a JavaScript number in compiled code, with JavaScript’s own + - * / and no checks. Under use Float in, a scope’s whole-number literals and plain operators are Float’s too. Gnome world’s Folk.hz (0.0.157), Path.hz and Rivers.hz (0.0.158) are written that way now, with every answer the same as the page’s. Matthew’s choice, 2026-11-28: “Float, use Float in”, over a new JSNum type (^ticket(910)). The page’s random numbers in Floats are its own steps in doubles, float_mod(s * 1103515245 + 12345, 2147483648): the same numbers, with no BigInts.

Lists as segments, built and measured#

Steps 1 to 3 are built: trial/909-segments on hazel-jit (the compiler and runtime), and trial/909-segments-pkg on hazeljs (that, and the converters), deployed to build.hazel.org. In one browser on one Gnome world, every twin gives the same answers under it, and most pieces take a quarter to two fifths less time. A list is null, a cell {$h, $t}, or a segment {$a, $i, $n}. A literal, a builtin’s list and a page’s array are segments; :: still makes a cell. length, nth, map, filter, fold_left and reverse, called by name, run as JavaScript loops. A page’s array whose elements cross as themselves goes in as a segment over that very array, and a segment from 0 comes out as its own array.

That brought the planning below cells, and the squirrels to 0.052 ms, still above cells’ 0.031: their lists are short, and every head and tail now has one more test.

The conversion that is left, and how to take it out#

With segments, a page’s list of plain values crosses with no copy and no cells. What is left is checking: each number’s, string’s and boolean’s kind, and each field of each record. Rivers.dry’s 897 records still take 15.5 µs to cross, about 17 ns each, though its compiled work halved. Measured the same way as above, the same 400 recorded steps, on each build:

So the conversion left has four parts, and each has a way out:

  • Checks on what comes in. They catch a page that passes the wrong kind of value, and send the call to the interpreter. A page whose values are known to fit could skip them: a trusted call, or the checks made only under Hazel.development(true), as freezing is. Then a page’s array of plain records would cross in one step.
  • Lists built by ::. A list compiled code builds cell by cell is copied into an array on the way out. Built by map or filter, it is a segment and goes out as it is. A Hazel program that returns long lists can build them with the builtins.
  • Records that hold lists or sums. These are new objects each way. With lists as segments and plain records as themselves, a record’s fields cross as they are, so the record itself could too.
  • Constructors. A page writes {tag, value} and compiled code {$c, $v}. None of Gnome world’s 42 Hazel functions passes a sum, so this costs Gnome world nothing; for other apps, one shape both sides would.

With all four, a game’s state could stay in the form compiled code holds it, the page reading and writing the same objects, Matthew’s “post JIT form”: arrays for lists, objects for records.

Next steps#

  1. Done on the trial. Bring the hybrid up to date: merge hazel-jit into hazel-jit-lists (or replay its two commits on a new trial, trial/909-lists), with today’s {$h, $t}, and run CI: the static, fast and full tests, and the agreement tests with segments in them.
  2. Done on the trial. Let the converters hand segments over. A page’s array goes in as a segment {a, i: 0} with no copy when its elements need no conversion: numbers, strings, booleans, and records of plain values, each checked but not copied. Otherwise it is one mapped array, still no cells. Going out, a segment over the whole of a page’s array is that array, a segment from a later index is a slice, and cells become an array as now. This is the change that keeps a game’s lists in the form the page holds.
  3. Done on the trial. Builtins over segments: length and nth in one step, and map, filter, fold_left, reverse and append as JavaScript loops that make arrays, not cells.
  4. Gnome world done, in one browser (above); the 17 games open. Measure on Gnome world with ?libat=trial/909-lists: this report’s crossing table again in the pane, and the speed run with every Hazel option on in the GitHub frames job. Then the 17 games of ^report(63) (bench/4way), to see what the hybrid costs where lists are short.
  5. Begun: a segment keeps its tail. Bring the hybrid’s in-loop cost toward zero: give cells and segments one shape (the same fields, so each match site sees one hidden class), and, later, compile a function that walks a segment through x :: rest to a loop over its index.
  6. Constructors: a page writes {tag, value} and compiled code {$c, $v}, so a sum is renamed both ways. If compiled code read and wrote the page’s shape, sums would cross as they are too, and a game’s whole state could stay in one form.
  7. Decided: Floats, not a new type (^ticket(910), “Float, use Float in”). Done for Folk, Path and Rivers; open for World.hz (the gnome’s step, 198 Ints) and Plan.hz. Gnome world’s drawing (^ticket(908)) and physics will be written in Floats.
  8. Open: CI’s full tests on both trial branches, then Matthew’s word on merging trial/909-segments into hazel-jit (#2859) and the package branch into hazeljs (#2857).
  9. Open: Path.hz by nth over the page’s window (written and checked, _path_nth.hz), its tree of tiles gone, once segments are in the page’s build; and the trusted call, to measure crossing with no checks.

How this was put together#

The crossing and the integers were measured in the Claude app’s browser pane on the laptop, on Gnome world 0.0.156 (hazeljs-examples 97fccb2) with its test hooks. The compiled code was world/rules-aot.json (hazel-jit from trial/1126-night, abf653a21d, the same compiler as the hazeljs branch’s 0f24cea171, which the page itself loaded). Calls were recorded over 400 steps of the speed run with every Hazel option on and the rain started, then replayed with fresh copies of the page’s arguments, except the squirrels’ graphs and the hawks’ great trees, which the game hands over as the same objects. The crossing was timed through the AOT file’s own converters around a stub that returns the compiled answer, and the compiled work by calling the compiled function with exactly the arguments the converters had made for it. A first try timed the page’s own compiled copy against the AOT copy and was dropped: two copies of the compiled code ran at different speeds. The integer experiment replaced the runtime’s integer operations on a second copy of the compiled code, for timing only (its answers are not exact past 253), and took the fuel checks out of a third. The hybrid’s numbers are ^report(54)’s. Every number here is one run in a hidden pane, whose timer is coarse; each is a mean over thousands of calls. The page is built by gen071.py from data/pane.json.
