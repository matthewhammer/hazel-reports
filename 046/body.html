What each is

Three compilers from one family, and one from another.

  • BuckleScript (2016, Bloomberg) compiled OCaml, and later Reason, to readable JavaScript: OCaml's front end and type checker, then its own back end from OCaml's typed intermediate language, one JS module per OCaml module.
  • ReScript is BuckleScript renamed (2020) and grown into a language of its own, with a syntax for JavaScript developers, its own standard library, and, since version 11, functions uncurried by default. Version 12.3.1 here.
  • Melange is the fork of BuckleScript's compiler that kept OCaml (and Reason) and joined OCaml's own tools: dune and opam. Its output is close to ReScript's, as the listings below show. Version 5.0.0 here, with OCaml 5.3.
  • js_of_ocaml, which builds Hazel itself, is the other family: it compiles OCaml's bytecode, a whole program, to JavaScript, with OCaml's runtime in JS around it. Values keep OCaml's memory layout (every block an array, its tag first), and it optimizes the whole program at once. Version 5.9.1 here.
  • hazel-jit (^report(45)) compiles Hazel's elaborated terms to JS source, in the browser, while the program runs, with a runtime of about 2.5 KB.

How fast

On report 043's rule, Melange's and ReScript's JavaScript beat the JS a person wrote: {{n:Melange}} and {{n:ReScript}} µs a call against {{n:hand-written JS}}. hazel-jit's takes {{n:hazel-jit}} µs, about {{n:hj_x_res}} times ReScript's and {{n:hj_x_hand}} times the hand-written; Hazel's interpreter takes {{n:interp}} µs. Each answers the same 2,000 events (fire transition i mod 4, then the command performed on the marking), and all end on the same marking. js_of_ocaml's {{n:js_of_ocaml}} µs is a best case: it compiled the timing loop and the rule as one program, and inlined the whole rule into the loop.

Report 45's ideas, here

The Witch's compiled numbers draw the view's answer straight from its JS and never make it Hazel, as ^report(45) does. They use no diffs: a view's answer never comes back to Hazel, so there is nothing for a diff to carry. Matthew asked, on 2026-11-07 (this section added 20:30): are we using diffs, and are we skipping the trip of the Html back to Hazel?

  • The Html's trip back to Hazel: skipped, in every compiled time here. The view's answer is drawn straight from its JS (HazelJitDOM; ^report(45)'s a view's answer, never made Hazel, ^ticket(714)). It is made Hazel only if something asks for it (the lazy html of LivelitProj.eval_view_answer), and on this slide nothing does. The commands the view runs are answered in JS too. Until bcec455abc, the splice's value went back to Hazel and in again, and that was 20 of the 21 ms of the picture's drawing from JS in the Hazel test. ^report(45)'s cheaper ids are in as well, though a drawing from JS makes none.
  • Diffs: not used, and a render has nothing for one to carry. ^report(45)'s diff carries a new value back to Hazel against the last one (the way back as a diff, ^ticket(715)): in the app, the model a livelit's update returns. The picture's update returns its model unchanged (Pure(m)), and its model changes only when the program's run gives the splice a new value. The slide's sliders and polygon editors do run their updates compiled, their models back as diffs, but this report times views. What a render does carry whole is the other way: the picture into JS, {{w:trip_in}} ms of the {{w:frame}} ms frame in the Hazel test, each time the model changes. A diff that way is below.

  • Sharing is the largest step, and it finds almost nothing to share. In these results it found none on the arms edits and {{w:an_held_lo}} references on the neck edits, which still came to {{w:an_rbytes_lo}} MB.   • Encoding, posting, decoding. Encoding is Marshal to a string, about {{w:an_enc_rate}} s a MB here. Posting the string takes 2 to 4 ms. Compiling the run: a speculation

The trip between the worker and the page is most of an edit (above), and the way to save all of it is not to take it. Under the right conditions, the slide's program could run compiled to JS on the main thread, and each livelit's model could go straight into its compiled view as a JS value, as a view's answer goes straight to the page now. Nothing would be made Hazel, encoded, posted or decoded, and nothing would wait on the worker. This is a speculation, not measured. (Matthew, 2026-11-08: "speculate on ways to hazel-jit more of the worker thread for a slide, so it can be absorbed into the main JS thread under ideal conditions".)

  • What the page takes from the run today. Each livelit's view and model, as samples: the run computes view(model) for every livelit use on the slide ({{w:e_livelits}} here) and samples it at the use's projector (the view fold-in, UserLivelit.instrument_view), and the page draws each livelit from its latest sample (LivelitProj.live_html). Besides those: the probes' samples and the tests, for the editor; the program's value, for its result; and each statement's status, for the editor's highlights. After a slider's edit on this slide, only the first is drawn: the picture, and the slider itself.
  • The idea, from views to the run. A compiled view's answer stays in JS from the call to the page's elements (above). The run could do the same. Compile the slide's program once, with each livelit use's model as a parameter (its literal lifted out of the code), so an edit to a model is a new argument, not new code. At each use, where the run samples view(model) now, call the livelit's compiled view on the model's JS value, and draw its answer as now. The run's answer, as far as the page is concerned, is those calls' answers; nothing else has to leave JS.
  • The conditions: when the fast path is allowed.
    1. The program is statically clean: no type errors and no holes (an indeterminate value has no JS form), and every form in it is one hazel-jit compiles.
    2. No probes or tests are shown for the slide (their samples are Hazel values with environments; a test's pass or fail could be counted in JS instead).
    3. The edit changes livelit models only (a slider, a polygon editor), each to a value of the same type, so the statics need not run again.
    4. The run ends within a budget. On the main thread nothing can stop a loop, so the compiled code would count its calls (fuel) and give up past a limit.
    5. JS's numbers are accepted, as for compiled views (^ticket(694)'s best case).
    6. No stepper or trace is open on the slide.
    When any fails, the worker runs as it does today.
  • The worker, afterward. The fast path shows the edit; the worker can still run the program after it, at a lower priority, for what only it gives: probes, statuses and the editor's decorations. Its answer can also check the JS's, as ^report(45)'s tests check compiled views against the interpreter.
  • What it might gain. The evaluator's {{w:an_evall_lo}} to {{w:an_evall_hi}} s is Hazel's interpreter. Compiled, ^report(45)'s whole programs, their answers kept in JS, ran {{w:r45_whole_lo}} to {{w:r45_whole_hi}} times faster in Node, and the picture's view in Firefox, with its trip in, {{w:ff_pic_x}} times. Even at the smallest of those, the run would take {{w:jr_run_lo}} to {{w:jr_run_hi}} ms, and the trip, {{w:an_trip_lo}} to {{w:an_trip_hi}} s, would be gone. What would be left is the page's own work: about {{w:tl_post_lo}} to {{w:tl_post_hi}} s before the request today, and the whole slide's view, {{w:tl_view_med}} ms each time it is drawn. That page work would then be the next cost.
  • The cuts above first. They keep the worker, and every condition below goes away with them; they are the first step whichever way this goes. A compiled run in the worker, posting the livelits' models as plain JS data (tens of KB for the picture) instead of Hazel's values, would be a step between them and this.
  • Incremental, later. With the models as the program's inputs, its top-level definitions could be kept by their inputs, and an edit could rerun only what depends on the model it changed: the neck slider moves {{w:e_neck}} of the picture's {{w:e_shapes}} shapes. A first cut does not need this.

What it suggests for hazel-jit

Five changes to what hazel-jit writes, each something these compilers already do, would close most of the gap to ReScript. In the order they would likely help this rule:

  1. Pass a function's arguments as JS arguments. A Hazel function of a tuple, fun (n, i) -> …, is a JS function of one array, so every call allocates an array and reads it back. Where the parameter is a tuple pattern, compile (n, i) => … and call it with f(n, i), keeping the one-argument form for a function passed as a value.
  2. Compare Ints with ===. hazel-jit calls its generic structural equality for every ==; the elaborated term knows when both sides are Ints (or Floats, Bools, Strings).
  3. Turn tail calls into loops, as all three do for nth, pick and has: faster, and no stack to overflow on a long list.
  4. Unbox options, and make constructors flat. Some(t) as t and None as undefined saves an allocation per option; {TAG, _0, _1, _2} saves the inner array of {c, v: [a, b, k]}.
  5. Lay out labeled tuples as objects only, not as arrays with the labels as properties too: one shape per type, which JS engines optimize best.

On the Witch's picture the five matter less, since the builtin does most of the work there, but the first and fourth still apply: each point calls grow and grow_all with a fresh array of arguments, and each number goes through $R.b.to_fixed([x, 1]), another array, where the others call x.toFixed(1). A sixth change follows from it: call a builtin JS has directly when its arguments are known to be in range (to_fixed's digits a literal 1, say), as ReScript and Melange do.

Each changes the layout that the trip in and out reads and writes (^report(45)'s to_js and of_js), so each is a change to both sides, and to HazelJitDOM's reading of a view's answer. The first three change only the code inside a compiled function, and are the place to start.

Could any of them be used

Not as hazel-jit's back end; but what they do, yes.

  • As a back end, each would need Hazel translated into its source language (ReScript or OCaml) and then compiled, in the browser, as the program changes. Hazel's holes, its gradual types and its livelits have no counterpart in either, so the translation would refuse much of what hazel-jit compiles, or fall back as hazel-jit does now. And the toolchain is large: Melange's playground compiles in the browser, but only by loading the whole compiler, built to JavaScript, first.
  • Their value layouts are a good target for hazel-jit's next version, above, and would let Hazel values pass to ReScript or Melange code directly, if Hazel apps ever share values with code written in them.
  • js_of_ocaml is what Hazel itself is built with, and its whole-program optimization (inlining across functions, as it did here) is not something a compiler working one definition at a time, in the browser, can do the same way.

Each alternative, for and against

For running a Hazel program's views and updates compiled, in the browser, as the program is edited, hazel-jit stays the right base: it is the only one of these that compiles Hazel itself, all of it that it can, while the program runs. ReScript and Melange are the models for its output; js_of_ocaml stays what Hazel itself is built with. The question for each is the one Hazel has: compile a program that is being edited, holes and all, in the page, and hand its values back and forth with the editor.

hazel-jit

  • For: it compiles Hazel's own elaborated terms, so nothing is translated first, and whatever it cannot compile (a hole, a test, a splice) runs on the interpreter, one definition or one form at a time. It runs in the page, and fast enough to compile on every edit: the Petri rule's program in about 0.6 ms, the Polygons livelit's definition in 3 to 10 ms. Its values come back as Hazel values, closures as Hazel closures, so the editor, the probes and the interpreter take them as their own. Its runtime is about 2.5 KB; the compiler is already in Hazel's bundle.
  • Against: its code is the slowest of the compilers here, {{n:hazel-jit}} µs a call, about {{n:hj_x_res}} times ReScript's, for the reasons above: arguments in an array, a generic equality, no loops, boxed options. It uses no types to choose its code yet. Its Ints are JS numbers, which overflow and round as JS's do, the best-case trade agreed for now. It compiles one definition at a time, so it cannot inline across a program as js_of_ocaml does. On the Witch's picture it is within {{w:hj_x_res}}% of ReScript, at {{w:hj}} ms ({{w:hj_fps}} fps).

ReScript

  • For: among the fastest code here, {{n:ReScript}} µs a call, and the most readable: named tags, objects by field name, functions called with their arguments. It is mature and used in production, its layouts are documented, and its code passes values to and from plain JS easily. On the Witch's picture, {{w:res}} ms ({{w:res_fps}} fps).
  • Against: it is a language of its own, with its own syntax and standard library, so Hazel would be translated into it first, and Hazel's holes, gradual types and livelits have no counterpart there: the translation would refuse an unfinished program, which is most programs while they are being edited. Its compiler is a native program; in the page it would have to be loaded as JavaScript, as its online playground does. And each edit would mean a translation and a build.

Melange

  • For: the fastest compiled code here, {{n:Melange}} µs a call on the rule, {{w:mel}} ms ({{w:mel_fps}} fps) on the Witch's picture. It compiles OCaml, the language Hazel is written in, with OCaml's own tools (dune, opam), so Hazel's implementers know it, and OCaml that Hazel's tools generate could go through it unchanged. Its playground shows it running in the browser.
  • Against: everything said of ReScript as a back end, with OCaml in place of ReScript: Hazel translated to OCaml first, and OCaml's type checker rejecting what Hazel accepts (a hole, a mismatch the gradual types allow). The whole compiler loaded in the page. Its constructors are numbered, not named, so its JS is a little harder to read than ReScript's.

js_of_ocaml

  • For: it already builds Hazel. It optimizes a whole program at once, and inlined the whole rule into its caller here ({{n:js_of_ocaml}} µs a call, a best case). It compiles OCaml's bytecode, so any OCaml runs, exactly as OCaml means it, its integers included.
  • Against: for a Hazel program it would mean Hazel to OCaml, OCaml to bytecode, bytecode to JS, ahead of time: far too heavy to do as a program is edited. Its JS is OCaml's memory layout (every value an array with its tag first), hard to read and awkward to hand to plain JS. And OCaml's library comes along, as JS: on the Witch's picture, numbers formatted with Printf make its view {{w:pf_x_tf}} times as slow as the same view calling JS's toFixed ({{w:jsoo_pf}} against {{w:jsoo_tf}} ms).

BuckleScript

  • For: it is where ReScript's and Melange's code generator comes from, and why their output looks alike.
  • Against: it is no longer developed under that name: ReScript continues it, and Melange is the fork that kept OCaml. Not an option of its own.

Writing the JS by hand

  • For: no compiler at all, and full control: the Petri example's own fallback handler is written this way, for when its Hazel rules do not build.
  • Against: the point is to write the rule in Hazel, and see it in Hazel's editor. And hand-written JS is not the fastest by default: {{n:hand-written JS}} µs a call here, slower than three of the compilers, because it is written the way people write JS. (On the Witch's picture, written with loops over arrays, it is the fastest: {{w:hand}} ms.)

Hazel's interpreter

  • For: all of Hazel: holes, tests, probes, stepping, the call memo, Hazel's own Ints. No compile step, and the semantics are the definition's.
  • Against: {{n:interp}} µs a call on this rule, {{n:interp_x_hj}} times hazel-jit's; on a Polygons render, about 37 times (^report(45)); a frame of the Witch's picture, {{w:interp}} ms ({{w:interp_fps}} fps), {{w:interp_x_frame}} times hazel-jit's, and far outside a 60 fps frame. It stays what runs whatever hazel-jit cannot.

How this was made

  • The program is report 043's Petri net rule as matthewhammer/hazeljs-petri-example has it at 4c85792 (its rules: the preamble, Common, Rules and Main), written again in ReScript (data/Petri.res) and OCaml (data/petri.ml), function for function, as the Hazel is written.
  • The compilers: ReScript 12.3.1 from npm; Melange 5.0.0 (with OCaml 5.3.0) in its playground at melange.re, its JS copied from there; js_of_ocaml 5.9.1 from the opam switch Hazel builds with (ocamlc to bytecode, then js_of_ocaml --pretty); hazel-jit at 28fc073ed5 on trial/694-view-jit, its compiled program run in plain Node with its runtime.
  • The timings: Node 22.23.2 on a Framework 13 laptop (Intel Core i7-1370P), 2026-11-07 at 10:43 MST. One script (data/bench.mjs) runs the hand-written handler, ReScript's, Melange's and hazel-jit's in one process, each on its own values, 2,000 events each; js_of_ocaml's program times itself the same way. Five runs of each; the table gives the median of the five runs' medians, and the fastest single call. The interpreter's number is from Test_HazelJit at 28fc073ed5, a development build.
  • The view is the Witch slide's Drawing.^picture (hazel-programs/docs/livelits/playground/witch.hz at ba72773d46, data/witch/picture.hz), on the picture the slide draws, evaluated by the Hazel test (Test_HazelJit's witch_view_run, test 50) and written out as JSON (data/witch/picture.json).   • Its timings: data/witch/witch-bench.mjs times hazel-jit's, ReScript's, Melange's and the hand-written view in one Node 22.23.2 process, three runs, each the median of five rounds of 200 calls after 20 untimed; js_of_ocaml's two programs time themselves, five runs of 200. Each version's Html is written out as markup in its own language and compared with the SVG the test drew from hazel-jit's answer, which the test checks against the interpreter's drawing. The frame's numbers are from the test, at bcec455abc on trial/694-view-jit (the splice's answers made in JS), two runs of 15 pooled (raw-run1.json, raw-run2.json), 2026-11-07 at 11:28 and 11:35 MST.
