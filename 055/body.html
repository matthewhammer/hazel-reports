Holes Across the Boundary

A starter project for hazel-jit. In mixed mode, Hazel's interpreter runs a program and calls its fully typed functions compiled to JavaScript; when an argument holds a hole anywhere, the whole call goes back to the interpreter. Can such a value cross into compiled code and out again, unopened, and what do the checks that keep it unopened cost? Written for John, on the Hazel team, who offered on 2026-11-17 to take on the question of holes raised at the team's meeting that day, and for anyone else starting on hazel-jit, with notes on where it stands.

Where hazel-jit stands

As of 2026-11-18, hazel-jit lives on one prototype branch, build 50 (build 49 and the slides' builtins). It compiles 260 of the evaluator's 313 test programs and gives the interpreter's answer on every one it can compare. It is not on dev, and three small PRs to dev are waiting for review. What it does not do yet

Some things stay with the interpreter by rule; the rest are limits, each a reason the compiler names.

  • By rule (Matthew and Cyrus, 2026-11-13): code with a hole or a type hole; a program with a static error, which keeps the whole program interpreted; the stepper's filters, and anything the stepper shows, which it steps with the interpreter.
  • Limits the slides meet (the slides' branch, CI run 44184122601): a type hole 29 times and a hole 28, both by rule; test ... end 28 times, a limit (Test and HintedTest, HazelJit.re line 1029), the largest one left on the slides and a contained piece of work; a splice pattern, the builtin group_by_label, and a closure with its own environment, once each; 21 slides have a static error.
  • Holes at the boundary. In mixed mode, a value with a hole in it cannot cross into compiled code, so its call goes back to the interpreter: the project in the sections below.
  • Mixed mode (ticket 766) runs only in the tests: there is no setting in the app yet. A module's member that calls another module's member is not compiled. A call across the boundary costs more than a tiny function saves: 500 calls of a one-line function took 27 ms mixed against 22 interpreted.
  • Probes. In mixed mode today, a compiled function's own probes record nothing, and the stepper does not see its calls (HazelJitMixed.re, its opening comment). Mixed mode runs only in the tests, so no one meets this yet. Probes in compiled code wait on step counts; until then, the plan is to leave a function with a probe uncompiled (report 054, question 5).
  • Step counts (ticket 767). The meeting of 2026-11-13 asked compiled code to count the interpreter's steps, so that probes and the stepper's budget mean the same compiled. The interpreter's costs are calibrated; compiled code does not count them yet.
  • A budget. A compiled run can be given a budget of calls and time (Runtime.limit); mixed mode gives each call 50 million calls and a second, and a run past it falls back. Whether mixed mode runs on the main thread or only in the evaluator's worker is an open question.
  • hazeljs, the library apps use, has the interpreter alone; two problems an app met there are filed, not fixed: float literals print with six decimals (hazelgrove/hazel#2831), and an answer that is a function grows past gigabytes (hazelgrove/hazel#2832).

Working with the tests and CI

CI is the place to run the suite, and its time limits are close: build 50's full tests took 77, 92 and 94.5 of their 100 minutes in three runs.

  • Two suites. The quick tests (make ci-quick, run with -q) have 20 minutes, the full tests (make ci) 100. On build 49 they took 15.4 and 72 minutes; on build 50, 9 to 14 and 77 to 94.5 (the jobs' times: CI runs 44184122601 and 44211080673 on the slides' branch, and 44319161267 on the prototype). A test added to the quick suite could push build 49's past: the astrology test did, four times. The cause, confirmed when the same branch passed with build 50 merged in (CI run 44320263066): build 49's consistency check times each program it compares by running it at least ten more times in the interpreter, however long one run takes. Build 50 runs a program that already takes 20 ms only once more, has the slides' check in the full tests, and leaves the full tests' runs untimed. So the full tests are now the close ones: the slides' check is 13 of their minutes, by the trail below, and a run's time varies by 15 minutes from one run to the next.
  • A killed run says nothing. Test output is printed at the end of a run, so a run stopped at its limit prints none of it. On the two trial branches above, the tests append to hazel-jit-trail.txt as they go, and a CI step prints it after the tests, pass or fail.
  • Parsing big programs in a test. The tests' parse_exp reads text by inserting it, as typing would, which is very slow for a large program; parse with FastParse instead, as hazeljs does (parse_fast on trial/768-astrology-timed).
  • One group at a time. bash test/run_node.sh test HazelJit runs the hazel-jit tests alone. Alcotest's test subcommand exits after the run, so a filtered run skips writing JUnit and coverage; reports printed at exit still print.
  • The Firefox check. .github/workflows/jit.yml loads the slides compiled and not, compares every livelit's drawing, and times the Witch slide's slider; gh workflow run jit.yml --ref BRANCH -f only=Witch runs it by hand.

Where holes stand

No code with a hole is compiled, by rule, and today a value with a hole cannot cross into compiled code at all: the call goes back to the interpreter whole.

hazel-jit compiles Hazel to JavaScript (reports 050 to 054). What it leaves to the interpreter by rule, not as a gap to close, was settled at Matthew Hammer and Cyrus Omar's meeting of 2026-11-13: "for the output of hazel-jit, we should continue to avoid translating code with holes". The interpreter evaluates around holes, and its indeterminate results are the point of them (report 054, What stays with the interpreter). That rule stands here.

Mixed mode (report 054, Mixed mode; on the prototype branch only) is where values meet compiled code. The interpreter runs the program as always. Each function bound at the program's top, or in a module there, whose whole type is declared (let f : A -> B = fun ...) is compiled, and the interpreter calls it as it calls a builtin: the argument is converted to a JavaScript value (HazelJitValue.to_js), the compiled function runs, and its answer is converted back by the declared result type (of_js). On any stop, that call falls back: the interpreter applies its own closure to the same argument, and its answer is the answer.

The conversion knows numbers, booleans, strings, lists, tuples, labeled tuples and constructors. On anything else, a hole among them, it raises, and the call falls back, even when the function would never have looked at the hole:

ProgramMixed mode todayWith this project
let swap : (Int, Int) -> (Int, Int) = fun (a, b) -> (b, a) in swap(1, ?)falls back; the interpreter answers (?, 1)compiled; the same (?, 1), the same hole
let len : [Int] -> Int = fun xs -> case xs | [] => 0 | _ :: rest => 1 + len(rest) end in len([1, ?, 3])falls backcompiled; 3, never looking at an element
let inc : Int -> Int = fun x -> x + 1 in inc(?)falls back; ? + 1still falls back: + looks inside
type Shape = + Circle(Float) + Square(Float) in let round : Shape -> Bool = fun s -> case s | Circle(_) => true | _ => false end in round(?)falls back; the interpreter's match is stuckstill falls back, which takes a check: see below

It matters because a program being edited usually has a hole somewhere, and data with holes in it (a livelit's model with a field not yet filled, a list being typed) reaches functions that only move it around.

The idea

Carry a hole as an opaque JavaScript value: compiled code may store it, pass it and return it, but any operation that would look inside it stops the run, and that call goes back to the interpreter.

{{fig_idea}}
  • In: where to_js meets a value it cannot represent (an empty hole, a multihole, or any indeterminate term, such as ? + 1 or a stuck match), it gives a fresh object standing for it, say {$opaque: k}, and keeps the Hazel term itself in a table at k, its hole ids and environment as they are.
  • Through: compiled code moves it as it moves any value: into a list, a tuple or a constructor's argument, and out as the answer.
  • Never opened: an operation that would look inside it stops the run as an indeterminate result, as reaching undefined does since ticket 761 (Runtime.indet), and the call falls back, so its answer is the interpreter's.
  • Out: of_js, meeting {$opaque: k}, gives back the term from the table, exactly, so a probe or fill-and-resume sees what it would have seen.

Compiled code still contains no hole; only the data does, and compiled code never inspects it. So the rule of 2026-11-13 holds.

Where compiled code looks inside a value

JavaScript will not stop by itself: an opaque object in the wrong place gives a wrong answer silently, so the checks have to be written. Where an operation throws, the run stops and the call falls back, which is safe. Where it returns, it is wrong:

WhereWhat the compiled code doesWith an opaque object
A pattern on a constructorv.c === "Some" (HazelJit.re, line 577)false, so the next arm is tried, and a wildcard arm then matches, where the interpreter's match is stuck. Wrong.
The empty-list patternv === null (line 529)false, so the cons arm runs and reads v.h: undefined. Wrong.
Float arithmetica + ba string such as "[object Object]1", or NaN. Wrong.
Equality===, and the runtime's eq for structuresfalse, where the interpreter is stuck. Wrong.
A tuple's partv[0]undefined, carried on. Wrong.
A callf(x)a TypeError when f is opaque: the run stops and falls back. Safe.
A labeled projectionthe runtime's project_labelsalready stops as indeterminate on a value that is not a tuple. Safe.

Three places for the checks

The checks can go everywhere, only where a silent wrong answer can come out, or into a second compiled version used only when a hole arrives; the third keeps calls without holes at today's speed. The cost that matters is the one on calls with no hole in them, the common case: the Witch slide's compiled views must stay within a frame at 60 a second (report 054, What it all costs: 6.5 ms a frame on build 50).

  1. Everywhere compiled code looks inside a value: a test before each operation, pattern test and part (typeof v === "object" && v !== null && "$opaque" in v). Simple, and every call pays, holes or not.
  2. Only where a wrong answer comes out silently (the rows marked wrong above), leaving the rest to JavaScript's own errors. Fewer tests; still paid by every call.
  3. Two compiled versions of each function. to_js already walks the whole argument, so it knows whether a hole was in it: with none, today's unchecked code runs; with one, a checked version, with the second design's tests, compiled the first time such an argument arrives. Calls without holes cost what they cost today, and the price is compile time and code size, once per function that ever meets a hole.

Our lean, for discussion: the third, its checked version carrying the second's tests. Whether any of this pays is a measurement, not a guess (below).

A first step

Start with values that only pass through, checked by tests that already exist and measured by timings that already run in CI.

  1. The boundary. to_js and of_js carry opaque values and keep their table (HazelJitValue.re).
  2. The checked version. The second design's tests generated under a flag in HazelJit.re's code generation, and mixed mode choosing the checked version when to_js met a hole (HazelJitMixed.re).
  3. Tests beside the mixed-mode tests in test/Test_HazelJit.re: swap(1, ?) and len([1, ?, 3]) compiled, with the interpreter's answers, compared by same_value, which must find the same hole; inc(?) and round(?) still falling back; a hole inside a constructor's argument; a hole's environment kept.
  4. The consistency check. mixed_sweep (test/Test_HazelJit_Agree.re) already runs every evaluator test program in mixed mode and compares its answer with the interpreter's; the programs that pass holes to typed functions start taking the new path.
  5. The cost. The timings in report 054's The same programs, timed come from the quick tests on every push, and the Witch slide's frame time from the jit.yml check in Firefox, so a change to the code generation shows its cost on its next push.

Questions to settle first

Four, with Cyrus and Matthew, before code: where the work lives, which values are opaque, whether a hole keeps its identity, and when the checked version is compiled. Each has our lean.

  1. Does it live on the prototype branch? Report 053 proposes redoing hazel-jit by hand, in small PRs to dev, and mixed mode is so far only on the prototype. Lean: design and measure there; it lands on dev with mixed mode.
  2. Which values are opaque: empty holes only, or every indeterminate term (a stuck application, a failed cast)? Lean: every value to_js cannot represent, since the interpreter's answer holds the term itself either way.
  3. Must a hole keep its identity through compiled code, its id and its closure's environment, so that fill-and-resume and probes still work? Lean: yes; the table gives back the very term that went in.
  4. The checked version: compiled up front, or the first time a hole arrives? Lean: the first time; most functions never meet one.

A warm-up on dev

A smaller first PR, independent of the prototype: make float literals print so that they read back as the same number (hazelgrove/hazel#2831). Atom.to_literal prints a float with %f, six decimal places (src/language/term/Atom.re, line 208 on dev), so a literal such as 280.4606184 does not survive the fast parser's round trip, and its module falls to the slow parser, whose cost grows much faster than the module. The fix is the shortest form that reads back. Atom's derived equality compares floats by the same six decimals (lines 30 to 32); evaluation does not, it compares by value. It is a tour of the parser and of review on dev.
