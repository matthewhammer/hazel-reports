Hazel as an npm Package, Then and Now

On 2026-11-23, ^report(63) asked what the hazeljs npm package is, which PRs it comes from, how its branch differs from dev, how fast each way of running a program is on the games of hazeljs-examples, and what to decide before it goes to dev. This report asks the same questions four days later, of hazeljs 0.0.14 and the jit it carries, and redraws each of 063’s charts with today’s data beside 063’s own. It is for Matthew and Cyrus, after their meeting of 2026-11-27, which found hazel-jit looking good, maybe a couple of weeks from dev, and the package with it.

Outline#

  1. What the package is: hazeljs 0.0.14, on npm since 2026-11-25, the first version there with hazel-jit; the same three ways to run Hazel, and the editor.
  2. The PRs: two PRs now carry it, #2859 (hazel-jit, from dev) and #2857 (the package, which merges it); none is merged.
  3. How the branch differs from dev: 8,577 lines added then, 13,049 now; what grew is hazel-jit, its mixed mode and its tests.
  4. Every game, four ways: the three-way job times five games, with an older interpreter and the games’ compiled.js of 11-20, so it shows plain JavaScript’s lead, not today’s jit.
  5. Where the jit’s time goes: converting values, most of a call on 11-23, now costs nothing for a value handed back unchanged and about half of a call for a fresh list.
  6. The converters, then and now: the jit’s time over the ahead-of-time code’s, 7.50× on 11-23, 0.34× on 11-25.
  7. A game’s own run of states: 0.0.14’s jit takes 0.32× the time of each game’s compiled.js, runs 4,148× as fast as the interpreter, and takes 3.8× plain JavaScript’s time.
  8. Building the rules: as slow as on 11-23, and nearly all of it Hazel’s type checker; the open statics PRs make Gnome world’s warm build 9 to 10 times as fast, and its rules now ship compiled ahead of time.
  9. Against plain JavaScript: Gnome world’s whole speed run takes 6% longer with every piece Hazel’s; World.step alone 5.3× plain JavaScript’s time, 4.0× with the night’s trials.
  10. What to decide before dev: 063’s ten questions with today’s answers, and four new ones.
  11. What next for speed, and how this was put together.

In short. The jit is no longer the slow part. On each game’s own run, it went from 7.50× the time of code compiled ahead of time (11-23) to 0.32× (11-25, the library 0.0.14 ships), and Gnome world’s whole speed run is 6% slower with its rules in Hazel than in JavaScript. What is slow is building the rules, seconds of type checking on each load, which the statics PRs and compiling ahead of time both answer. On 11-27, three places where the package’s two ways part were found (^ticket(898), ^ticket(897), ^ticket(896)), and five trials from the night of 11-26 wait on Matthew’s word.

What the package is#

hazeljs 0.0.14, on npm since 2026-11-25, gives a page the same three ways to run a Hazel program as 0.0.11 did, and Hazel’s own editor; it is the first version on npm with hazel-jit. The jit came into the package in 0.0.10 and moved to Jane Street Core in 0.0.11, and neither was published: npm has 0.0.1 to 0.0.8, then 0.0.14. Its hazel-lib.js (2.9 MB) is built from hazelgrove/hazel 2c4a61560f on the hazeljs branch (#2857), as its package.json records; the package is 78 files and 14.0 MB unpacked, 11 MB of it the editor.

What changed under the jit since 0.0.11, in the order it was made:

  • Converters by declared type (a97b6f7465, 11-23): a page’s values go straight into compiled code’s shapes and back, with no Hazel values in between; remembered by links on the objects (ca851b422d, 11-24), not in WeakMaps.
  • Records as plain objects in compiled code, a field read in place (0.0.13, 20febee548, 11-24).
  • Loops for a recursive function’s calls of itself in tail position; JS arguments for a named function’s tuple parameters; constructors without arguments made once; a module’s members read by name; and == against a literal as === (0.0.14, 2c4a61560f, 11-25; ^report(65)).
  • Holes in mixed mode (^ticket(769)): a hole in an argument crosses into compiled code unopened, and code with holes compiles. On the branch since 11-26 (b1b4e19286), after 0.0.14, so in no published package.
  • Not yet: SInt with 64 bits, which waits on #2828; the branch still checks SInt at 32 bits.

The third way has a new user. Since Gnome world 0.0.147, its rules are compiled on GitHub (node/world-aot.mjs, with the night’s trials’ library) and the page makes them from that text in 188 ms, instead of building them on every load (building the rules).

Every game, four ways#

The job that times the games when their rules change, hazeljs-examples’ three-way timing, covers five games, not every game, and neither of its Hazel ways is today’s package: it interprets with hazeljs 0.0.4 and runs each game’s compiled.js, compiled by hazel-jit on 11-20. On its latest run, compiled.js ran the five games 3,436× as fast as the interpreter (the geometric mean over 34 operations) and took 14× plain JavaScript’s time; whole games played by Hazel, 5.7×. So it measures plain JavaScript’s lead over hazel-jit’s code of 11-20, and what that code pays for. Today’s jit, the package’s own, is measured on 14 games in a game’s own run of states.

Then: ^report(63)’s run timed 45 operations of 17 games four ways through hazeljs 0.0.11 itself: the jit 317× as fast as the interpreter, code compiled ahead of time 2,392×, and plain JavaScript 16× as fast again as code compiled ahead of time (20 operations of the five games that had it).

  • What the three-way job adds: two variants of compiled.js that say what hazel-jit’s code pays for. Without its step budget, a call takes 0.95 of the time (the geometric mean over the operations); without the budget and with plain numbers instead of exact Ints, 0.83. So the budget and exact arithmetic are about a sixth of compiled.js’s time here, and most of the gap to plain JavaScript is elsewhere (against plain JavaScript).
  • Expert Minesweeper, then and now: opening one cell took 32 ms interpreted, 7.5 ms through 0.0.11’s jit, 50 µs ahead of time and 531 ns in plain JavaScript on 11-23; on the three-way job, 53 ms interpreted, 53 µs in compiled.js and 440 ns in plain JavaScript. The positions are each driver’s own, so compare ratios within a run, not times across.
  • Whole games, interpreted: 2,642× the time of compiled.js. A game of Go on 9 by 9, Hazel against Hazel, took 53.1 s interpreted and 13.1 ms compiled; Solitaire’s 300 random moves, 49.1 s and 7.6 ms. The longest whole games were not played interpreted.

Where the jit’s time goes#

Then, converting the values in and out took more of the jit’s time than the compiled code did, on 34 of 45 operations. Now a value the page hands back unchanged crosses for nothing, and what still costs is a fresh one: on Gnome world’s pieces that take lists, the crossing alone is about half of a call on fresh inputs, and a call takes 7 to 9 times its JavaScript twin’s time. Since 11-24 the converters go by declared type and remember what they made of each object, so a page that gives back what Hazel answered pays only for the parts that changed. Gnome world makes its animals’ surroundings new every step, so those lists cross again each time; ^report(64) timed that.

A fresh list crosses cell by cell, and a constructor node by node, from the page’s {tag, value} to compiled code’s {$c, $v} (^report(65), conversion at the edges). ^ticket(681)’s trial remembers only lists of 16 elements or more, so a small list handed back again is converted again rather than looked up, and a large fresh one costs less: on fresh copies of each game’s run, Solitaire went from 30 to 8.6 ms and Mahjong solitaire from 33 to 12 (package bench run 45936503544, as ^ticket(681) records; not rechecked here).

The converters, then and now#

The jit’s time a call over the ahead-of-time code’s went from 7.50× on 11-23 to 0.34× on 11-25, as ^report(65) counted it over the 14 games’ runs: the converters by declared type brought the jit to about even, and changes to the compiled code itself (records as objects, loops, JS arguments, constructors once, modules by name) took it well below. The yardstick is each game’s own compiled.js, compiled by the hazel-jit of 11-20 with converters a person wrote; under 1×, today’s jit, converting as it goes, beats that older code with its hand-written converters. On ^report(65)’s four-way run of the same day and library, used in the next section, it is 0.32×.

A game’s own run of states#

On each game’s own run of states, 0.0.14’s jit takes 0.32× the time of the game’s compiled.js (the geometric mean over 14 games), where build 5 took 0.91× and build 6 0.76× on 11-24. It runs 4,148× as fast as the interpreter (1,729× then), and takes 3.8× plain JavaScript’s time, every one of the 14 games now having a plain.js. A call through the jit was 2.5× as fast as on 11-24 (the geometric mean, across runners): Gnome dig 51 µs → 11 µs a call, Mahjong solitaire 100 µs → 8.1 µs. Every answer was the same every way.

  • Against compiled.js: the jit did best in Butterfly garden 0.09×, Minesweeper 0.10×, Gnome dig 0.21×, and least well in Checkers 0.96×, Snake 0.66×, Mahjong 0.60×; it was the faster in every game.
  • Fresh copies: given a fresh copy of every argument, so that the converters remember nothing, the jit took 1.9× its own time (2.2× on 11-24).
  • Interpreted: in 6 of the 14 games an interpreted call fits in a frame of 16.7 ms (60 fps); through the jit, the slowest game is Go, 13 µs a call.
  • Plain JavaScript: on the five games that had plain.js on 11-24, the jit’s time over plain JavaScript’s went from 8.7× to 4.1×.

Building the rules#

Building a game’s rules takes as long as it did on 11-23: with the jit 170 ms to 4.5 s on the 14 games, interpreted 485 ms to 6.7 s (now over then, 1.01× and 0.98×, within the runners’ spread). It is nearly all Hazel’s type checker, not the jit: for Gnome world, the two open statics PRs (#2603, #2717) take a warm build from 3.14–3.32 s to 0.33–0.34 s, and its rules now ship compiled ahead of time, made from text in 188 ms. Gnome dig: 5.6 s → 6.3 s interpreted, 3.7 s → 4.5 s with the jit. The games’ rules are the same in both runs but Snake’s (hazeljs-examples a4a0a88 and 05894e1).

A CPU profile of Gnome world’s build (^report(64); hazeljs-examples’ build profile run 45935259272, the library of b1b4e19286 built unminified) puts 70% of it in Hazel’s statics, 28% in garbage collection, and 0.5% in hazel-jit’s compiler; the parser does not show. Labeled tuples weigh: Typ.re 31%, LabeledTuple.re 16%. On 11-27 Matthew asked why the rules take seconds when the jit is fast, and for an experiment, not to merge, with the open PRs that address it (^ticket(894)): on the branch every let analyzes its definition twice, a function-shaped one three times, so nested lets multiply; #2603 analyzes a let once unless it refers to itself, and #2717 a module binding once.

  • The first build took 4.34–5.09 s with the package’s branch, 3.94–4.44 s with the night’s trials and 1.39–1.58 s with the statics PRs on them; warm, 3.14–3.32, 2.87–3.19 and 0.33–0.34 s. The statics trial gave the same answers on every Gnome world piece (fresh timing run 46023247014).
  • Ahead of time: Gnome world 0.0.147’s rules are compiled on GitHub (8.3 s there, 24 functions, 510 KB) into world/rules-aot.json; the page makes them from that text in 188 ms and is ready 1.7 s after opening, where its own first build at load took about 15 s cold (^report(64)). ^ticket(890)’s Hazel.jitProgramSaved would do the same for any page, keeping a build in the browser’s storage: ready 0.70 s after a reload, 13 to 19 ms to make the rules (in the pane, as ^ticket(890) records).

Against plain JavaScript#

The whole game is now within a few percent: Gnome world’s speed run, 46,276 steps, took 34.1 s with every piece Hazel’s, compiled ahead of time, against 32.3 s with every piece in JavaScript, 6% longer, the two runs the same at 24 of 24 fingerprints. Piece by piece, Hazel takes 1.9× to 6.6× its JavaScript twin’s time; World.step 5.3× with the package’s library and 4.0× with the night’s trials. On 11-23, ^report(63) had plain JavaScript about 16× as fast as hazel-jit’s code on the five board and card games, by operation; on the games’ runs, today’s jit takes 3.8× plain JavaScript’s time.

A step of the speed run took 0.74 ms (about 1,357 fps) with Hazel’s pieces and 0.70 ms (about 1,434 fps) with JavaScript’s; the rules’ own calls were 1.22 s of the 34.1 s (3.6%). The rest of each step is the page’s own JavaScript either way.

  • The night’s trials take World.step from 4.17–4.32 µs to 2.41–2.47 µs on the same inputs again (43% less time; plain JavaScript 0.79–0.81 and 0.60–0.62 µs in the same runs), and from 4.50–4.77 to 2.74–2.82 µs on fresh inputs (40% less; plain 1.17–1.20 and 1.00–1.06 µs). Most of it is ^ticket(891): an Int division as Math.trunc(a / b) + 0, exact and never −0, and arithmetic on numbers written out folded when compiling, so that 0 - 1 is no runtime call (division and folding alone: about 42% less time on one runner, run 45942901416, as ^ticket(891) records; not rechecked here).
  • What hazel-jit’s code still pays for, on the three-way job’s five games: the step budget and exact Ints together about a sixth of a call (0.83 of the time without both). ^report(60) listed the others: lists as chains of cells, and tuples as arrays carrying their labels; since then records became plain objects and calls of named functions plain JavaScript calls (^report(65)).
  • Fresh inputs: World.step takes 3.9× plain JavaScript’s time on fresh inputs with the package’s library and 2.7× with the night’s trials, less than on the same inputs again, since fresh inputs cost plain JavaScript about as much more as they cost Hazel.

What to decide before dev#

On 2026-11-27 Matthew and Cyrus found hazel-jit looking good, maybe a couple of weeks from merging to dev, and the package ditto; for next week, a jit subcommand for Hazel’s command line (^ticket(899)) and a livelits PR with a tree of slides, “Livelit applications” (^ticket(900)). ^report(63)’s ten questions, each with where it stands now, then four new ones.

  1. One PR, or its parts? Now: two, by design: #2859 for hazel-jit and #2857 for the package, which merges it. The parts (#2711, #2719, #2814, #2837, #2842) are still open and still written for OCaml’s standard library; the options are as before (close them for #2857, land the font and icons first, or split #2857).

  3. How is agreement kept? Now: in Hazel’s CI. #2859’s agreement tests run every evaluator test compiled where it compiles: of 289 checks, 234 compile, 211 give the interpreter’s answer and none differs; the other 23 end where the interpreter’s result is not a value (#2859’s description). The games’ own agreement stays in hazeljs-examples.
  4. Finished programs, or the editor too? Now: both, in part. Mixed mode on #2859 compiles a program’s fully typed top-level functions and the interpreter runs the rest, holes included; holes cross into compiled code unopened (^ticket(769)).   8. Licenses. Now: no license file changed since 11-23 (the diff); the Noun Project icons’ question is open.

World.step still takes 4.0× plain JavaScript’s time with them; the step budget and exact Ints are about a sixth of compiled code’s time.
