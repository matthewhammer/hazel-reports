What the package is

hazeljs 0.0.14, on npm since 2026-11-25, gives a page the same three ways to run a Hazel program as 0.0.11 did, and Hazel’s own editor; it is the first version on npm with hazel-jit. The jit came into the package in 0.0.10 and moved to Jane Street Core in 0.0.11, and neither was published: npm has 0.0.1 to 0.0.8, then 0.0.14. Its hazel-lib.js (2.9 MB) is built from hazelgrove/hazel 2c4a61560f on the hazeljs branch (#2857), as its package.json records; the package is 78 files and 14.0 MB unpacked, 11 MB of it the editor.

What changed under the jit since 0.0.11, in the order it was made:

  • Converters by declared type (a97b6f7465, 11-23): a page’s values go straight into compiled code’s shapes and back, with no Hazel values in between; remembered by links on the objects (ca851b422d, 11-24), not in WeakMaps.
  • Records as plain objects in compiled code, a field read in place (0.0.13, 20febee548, 11-24).
  • Loops for a recursive function’s calls of itself in tail position; JS arguments for a named function’s tuple parameters; constructors without arguments made once; a module’s members read by name; and == against a literal as === (0.0.14, 2c4a61560f, 11-25; ^report(65)).
  • Holes in mixed mode (^ticket(769)): a hole in an argument crosses into compiled code unopened, and code with holes compiles. On the branch since 11-26 (b1b4e19286), after 0.0.14, so in no published package.
  • Not yet: SInt with 64 bits, which waits on #2828; the branch still checks SInt at 32 bits.

The third way has a new user. Since Gnome world 0.0.147, its rules are compiled on GitHub (node/world-aot.mjs, with the night’s trials’ library) and the page makes them from that text in 188 ms, instead of building them on every load (building the rules).

Where the jit’s time goes

Then, converting the values in and out took more of the jit’s time than the compiled code did, on {{light63}} of {{ops63}} operations. Now a value the page hands back unchanged crosses for nothing, and what still costs is a fresh one: on Gnome world’s pieces that take lists, the crossing alone is about half of a call on fresh inputs, and a call takes 7 to 9 times its JavaScript twin’s time. Since 11-24 the converters go by declared type and remember what they made of each object, so a page that gives back what Hazel answered pays only for the parts that changed. Gnome world makes its animals’ surroundings new every step, so those lists cross again each time; ^report(64) timed that.

A fresh list crosses cell by cell, and a constructor node by node, from the page’s {tag, value} to compiled code’s {$c, $v} (^report(65), conversion at the edges). ^ticket(681)’s trial remembers only lists of 16 elements or more, so a small list handed back again is converted again rather than looked up, and a large fresh one costs less: on fresh copies of each game’s run, Solitaire went from 30 to 8.6 ms and Mahjong solitaire from 33 to 12 (package bench run 45936503544, as ^ticket(681) records; not rechecked here).

What to decide before dev

On 2026-11-27 Matthew and Cyrus found hazel-jit looking good, maybe a couple of weeks from merging to dev, and the package ditto; for next week, a jit subcommand for Hazel’s command line (^ticket(899)) and a livelits PR with a tree of slides, “Livelit applications” (^ticket(900)). Report 063’s ten questions, each with where it stands now, then four new ones.

  1. One PR, or its parts? Now: two, by design: #2859 for hazel-jit and #2857 for the package, which merges it. The parts (#2711, #2719, #2814, #2837, #2842) are still open and still written for OCaml’s standard library; the options are as before (close them for #2857, land the font and icons first, or split #2857).
  2. Does hazel-jit belong on dev, and where? Now: #2859 proposes it in src/language/dynamics, {{pr2859_add}} lines, 13 of them in dev’s own files, with nothing in the app turning it on. The meeting found it looking good. Open: whether the livelits line’s hazel-jit (#2817) is then rebased on it.
  3. How is agreement kept? Now: in Hazel’s CI. #2859’s agreement tests run every evaluator test compiled where it compiles: of 289 checks, 234 compile, 211 give the interpreter’s answer and none differs; the other 23 end where the interpreter’s result is not a value (#2859’s description). The games’ own agreement stays in hazeljs-examples.
  4. Finished programs, or the editor too? Now: both, in part. Mixed mode on #2859 compiles a program’s fully typed top-level functions and the interpreter runs the rest, holes included; holes cross into compiled code unopened (^ticket(769)). Polymorphic functions are not compiled in mixed mode (^ticket(897)).
  5. The values a page sees are an API: which shapes? Now: plain values, converted by declared type and remembered by object; records are plain objects. ^ticket(890)’s Hazel.jitProgramSaved would add a saved program; handles are not started. Open: take jitProgramSaved into #2857, an API addition.
  6. Numbers. Now: SInt is to have 64 bits everywhere; #2828 is still a draft, and the branch checks SInt at 32. On the night’s trials, ^ticket(792) reads an Int from JavaScript whole (it arrived as 32 bits) and a BigInt past 253, and ^ticket(891) makes Int division exact and twice as fast.
  7. What dev’s users would see. Now: as before: the interface font on every page, the icons offline; mixed mode’s hooks change nothing visible.
  8. Licenses. Now: no license file changed since 11-23 (the diff); the Noun Project icons’ question is open.
  9. Who may embed Hazel? Now: not revisited here.
  10. Publishing. Now: 0.0.14 is on npm, from the hazeljs branch’s build at 2c4a61560f; 0.0.9 to 0.0.13 never were. Open: whether a version must come from a commit on dev once the branch is merged.
  11. New: a cast out of an unknown type nobody wrote. Compiled code erases it, so let f = fun x -> x + 1 in f(true) answers 2 compiled where the interpreter stops at the failed cast; and the package compiles a program with static errors, where the editor compiles none (^ticket(898)). Options: a check at each such cast that stops the run, so the interpreter answers; and compiled: false for a program with static errors.
  12. New: polymorphic functions in mixed mode (^ticket(897)): compile them, reading each call’s answer back by the type at its use, or leave them to the interpreter.
  13. New: the interpreter path’s Floats (^ticket(896)): a function typed on its let took whole numbers as Ints where its type says Float, which stopped Gnome world’s interpreted speed run. The fix (one line in HazelLibCore.param_type, and a test) is on trial/896-interp-param, its CI pending: merge it into #2857?
  14. New: the night’s trials. Merge trial/1126-night’s five (^ticket(792), ^ticket(681), ^ticket(890), ^ticket(891), ^ticket(791)) into #2859 and #2857, all or some, and publish a 0.0.15?

What next for speed

  1. Convert by declared type, in one step. Done 11-24 (build 5); since then 0.91× → {{ct_last}} the ahead-of-time code’s time.
  2. Time the converters on a game’s own run of states. Done 11-24, and again on 11-25 with 0.0.14’s library (above).
  3. Keep values compiled between calls. Not started. Fresh inputs are now nearly all of the crossing’s cost (above); ^ticket(681)’s threshold softens it, and handles, or an interpreter that keeps compiled values, would remove it.
  4. Load time. Answered for Gnome world by compiling ahead of time (0.0.147), and for any page by ^ticket(890)’s trial; the statics PRs make building itself {{wb_gain}} as fast. Next week’s jit subcommand for the CLI (^ticket(899)) would make the ahead-of-time files the games ship.
  5. The costs over plain JavaScript. In part: loops, JS arguments, constructors once and modules by name (0.0.14), and Int division and folding (^ticket(891), on the trials). World.step still takes {{ws_nx}} plain JavaScript’s time with them; the step budget and exact Ints are about a sixth of compiled code’s time.
  6. Agreement in CI. Done in #2859. The cast check of ^ticket(898) comes before more speed.
  7. New: the statics. #2603 and #2717 are open PRs on dev; under the package’s branch they make Gnome world’s warm build {{wb_gain}} as fast. Porting them to Core and landing them on dev is Matthew’s and Cyrus’s call.
