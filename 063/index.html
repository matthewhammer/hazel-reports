Hazel as an npm Package: What to Decide Next

On 2026-11-23 Matthew asked for one PR that tracks everything the hazeljs npm package depends on: Hazel’s editor in the package, working offline, with fonts and icons whose licenses allow it, and hazel-jit, “so that hazel code can be parsed and jitted from the npm package API as well”. That PR is hazelgrove/hazel#2857, and hazeljs 0.0.11 is built from it. This report is for Matthew and Cyrus, to see the design space before it goes to dev: what the package is, the PRs it comes from, how its branch differs from dev, how fast each way of running a program is on every game in hazeljs-examples, and the decisions to make next.

Outline#

  1. What the package is: three ways for a page to run Hazel code, and Hazel’s own editor, offline.
  2. The PRs: one PR holds it all; the parts it came from are still open.
  3. How the branch differs from dev: 8,577 lines added, nearly all in new files, and the move to Jane Street Core.
  4. Every game, four ways: the 17 games’ 45 operations, interpreted, through the jit, compiled ahead of time, and in plain JavaScript.
  5. Where the jit’s time goes: before the converters, on most calls, converting the values in and out cost more than the compiled code itself.
  6. The converters, a day later: the jit 9.0× as fast, and about even with code compiled ahead of time.
  7. A game’s own run of states: played as a page plays them, the jit takes 0.91× the time of code compiled ahead of time, and 0.76× with its memos kept as links on the objects; with nothing remembered, 2.2× its own.
  8. Building the rules: the jit builds faster than the interpreter; ahead of time, nothing is built in the page.

What the package is#

hazeljs 0.0.11 gives a page three ways to run a Hazel program, and Hazel’s own editor. The first two come in one file, hazel-lib.js (2.9 MB, Hazel compiled to JavaScript by js_of_ocaml): Hazel.run and runProgram interpret a program; Hazel.jit and jitProgram compile it to JavaScript with hazel-jit in the page and run that. The third needs no Hazel in the page at all: Hazel.compileProgram gives the JavaScript and its runtime once, ahead of time, to keep in a file, which is how every game in hazeljs-examples ships. The editor is Hazel’s web app, built from the same commit, framed by the package’s hazel-listings.js; its fonts and icons are in the package with their licenses, so it loads nothing from another host.

0.0.11 is pushed on hazelgrove/hazeljs’s editor-in-package branch and is not on npm. Its hazel-lib.js is byte for byte the file Hazel’s own deploy of the same commit serves, and the package’s Verify workflow rebuilds it on GitHub and checks that. Its install checks run on Node 18, 20 and 22, in TypeScript, and in a headless Firefox.

The PRs#

One PR, #2857, holds everything the package is built from; the PRs its parts came from are still open, and none is merged. #2857 merges the library and embed line (#2711, #2719, #2814, stacked on each other), the font (#2837) and the icons (#2842), adds hazel-jit’s compiler, and merges dev. How the branch differs from dev#

The branch is 50 commits ahead of dev and 0 behind. It changes 41 files, adding 8,577 lines and removing 59: almost all of it new files, and 2,276 lines of it tests. Only 179 added lines touch what dev’s own code does; the rest is new modules and files that dev does not have.

What changes for dev’s own app. The interface font is IBM Plex Sans instead of Helvetica Neue, on every page. The icons load from Hazel’s own files instead of from Google. Hazel’s list of error messages can also give each with the id of the term it is on (the library’s errors per module use it). An editor rooted at a module reads its text as a module body, and the fast parser retries a module body whose last member is still being written. In the interpreter, a labeled tuple whose fields arrive in another order than its type’s is put in its type’s order before it runs; only a value made in JavaScript ever arrives that way. Embed mode (the frame, editable cells, go to definition across cells) is reached through #embed and changes nothing in the normal app.

Jane Street Core. dev moved to Core in hazelgrove/hazel#2470 through #2477, and -open Core applies to a whole library at once, so the branch’s own files were ported in the same merge. One difference no type error showed: Core’s List.init calls its function from the last index down, where OCaml’s own went up from 0. The jit finds a compiled tuple’s labels by the value at each index, using each label up as it goes, so in reverse it swapped fields that JavaScript’s == takes as equal: (b = false, a = 0, c = 5) came back as {a: false, b: 0, c: 5}. Comparing Gnome dig’s compiled run with its interpreted run in Node found it; 98c482395d fixes it, with a test. The parts’ own PRs (#2711, #2719, #2814) are still written for OCaml’s standard library.

Every game, four ways#

Through the package’s jit, the 17 games run 317× as fast as through its interpreter (the geometric mean over 45 operations), from 4.2× to 4,955×. Compiled ahead of time, the same code runs 2,392× as fast as the interpreter. The spread is the point. On the 11 operations that are mostly the program’s own work, a robot choosing or Hazel searching for a move, the jit is 1,063× to 4,955× as fast as the interpreter and within 1.7× of code compiled ahead of time. On the other 34, where the call itself is short, it is 4.2× to 1,563× as fast as the interpreter. All four ways gave the same answer on every operation. (These are build 2’s jit numbers; the jit with direct converters, build 5, is in the converters, a day later.)

The jit and ahead of time run the same compiled code; the gap between them is how the values get in and out of it, not compiling, and not the code. Both come from one compiler: Hazel.jitProgram and Hazel.compileProgram run the same analysis and the same compile_elab on a program, and produce the same JavaScript. The jit makes it as the page loads (117 ms to 3.7 s for these games) and the ahead-of-time file was made before, so neither way’s compiling is in a call’s time. What a call does:

  • Ahead of time (blue): the game’s own converters, written by hand for its types, turn the page’s values straight into the compiled code’s shapes; the compiled code runs; its answer is turned straight back into the page’s values.
  • Through the jit (orange), in build 2: each argument is first made into Hazel’s own value, the interpreter’s representation of a term (OCaml data, built by the function’s declared type), and then from that into the compiled code’s shape; the same compiled code runs; its answer is made into a Hazel value, and from that into the page’s. Every value crosses twice each way, through a representation made for the interpreter, and a call also has a fallback to the interpreter if the compiled code throws.

So where a call works long on a small value (a robot choosing, Hazel searching for a move), the conversions are a small part of it and the two ways come within 1.7× of each other; where a call is short and its value large (an expert Minesweeper board of 480 cells, for one opened cell), the conversions are most of the jit’s time. Where the jit’s time goes splits each operation that way, and the converters, a day later times the jit with the conversion made direct (build 5).

For one game, Gnome dig: a step of the game takes 97 ms interpreted, 0.36 ms through the jit and 43 µs ahead of time; the robot choosing its move takes 3.8 s, 1.0 ms and 0.88 ms. At 60 frames a second a frame has 16.7 ms, so interpreted, one step is six frames and the robot’s choice almost four seconds; through the jit, both fit in a frame many times over.

Where the jit’s time goes#

With build 2 (before the converters: with them, this crossing all but went), on 34 of the 45 operations, more of the jit’s time went to converting the values in and out than to the compiled code itself. The largest: Minesweeper, 16 by 30: a cell opened, 7.5 ms through the jit against 50 µs ahead of time. A call through the jit converts its arguments from the page’s JavaScript values into Hazel’s own values, using the function’s declared types, then from those into hazel-jit’s shapes; calls the compiled function; and converts its answer back the same two steps. A game’s whole state crosses on every call, both ways. Code compiled ahead of time does the same work with converters written by hand for the game’s values, straight from one shape to the other, so it pays for the crossing too, but far less.

Expert Minesweeper shows the extremes. Opening one cell of a 16 by 30 board takes 32 ms interpreted, 7.5 ms through the jit, 50 µs ahead of time and 531 ns in plain JavaScript: the call does almost nothing, and the board of 480 cells crosses twice. A search, on the other hand, works for milliseconds on a state that crosses once: there the jit and code compiled ahead of time are the same speed.

The converters, a day later#

With #2857’s converters by declared type (build 5), the 45 operations ran 9.0× as fast through the jit as with build 2 (the geometric mean), and the jit came out about even with code compiled ahead of time: 0.8× its time, against 7.5× the day before. On 35 of the 45 operations the jit is now within half again of the ahead-of-time code, or faster. Part of that is the driver’s: see the first caution below, before reading these as a game’s speed. Build 5 is build 2’s package with one file changed: its hazel-lib.js, taken from #2857 at a97b6f7465, whose jit writes a page’s values straight into compiled code’s shapes and back by each function’s declared type, with no Hazel values in between, and remembers each value it has converted. Every answer was the same.

  • The same values every call: this flatters the jit. The driver times each operation on the same position again and again, and the converters remember what they converted, so an unchanged value crosses for nothing the second time, while the ahead-of-time files’ own converters still convert it every call. Pinball’s board went from 0.31 ms to 44 ns, and an expert Minesweeper cell now takes 2.7 µs through the jit against 50 µs ahead of time. In a game, each step’s new state crosses again, all but the parts that did not change, which are the same objects as before; how much of the 9.0× survives that is measured in a game’s own run of states, next.
  • The runners differ from day to day. The interpreter and the ahead-of-time code were the same in both runs, yet came out at 1.17× and 1.12× of the day before’s times (geometric means), one operation from 0.66× to 1.83×. So read an operation’s change against its game’s own ahead-of-time time, as the figure does, not across the two days.
  • Building took longer for some games: Mahjong 1.1 s → 1.9 s, Solitaire 367 ms → 572 ms, Bricks 230 ms → 356 ms. The converters need each function’s types from the statics; whether that or the runner is the cost needs both builds timed on one machine.

This was the first step of What next; the second follows.

A game’s own run of states#

Played the way a page plays them, each call given the state the last call answered, the jit took 0.91× the time of code compiled ahead of time (the geometric mean over 14 games), and every answer was the same. Given a fresh copy of every state, so that the converters remember nothing, the jit took 2.2× its own time. The operations above are timed on one position again and again, which flatters the jit’s memory. Here each game plays one run instead: up to 600 frames of an arcade game, or a whole game, hand or deal of a board or card game, 4,601 steps in all. Each run is recorded once by the compiled rules (the robot’s choices with a press of chance now and then, or random legal moves), then replayed by every way from the same start with the same inputs. A page gives back what the jit answered, so each state is the jit’s own: what did not change is the very object converted before, and only the new parts convert.

  • Against code compiled ahead of time. The jit did best against it in Butterfly garden 0.29×, Minesweeper 0.44×, Bricks 0.64×, and worst in Mahjong solitaire 1.53×, Light trails 1.42×, Solitaire 1.39× (its time over the ahead-of-time code’s). Even with fresh copies, remembering nothing, the jit was as fast as the ahead-of-time code or faster in Checkers, Downhill, Bricks, Light trails, Butterfly garden: there its converters, generated from the declared types, already match the hand-written ones. Elsewhere its memory is what keeps it even. Where it was slower, its memory cost more than it saved: see build 6, below. Light trails’ run is short (below).
  • Remembering nothing. With every argument a fresh copy, the jit took 2.2× its own time (the geometric mean), and 2.0× the ahead-of-time code’s; most where the state is large and the call light: Minesweeper 16×, Solitaire 13×, Mahjong solitaire 8×, Mahjong 4×. An expert Minesweeper tap took 19 µs through the jit, 0.31 ms with fresh copies, and 44 µs ahead of time. A page that builds its state anew for each call, rather than giving back what Hazel answered, pays that.
  • The memos as links (build 6). A profile of Mahjong solitaire’s run through the jit put a third of its time in the garbage collector and a quarter in the memos’ WeakMaps, their lookups and inserts: remembering cost more than converting. Build 6 keeps each memo as a link on the objects themselves: a hidden property on a page’s object, not enumerable, so {...answer} does not copy it into a copy the page then changes (a plain one did, and the copy crossed as the answer it was made from); a WeakMap entry for a frozen object; a plain property on a compiled value, which no page sees. Played again on GitHub, the jit took 0.76× the ahead-of-time code’s time over the 14 games, against 0.91× with build 5: Mahjong solitaire 1.53× → 0.85×, Solitaire 1.39× → 0.66×, Gnome dig 1.31× → 0.83×. Every answer was the same. The ratios are within each run: the runners differed between the two runs, and the same ahead-of-time code took 0.76× to 2.24× its earlier time, game by game. Within that spread, Light trails 1.42× → 1.78×, Checkers 0.97× → 1.20× came out worse.
  • Interpreted, and plain JavaScript. The interpreter took 1,729× the jit’s time a call. Plain JavaScript, in the five games that have it, ran 8.7× as fast as the jit.
  • Short runs: some games ended within 120 steps: Light trails, 22 frames; Checkers, 46 moves; Mahjong solitaire, 72 pairs taken; Go, 89 turns; Snake, 116 frames. Their times rest on fewer calls.
  • The clock: each call is timed on its own and the times summed, so the clock adds about 71 ns to a call, small against the microseconds here. Every way but the interpreter plays its run once to warm up, then again until at least five runs and 0.3 s, and the median run is taken; the interpreter plays it once.

Building the rules#

Building a game’s rules with the jit took less time than with the interpreter on every game: 117 ms to 3.7 s, against 511 ms to 6.1 s (23% to 65% of the interpreter’s time). Compiled ahead of time, nothing is built in the page. Both builds read and check the program first; then the interpreter evaluates every module’s definitions, while the jit compiles them and runs the compiled code. For Gnome dig that is 5.6 s interpreted and 3.7 s through the jit, each time a page loads it. An ahead-of-time file is 32 kB to 124 kB (the compiled program, 18 kB of runtime and the converters), against 2.9 MB of hazel-lib.js, and it starts at once.

Against plain JavaScript#

Plain JavaScript runs the 5 games that have it about 16× as fast as hazel-jit’s code compiled ahead of time (geometric mean over 20 operations), from 2.3× to 283×; that is 36,200× as fast as the interpreter. These are the games of ^report(60), which measured the same gap with an earlier hazel-jit (about 13 times) and listed what hazel-jit’s code pays for, one cost at a time: a step budget checked in every function, exact integers through runtime calls, lists as chains of cells, and tuples as arrays carrying their labels. This build’s compiler writes code the same way; this report adds no new measurement of those costs.

What to decide before dev#

Ten questions, roughly in the order they block. Each says what is at stake, the options we see, and what the measurements or the code say.

  1. One PR, or its parts? #2857 is 8,577 lines in one review. Its parts’ own PRs are still written for OCaml’s standard library, so landing them one by one means porting each to Core again; #2857 has the port done. Options: review and merge #2857, closing #2711, #2719 and #2814; land #2837 (the font) and #2842 (the icons) first, on their own, since they are small and independent and change what every user sees; or split #2857 by part, from its ported files.
  2. Does hazel-jit belong on dev, and where? It is 2,215 lines in src/language/dynamics: a second way to evaluate a program, which has to agree with the interpreter. Every new kind of term needs either a rule in the compiler or an explicit refusal (the program then runs interpreted). The livelits line (#2817) has a larger hazel-jit, with livelit views and the mixed mode of ^report(54). Options: on dev in the language library, with agreement tests in CI; on dev as a library of its own that only the package and the web app link; or on the package’s branch only, until the livelits line settles where hazel-jit lives.
  3. How is agreement kept? The answers agree on every operation measured here, but #2857’s CI checks the jit only through 7 library cases. The per-game agreement tests (the games’ rules, compiled and interpreted, the same answers) live on trial/794-games-aot. Options: bring them into #2857 (their programs into test/); or keep agreement as hazeljs-examples’ job, outside Hazel’s CI.
  4. What is the jit for: finished programs, or the editor too? It compiles a program only when every form in it compiles: a hole, a test, a stepper filter or a livelit makes the whole program run interpreted. That suits the games, which are finished programs; it does not help a program being edited. ^report(54)’s mixed mode, the interpreter calling compiled functions, is the path to the editor. Options: say the package’s jit is for finished programs, for now; or plan mixed mode into the package.
  5. The values a page sees are an API: which shapes? A constructor is {tag, value}, a list an array, a labeled tuple an object, a number read by its declared type, a function a function. Every call converts whole values (the crossing). Options: keep plain values only (simple, and the crossing stays); add handles, values kept in hazel-jit’s own shape between calls that a page reads through accessors; or both, plain by default.
  6. Numbers. On this branch an SInt is checked at 32 bits; #2828 gives SInt 64 bits everywhere and is on Core like this branch now, and the 64-bit compiled SInt of trial/694-view-jit needs it. An Int is exact in compiled code (a BigInt past 253), through runtime calls that ^report(60) found among the costs over plain JavaScript. Options: bring #2828 and the 64-bit compiled SInt into #2857 before merging; or merge first and follow with them. Either way, the number model is part of the API above.
  7. What dev’s users would see. The interface font changes on every page, and the icons work offline. The interpreter’s change is small and only reachable from JavaScript (fields put in their type’s order). Option: agree to the font as a team, since it is the one visible change.
  8. Licenses. The Source Code Pro, IBM Plex Sans and Material Icons licenses are now in licenses/ and ship with the editor. Five icons from The Noun Project, under its “Icon Pro” license, still ship, as Hazel’s web app always has. Options: confirm that license allows an npm package to carry them; replace them; or leave them out of the package’s editor.
  9. Who may embed Hazel? Embed mode takes messages only from matthewhammer.org, localhost and its own origin, a list in the code. On dev every hazel.org build would have it. Options: a list kept in the code; any page; or a setting at build time.
  10. Publishing. The package records the Hazel commit, branch and PR it was built from, and Verify checks its hazel-lib.js against that commit. 0.0.10 and 0.0.11 are not on npm. What next for speed#

  1. Convert by declared type, in one step. Done on 2026-11-24 (build 5, the converters, a day later): the jit 9.0× as fast, about even with ahead of time. Write the page’s values straight into hazel-jit’s shapes and back, guided by the function’s declared types, as the hand-written converters of the ahead-of-time files do, instead of through Hazel’s own values. On the 34 operations where the crossing is most of the jit’s time, this should bring the jit near the ahead-of-time column (7.5 ms to near 50 µs for an expert Minesweeper cell). The converters could be generated, and the ahead-of-time files could use them too.
  2. Time the converters on a game’s own run of states. Done on 2026-11-24 (a game’s own run of states): the jit 0.91× the ahead-of-time code’s time; with nothing remembered, 2.2× its own. Drive each game a few hundred steps from a seed and time the calls as a page makes them, each step’s state new, so that the converters’ memory helps only where a part of the state did not change; compare the jit with the ahead-of-time files the same way.
  3. Keep values compiled between calls. With handles (question 5 above), a game’s state stays in hazel-jit’s shape from one call to the next, and only what the page reads crosses. That removes the crossing’s cost for the state entirely, at the price of a second kind of value in the API.
  4. Load time. The jit builds a program each time a page loads it, 117 ms to 3.7 s for these games. Keep the compiled program in the browser’s storage, keyed by the program’s text, or compile it ahead of time when the program does not change, as the games do now.
  5. The costs over plain JavaScript. About 16× remains between hazel-jit’s code and a hand-written game. ^report(60) measured each cost on its own; the next step is to remove the largest where the declared types allow it, for example plain arithmetic where an Int provably stays small.
  6. Agreement in CI. Before any of these, bring the per-game agreement tests into Hazel’s CI (question 3), so a change to the compiler that changes an answer fails there, and not in a game.
