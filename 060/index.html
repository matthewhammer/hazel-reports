How Fast Is Hazel? Five Games, Three Ways

Cyrus asked how fast Hazel is: interpreted, compiled by hazel-jit, and against plain JavaScript. Five games from the Hazel activities answer it here. Each game’s rules and strategy are a Hazel program, run three ways: interpreted by hazeljs, compiled ahead of time by hazel-jit, and rewritten in plain JavaScript, a version written to give the same answers in the same order. All three are timed on one machine, operation by operation and over whole games that Hazel plays against itself.

Every operation, three ways#

Compiled by hazel-jit, the five games’ rules run about 3,300 times as fast as hazeljs interprets them; written in plain JavaScript, the same games run about 13 times as fast again. So plain JavaScript is about 45,000 times as fast as Hazel’s interpreter on these games, and hazel-jit closes all but a factor of about 13 of that distance. Operation by operation the factors spread: compiled over interpreted from 841× (opening a cell on an expert Minesweeper board) to 10,082× (listing Solitaire’s legal moves), and plain JavaScript over compiled from 2× (dealing a Mahjong hand) to 137× (opening that Minesweeper cell).

How much faster, game by game#

Compiled over interpreted varies little between the games, from about 2,000× (Minesweeper) to 5,300× (Go); plain JavaScript over compiled varies much more, from 4.6× (Mahjong) to 26× (Minesweeper). Interpreting costs about the same per step of work in every game, so compiling gains about the same everywhere. How much more plain JavaScript gains depends on what each program does with its data: least where the work is small lists copied as they change, as Mahjong’s tiles are, most where a JavaScript array or bit operation replaces a walk along a list, as on a Minesweeper board (where hazel-jit’s time goes).

Where hazel-jit’s time goes#

Taking out hazel-jit’s step budget, and making its arithmetic plain, saves at most about a quarter of its time: most of the distance to plain JavaScript is elsewhere. Without the step check in every function, the games ran in 0.76 (Mahjong) to 1.04 (Checkers, within the noise) of hazel-jit’s time; with plain-number arithmetic as well, in 0.77 to 0.91.

Every compiled function starts by counting a step. hazel-jit keeps the interpreter’s step limit: each compiled function begins with if (--$R.fuel < 0 || (($R.fuel & 16383) === 0 && performance.now() > $R.deadline)) $R.out();, so a run that loops can be stopped, as the interpreter’s can (^report(54)). Build 2a takes that line out of every function.

Every +, -, * and / on Hazel’s Ints is a call into hazel-jit’s runtime. $R.iadd, $R.isub, $R.imul and $R.idiv keep Hazel’s integers exact past 253, where JavaScript’s numbers stop being exact, by switching to a BigInt there, as the interpreter’s integers are exact (^ticket(757)). Build 2b replaces them with plain number arithmetic, which these games can stand: their numbers stay far below 253.

Most of the rest is the program’s shape: what Hazel gives a program to compute with, and how hazel-jit passes values around. Hazel has lists and no arrays, numbers and no bit operations, and no way to change a value in place. So the Hazel finds the stone at a point of the Go board by walking the rows to its row and along it; tests whether a Checkers square is in a set by dividing the set by a power of two, a power it finds by comparisons; and changes one cell of a Minesweeper board by building a new row and a new list of rows. The plain JavaScript indexes an array, shifts a number, and copies only what changed. hazel-jit adds costs of its own: every function takes one argument, so a call with two makes an array to hold them (has$16([b$19, k$20])), and every labeled tuple is an array whose labels are then set on it as properties, one by one ($R.tup). Removing those would take a compiler change, not a text replacement, so this report does not measure them apart (What next, steps 2 and 3).

Converting the game between the page’s values and hazel-jit’s, on every call, costs little for a game made of a few numbers, and a lot for a big board: 0.2 µs for Checkers, 40 µs for an expert Minesweeper board, most of the 46 µs that opening one of its cells costs compiled. The page holds the game as hazeljs gives it, JavaScript arrays and objects; hazel-jit’s code holds lists as chains of {h, t} cells and labeled tuples as arrays carrying their labels. compiled.js’s adapters convert the whole game in, and the answer out, on every call (the boundary’s own rows in each game’s table). Opening a Minesweeper cell, where plain JavaScript is 137 times as fast, is mostly this: the board, 480 cells of four fields each, built twice for one cell’s change.

The games, one by one#

For each game: what the program decides, where randomness enters, what makes its work grow, and its numbers. Randomness in all five works the same way: Hazel has no random numbers of its own, so the page passes them in, a list of numbers drawn by JavaScript’s Math.random() as an argument. That makes every function a pure function of its arguments. Seeded numbers make whole games repeat exactly, which is how all three versions were timed playing the same games, move for move.

Solitaire (Klondike)#

Compiled, Solitaire’s rules run about 3,700 times as fast as interpreted, and plain JavaScript about 22 times as fast again: listing every legal move takes 160 ms interpreted, 16 µs compiled, 0.9 µs in plain JavaScript.

The program. Three modules (Cards, Deal, Moves; 244 lines with its vocabulary): the deck, the deal, every legal move in a fixed order, a move made, and the win. There is no opponent: the program’s work is the rules.

Randomness. Only the deal: 52 numbers from the page, each taking a card from those left at the place it falls. Every move after the deal is the player’s.

What the work grows with. Listing every legal move tries each card that can move against each of the seven piles and its foundation: the waste’s top card, each run of face-up cards in each pile, and each foundation’s top card, so about (1 + the face-up cards) × 8 checks. The Hazel walks lists to reach the n-th pile or foundation. The deal takes each card from the list of those left, walking it to the card’s place.

Minesweeper#

The hint on an expert board takes 0.58 s interpreted, 0.23 ms compiled and 5 µs in plain JavaScript; Hazel sweeping a whole intermediate board, 115 moves, takes 122 s interpreted, 35 ms compiled and 4 ms in plain JavaScript.

The program. Three modules (Board, Play, Hint; 212 lines with its vocabulary): the mines laid after the first tap (never in its 3 by 3), each cell’s count, a cell opened (and the empty region around it), flags, a number’s neighbours opened at once, and the 💡 hint: a sure move worked out from the open numbers alone. 🤖 plays the hint’s sure moves one after another.

Randomness. The mines: one number from the page for each cell outside the first tap’s 3 by 3, by Knuth’s selection sampling, so exactly the mines asked for, each place as likely as any other. The hint is deterministic: the same board always gives the same sure move. When no number shows a sure move, the hint says so, and 🤖 guesses a closed cell picked at random by the page, not by Hazel, whose rules have no guessing.

What the work grows with. The board’s size and how much of it is open. The hint reads the board once, row by row, making each open cell with closed neighbours a number to reason from. It makes two passes over those numbers to find the mines they force, checking each number’s closed cells against the mines known so far, a list it walks. Then it looks for a number whose mines are all known. So its work grows with the numbers × their cells × the mines known, and so with the board’s size. Opening an empty cell sweeps the whole board, again and again, until no more cells open.

Go#

Hazel’s choice of move takes 0.59 to 0.91 s interpreted, 0.10 to 0.16 ms compiled, and 8 to 16 µs in plain JavaScript; a whole 9 by 9 game of Hazel against itself, 89 moves, takes 71 s, 17 ms and 5.5 ms. Go gains the most from compiling (5,300×), and plain JavaScript gains 10× more.

The program. One module (Go.hz; 235 lines with its vocabulary): the board as rows of points, a group of stones and its liberties, a move (its captures, no suicide, the ko), a pass, Tromp and Taylor’s area score, and the opponent.

The strategy. Hazel values every empty point as its move, in tenths of a point: what the move takes (20 a stone), saves (15 a stone of its own groups in atari), threatens (6 a stone left in atari) and risks (−12 a stone of a group left with one liberty), its liberties, and where it is (the third line best, the edge worst). It plays the best one, or passes when none is worth more than −3 points, or when the other side has passed and it is ahead.

Randomness. Each point’s worth gets one of the page’s random numbers added before the best is picked, drawn fresh for every move, from 0 up to the most set by the Go page’s randomness slider (2 points by default; 0 to 10). It varies Hazel’s play, breaks ties, and can tip a choice between moves within that many points of each other, or tip a weak move over the −3 point floor where Hazel would have passed. At 0 Hazel plays its best move every time: two games it plays against itself at 0 come out the same, stone for stone.

What the work grows with. The points on the board, for each move. Hazel traces the board’s groups once a turn, then values each of the 81 points (49 on 7 by 7), looking up the groups beside it. A capture is valued by playing it on a copy of the board. In the Hazel, the stone at a point is found by walking the rows to its row, then along that row, so each lookup costs about as many steps as the point is far from the corner. The plain JavaScript reads the stone at a point from an array, in one step. Counting the score floods each empty region.

Checkers (English draughts)#

Looking 4 moves ahead, Hazel’s move takes 6.2 s interpreted, 2.2 ms compiled and 0.14 ms in plain JavaScript, 2,800× and 16×; the factors hold at every depth, since the three search the same tree, each move further ahead about 3 times as much work.

The program. One module (Checkers.hz; 141 lines with its vocabulary): each side’s pieces as a set of the 32 dark squares kept in a number’s bits, the moves (jumps are compulsory and go on while they can), kings, the end (no move loses, 80 moves with no capture and no man moving draws), and the opponent.

The strategy. Alpha-beta search: Hazel tries each of its moves, then each answer, and so on, as many moves ahead as chosen, valuing the position at the end by material (a man 100, and 2 for each row it has come; a king 160) for the side to move.

Randomness. Ties only. The page passes 48 numbers, one for each move tried at the top. Of the moves with the best value, the one paired with the largest number is played. The search itself is deterministic.

What the work grows with. The search’s depth. With about 8 moves a position, looking one more move ahead costs several times as much, fewer than 8 because alpha-beta cuts off branches that cannot matter. The compiled times grow from 0.046 ms looking 1 ahead to 18.6 ms looking 6 ahead, at the position 8 moves in. Each position’s moves are found from the sets of squares. The Hazel has no bit operations, so it tests a square by dividing the set by a power of two, where the plain JavaScript shifts and masks.

Mahjong (Hong Kong rules)#

Mahjong is where plain JavaScript gains least, 4.6 times over compiled: a Hazel player’s turn takes 63 ms interpreted, 23 µs compiled and 2.3 µs in plain JavaScript, and the claims on a discard 60 ms, 21 µs and 9 µs. Eight hands of Hazel playing all four seats take 36 s, 20 ms and 10 ms.

The program. One module (Mahjong.hz; 316 lines with its vocabulary): the deal, a turn (a draw and a discard), the claims on a discard (a chow, a pung, a kong, a win) and which comes first, a winning hand and its faan, the points, and what each Hazel player discards and claims. 🤖 plays your seat by the step’s kind 9, as the Hazel players play theirs.

The strategy. A Hazel player wins when it can, declares a kong when it has one, and otherwise discards the tile that helps its hand least: its other copies, its neighbours in its suit, and a little for the middle of the suit or a scoring honour. On another seat’s discard it claims a win, a kong of three, a pung of a pair that is an honour or has few neighbours, or, as the next seat, a chow that breaks no pair.

Randomness. Only the shuffle: 136 numbers from the page, one a tile as its sort key. The players are deterministic: the same table always gives the same discard and the same claims.

What the work grows with. Whether a hand wins, asked again and again. Every step on another seat’s discard asks, for each of the three other seats, whether that discard would complete its hand. That means trying every way the hand makes a pair and four sets, a recursive search over pungs and chows. A player’s own turn asks it once more, then weighs each kind of tile in its hand.

The same answers, three ways#

The three versions of each game give the same answers, value for value, and in the same order where the order matters: the moves listed, the move chosen, the faan counted. Two Node scripts in hazeljs-examples checked it before anything was timed. node/compare-compiled.mjs plays seeded games and compares every answer of the compiled rules with hazeljs’s, and, with --plain, with the plain JavaScript’s:

None differed: every operation’s answer was the same all five ways (the three builds and the two variants), and every whole game ended in the same state.

The plain JavaScript keeps the Hazel’s algorithms and its order, not its data structures. Where the Hazel walks a list, the JavaScript indexes an array. Where it divides by a power of two, the JavaScript shifts. Where it looks a value up in a list, the JavaScript uses a Set or a Map. A JavaScript programmer writing the same game would make those choices, and Matthew asked for the JavaScript to be equivalent in the game, its logic and its strategy. Two places keep Hazel’s exact order where a simpler JavaScript would differ. Mahjong’s shuffle sorts the keys with the Hazel’s own merge sort, whose halves are taken alternately and reversed, so tied keys fall the same way. Minesweeper’s hint keeps the order in which the Hazel lists each number’s closed neighbours, because the first sure move found is the one it names.

What next#

  1. Time every hazel-jit change this way. The workflow three-way timing in hazeljs-examples runs on every change to the rules, the compiled programs or the plain JavaScript. Run against each new hazel-jit commit, its results would chart how the distance to plain JavaScript closes, as Matthew put it: “now, and in the future, as the hazel components become better in performance”.
  2. Split the program’s shape from the compiler. A third JavaScript version of one game, written the Hazel’s way (lists of cons cells, division for bits, a tuple for each call), would show how much of the gap to plain JavaScript is Hazel’s vocabulary and how much is hazel-jit’s code. Checkers and Go are the clearest cases.
  3. Calls without a tuple. Every multi-argument call in the compiled code allocates an array for its arguments and reads them back out. Compiling a known function of n arguments to a JavaScript function of n parameters would remove that allocation.
  4. A cheaper page boundary for big values. Minesweeper’s board crosses whole on every call, in and out: 40 µs on an expert board, most of what opening a cell costs. A page could keep hazel-jit’s own value of the game between calls and convert only what it draws, or hazel-jit could take JavaScript arrays as its lists.
  5. The same three ways in a browser, and on a phone. Each page’s ⚙️ Advanced already times its rules, interpreted or compiled. Adding plain JavaScript there would give these numbers on the devices the activities are played on.

The timing. node/three-way.mjs <game> builds the rules with hazeljs as the page does, loads compiled.js and plain.js, and makes the two variants of compiled.js by text replacement. It plays a seeded game to make each operation’s positions (with the compiled rules; all ways answer the same there). Then it times each operation each way: a call too fast for the clock is run in batches of as many calls as take at least a millisecond, and the median batch, per call, is reported. hazeljs is timed at least 3 times and for at least 1.5 s, the others at least 30 times and for at least 0.3 s, after 20 calls to warm up. Not timed in a browser. These are Node numbers, on a server processor. Chrome runs the same JavaScript engine as Node (V8); Firefox and Safari have their own, and on a phone every time will be several times longer. The ratios between the three ways are what this report is about.
