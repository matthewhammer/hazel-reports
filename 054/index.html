Same Answers as the Interpreter

hazel-jit compiles a livelit's view, and a slide's whole run, from Hazel to JavaScript, so that a slider's step can show in the picture within a frame (^report(50) to ^report(52)). On Friday 2026-11-13 Matthew Hammer and Cyrus Omar met about its next steps. The main one: what the compiled code computes must be what Hazel's interpreter computes, and CI must check it. Here is the plan from that meeting, change by change, and where each change stands. It also covers what it would take to run any piece of a Hazel program this way, not only livelit views, and the direction chosen: a mixed mode, where the interpreter calls compiled functions. This report is revised as the work goes on.

The plan#

Of the meeting's seven changes, six are done on the hazel-jit branch and pass CI, overflow among them: SInt is 32 bits everywhere, each result checked. One is under way: the limits, where eight of the evaluator's 313 programs still meet one, and probes are not begun. Each became a ticket on the work dashboard. Three more tickets came out of the work itself: a crash in the interpreter, now fixed on a PR to dev; a cost in how Hazel checks types at run time; and the oracles, slow on an older phone, now compiled ahead of time. A last ticket is the direction chosen after the meeting, mixed mode. What the team could decide is gathered in questions for the team.

Matthew's summary of the meeting, as he wrote it on 2026-11-15:

  • we want semantic consistency with Hazel the interpreter, and to ensure that with CI, and our design decisions.
  • arb precision Ints and Nats --- we want to use bignum in the output if we can, or something comparable, not native JS numbers for Ints and Nats.
  • when we hit an overflow for any times where that is possible -- we should check each time for non-arb precision numbers --- we should create an indet term / stuck term with that error -- look at existing interpreter cases for inspiration.
  • similar for divide by zero
  • for the output of hazel-jit, we should continue to avoid translating code with holes, and we should exclude "stepper functions" (don't know what that is myself, please explain later).
  • probes, step budgets, and all other limitations we should work to overcome in the coming days.

And Cyrus's concern, which Matthew passed on separately the same day: "We need a way to limit compiled hazel functions that diverge --- we need a step limit. esp if we continue to optimize by including certain jit-compiled hazel functions into the main thread"

What hazel-jit is#

hazel-jit translates an elaborated Hazel program to the text of a JavaScript function, and the page runs that function on its own thread at a livelit's event, to draw the livelits before the interpreter's answer comes back. Hazel's interpreter, in a web worker, still runs every program, and its answer is still the program's result: the probes, the tests and the result panel come from it. So far hazel-jit has been a measurement of how fast compiled Hazel could be (a step of the Witch's slider in 2 to 3 ms, ^report(50)). The meeting's point is that it must also be correct, because whatever it draws, a user reads as what Hazel computed.

A form the compiler does not handle raises an error with its reason, and the page then waits for the interpreter's run, as it did before hazel-jit. So a limit costs speed, never correctness. A compiled run that stops part way (an invalid operation, undefined, or the step budget) is handled the same way. These fallbacks are what keep hazel-jit's answers the same as the interpreter's: where the two would differ, hazel-jit gives no answer and the interpreter's is shown.

The same answers, checked in CI#

Every one of the evaluator's 313 test programs now also goes through hazel-jit in CI. 260 compile, and each gives the interpreter's answer, apart from 27 known ill-typed tests, and those the page never compiles. A new difference fails the build. (^ticket(756).)

The check is a sweep in the evaluator's tests: each test hands its program to hazel-jit, runs the JavaScript, and compares the value with the interpreter's: numbers exactly (floats within a relative 10-9), lists, tuples, labels and constructors by structure, and a function only as being a function. A compiled run that stopped at an invalid operation agrees with an interpreter result stuck at the same error (below). The 27 ill-typed tests are listed by name, and anything else that parts from the interpreter fails its test. The end of each run prints a report in CI's log: how many were compiled, how many agreed, and why the rest were not compiled.

The first sweep, on 2026-11-15 (the full tests), had 316 programs: 237 compiled, 207 agreed, 30 ill-typed, and none differed. It found the rule that programs with type errors stay with the interpreter (below). Merging the six branches found one more parting, with no static error: a value passed through a written type hole to a function that takes another type. That led to the rule that a type hole is a hole. The 49 programs not compiled by rule, and the 4 not compiled for a limit, are these:

Exact integers#

Int and Nat are now exact in compiled code, as the interpreter's are: an integer is a JavaScript number while it is a safe integer (up to 253 − 1), and a BigInt past that. (^ticket(757).) The interpreter's Int and Nat are arbitrary-precision integers (Jane Street's Bigint), and hazel-jit had made them JavaScript numbers, which round past 253: 253 + 1 came out as 253.

Every integer operation normalizes its result back to a number when it fits, so two equal integers are always the same value, and === still compares them. Division rounds toward zero, as the interpreter's does, and stays exact where Math.trunc(a / b) would round. Where plain BigInt everywhere cost a 4.1 times slower fib(25), a 1.5 times slower list walk, and 9.6 times slower model updates, this mix costs 1.6 times, nothing measurable, and 3.7 times (Node, against plain numbers; not a build of the app). On the Witch slide it costs nothing measurable (below). SInt, Hazel's fixed-width integer, stays a JavaScript number: its width is the overflow question.

Divide by zero and other invalid operations#

Where the interpreter stops at an error (dividing by zero, a negative power, int_of_string of something not a number), the compiled run now stops too, and the page shows the interpreter's run, which holds the stuck term with its error. (^ticket(759).) Before, 7 / 0 compiled to Infinity.

The stuck term is the same as the interpreter's by construction, since it is the interpreter's. The alternative, making the stuck term in JavaScript and evaluating around it as the interpreter does, would be a much larger piece of work and is not needed for the answers to agree. Writing the tests for this found a crash in the interpreter itself, on modulo by zero (below).

Overflow#

Decided on 2026-11-16, Matthew Hammer: an SInt has 32 bits everywhere, and a result past them is an error, a stuck term, as a divide by zero is. Done in the interpreter and in hazel-jit, and on the hazel-jit branch since build 48, all of CI passing. (^ticket(758).) Until now SInt overflowed three different ways, depending on how Hazel ran. In the browser, Hazel runs under js_of_ocaml, where an OCaml int has 32 bits, and SInt wrapped silently. A native build of Hazel has OCaml's 63-bit int. hazel-jit had a JavaScript number (checked through hazeljs 0.0.6, which runs Hazel as the browser does):

Now each of these stops, in all three, at a new error, IntegerOverflow ("Error: Integer overflow (an SInt has 32 bits)"). Every SInt operation (sum, difference, product, power, negation, and the one quotient too big, the least SInt divided by −1) checks its result against [−231, 231 − 1]. The interpreter computes the result as a floating-point number first: exact for any two 32-bit operands' sum, and past 253 surely out of range. So the answer no longer depends on the width of the int the interpreter runs on. A value made into an SInt from an Int, a Nat or a Float that does not fit stops at the existing IntegerTooBig, natively too. hazel-jit makes the same checks and stops its run there, for the interpreter's. Seven tests check both agree, values at the edges of 32 bits included (3c9fb4d9ed). Changing the interpreter changes the language, so the interpreter's half is its own PR to dev, hazelgrove/hazel#2828, with tests of its own. Its CI is green; it waits on a review.

Int and Nat cannot overflow (above), and Float follows IEEE 754 in all three.

What stays with the interpreter#

By rule, not as a limit, hazel-jit leaves to the interpreter: any program with a hole (now including a type hole, ? in a type), any program with type errors, and anything the stepper shows. (^ticket(760).) Each is written down at the head of the compiler's source, HazelJit.re.

Holes. Empty holes, multiholes, dynamic error holes and invalid text were already not compiled: the interpreter evaluates around a hole, and its indeterminate result is the point of a hole. Type holes are new, from the merge's sweep. A value passed through ? to a function taking [Int] fails a run-time check when it is a list of floats, and the interpreter shows the failed check. Compiled code has no types to check, and a float and an int are both a JavaScript number, so it cannot tell. No slide writes a type hole. Type errors. The first sweep's 30 ill-typed tests (4 : String, 1 + (4 : String), ...) are programs where the interpreter stops at a failed run-time check. Now the page compiles no program with static errors. Checked on the six slides of the Firefox check, neither rule stopped any slide from compiling. The four slides with compiled runs kept them (a count of 28 against 30 reflects when a run was timed, not a program that stopped compiling):

The stepper's functions, which Matthew asked to have explained. Hazel's stepper shows a program's evaluation one step at a time. Four forms of expression tell it which steps to show: hide P in e (skip the steps matching pattern P), eval P in e (take them without stopping), pause P in e (stop at them), and debug P in e. These are "stepper functions" in the sense Cyrus meant. They only mean something to a run that takes steps, so hazel-jit does not compile them (the reason is "a stepper filter"). Beyond the filters, nothing the stepper shows is drawn from compiled code. The stepper evaluates by the interpreter's own steps, and a livelit inside a probe drawer's stepper, drawn over one of its samples, is now drawn by the interpreter, never from a compiled run's answer (in the code and its tests; not yet checked in a browser).

The other limits, one at a time#

Ranked by the first sweep, the limits most often met were missing builtins, partial application, recursion over more than one name, undefined, and other forms of term. The first three are on the hazel-jit branch, undefined passes CI on its own branch, the other forms pass CI too, and probes are not begun. (^ticket(761).)

  • Builtins: 17 the runtime lacked, now as the interpreter has them: string_match, string_replace, string_search, string_join, string_escaped, string_capitalize, string_uncapitalize, omit_all_labels, the six compare builtins (int, sint, nat, float, bool and string), and invert_ord. Since then, string_sub and string_split too (with the string fix below); from_lvs is the one the sweep still finds.
  • Partial application, f(a, _): the function and the given arguments are evaluated first, in order, then a function of the missing ones.
  • Recursion over more than one name, let (even, odd) = (fun ..., fun ...): each name assigned once, then the tuple of them. This gives the interpreter's answer whenever every part is a function, since a name is only read when a function runs. Any other part stays with the interpreter.
  • undefined, on its own branch (trial/761-undefined, e62f0a855a): seven sweep programs, and more than that. The List builtins written in Hazel (List.head, List.tail and three others) use undefined for an empty list, so every program calling them was not compiled at all. A compiled run that reaches undefined now stops, as for an invalid operation; one that does not reach it costs nothing. With it the fast checks pass, and all seven programs compile and agree: 250 of the 313 compiled, 223 agreed, none differ (CI run 43899240156). One worry did not come true. Hazel gives undefined the hole type, the same as a written ?, so the type-hole rule above might have caught it, but in none of these programs does an ascription around it carry the hole. All of CI passes with it (static, fast and full tests).
  • Tuple extension and labels as values, the six programs the first sweep counted as "this kind of term": (a=1, b=2) ... (c=3), and label literals handed to project_labels, select_labels and omit_labels. Each now compiles as the interpreter defines it, on a branch above undefined's (trial/761-labels, 1087cdcace). All of CI passes, and with it the sweep compiles 256 of the 313 programs, all agreeing apart from the 27 known ill-typed tests.
  • Strings beyond ASCII, a parting the sweep could not see, because the evaluator's tests use only ASCII strings. Hazel counts a string's length and offsets in graphemes, the characters a reader sees. hazel-jit counted JavaScript's UTF-16 units, so string_length of an emoji was 2 compiled and 1 in Hazel. Now it counts graphemes, as Hazel does, and string_sub and string_split are compiled too. This is on a branch above the label work (trial/761-strings, 83f4dba237), with tests on an emoji, an accent written as a separate mark, and a flag, and all of CI passes.
  • Reverse application, x |> f, which Hazel holds as an application written the other way round and steps alike: compiled as f(x) is.
  • Next: labels that are not names, an expression as a module member, the builtin from_lvs. The three fixpoints over a pattern like _ are ill-typed tests, whose interpreter answers are failed casts, so compiling them would only add partings.
  • Probes are the largest: a probe shows the values that passed through it, and compiled code records none. Today a probe always shows the interpreter's run, which is correct, and never faster. Recording samples from compiled code would mean deciding what a sample is when the code that made it has no steps.
  • The sweep's last limits, on their own branch (trial/761-last-limits, dd85975e96, fast checks green, CI run 44134100041): an explicitly unlabeled entry, (_=e), compiled as the entry itself; from_lvs; a module member that is an expression, evaluated and dropped as the elaborated module's let _ = e is; and a recursive definition's part that is not a function, when it names none of the names. A tuple label that is a hole, (?=1, 2), counts as a hole now, which the rule keeps with the interpreter. Of the 313 programs, 260 compile, 233 give the interpreter's value, none differ, and 27 are the known ill-typed tests. Four still meet a limit: three ill-typed fixpoints over patterns that are not names (fix _, fix (), fix 0), left so on purpose, and one recursive definition whose value part names one of its names inside a function it builds, which a finer check could compile. CI found one thing on the way: let (_=x) = (_=1) in x is (_=1) to the interpreter and 1 compiled, which the evaluator's own tests count as the same (they ignore explicit unlabelling), and so now does the sweep.

A step budget#

Every compiled function now counts its calls and every 16,384 calls reads the clock. A run past its budget (50 ms or 50 million calls) stops, and the interpreter's run answers. (^ticket(763).) Cyrus's concern is that compiled code runs on the page's own thread, so a Hazel function that never ends would freeze the page. The interpreter has a 20-second timer and a limit of 100 million transitions.

Endless recursion turned out to be the smaller risk: it overflows JavaScript's stack in about a millisecond, and that error is caught like any other. The real risk is a run that ends, but late (fib(45)), and the clock catches that. In Node the counter costs 11 to 26%, and 20 to 33% with the clock (not a build of the app). On the Witch it costs nothing measurable in one run (below), well inside a frame. A cheaper counter, at only the calls that can recur, is the next step.

What it all costs#

On the Witch slide, the changes together are not measurably slower than build 45: over a 3 s drag the page's view took 5.4 to 7.2 ms a frame from build 46 to build 49 (6.8 ms, about 147 fps, on build 49), against build 45's 5.8 (about 172 fps); hazel-jit's own run is 1.1 to 1.6 ms of it. One run each. The spread between single runs (5.4 to 7.3 ms) is as large as any difference, so the numbers show no cost and no gain. On all six slides of the check, build 49 drew the same pictures as the interpreter, with no errors (run 44137800916: 6 slides, 0 differences). Every build stays far inside the 16.7 ms of a 60 fps frame. The fps assumes that updating the state is free: it is what the view alone allows.

Found along the way#

Modulo by zero crashed Hazel's interpreter, on dev too; the fix is a PR to dev, hazelgrove/hazel#2825, waiting for review. (^ticket(764).) int_mod, sint_mod, nat_mod and float_mod answered a zero divisor with an error naming a builtin mod that does not exist, so evaluating it raised an exception instead of showing "Error: Divide by Zero". This dates from at least 2025-07-02. Renaming was not enough: the error's inside was then stepped again, and the error was lost. So the fix also makes a builtin's error final, as an operator's already is. CI passes with it.

A Hazel function that declares what it takes but not what it returns costs 5 to 7 times as much a step at run time, in the interpreter. (^ticket(762).) It was measured in a Tarot deck written in Hazel: a step of take cost 0.36 ms with only its argument types, and 0.07 ms with its whole type. Declaring every type made a deal 3.7 times faster. The cause is not unknown types, but where the ascriptions (the run-time type checks) land: on each case arm's result, in each copy of the body, rather than once around it. This is the interpreter's cost, not hazel-jit's, and it is the kind of check Matthew Keenan asked about in ^report(53). The next step is to count the checks per call.

Beyond livelits#

Most of hazel-jit's limits come from one assumption: it compiles a whole program that is closed, finished and well typed, and its answer is only a preview, with the interpreter's run as the real answer. Running any piece of a program in JavaScript breaks each part of that. The direction chosen is a mixed mode: the interpreter keeps running the program and calls compiled functions as it calls a builtin. Matthew Hammer asked on 2026-11-16 what it would take to apply hazel-jit to any fragment of elaborated Hazel, and which of its assumptions stand in the way. Of three ways to go, he chose the third: "I like the mixed mode idea a lot."

What today's design assumes#

  1. The program is closed. Its only free variables are builtins, and a closure carrying its own environment is not compiled. A slide's run starts from nothing, so this has not mattered. A piece from inside a program has free variables bound to the interpreter's values, closures among them: those must be converted on the way in, and an interpreter closure must either be compiled too or be called back from JavaScript.
  2. The compiled answer is a preview. The page draws from it, and the interpreter's answer, arriving later, is the program's result. If compiled code gives the result itself, every remaining difference is a wrong answer, and the consistency check becomes a gate.
  3. Falling back is all or nothing, and costs nothing extra, since the interpreter runs anyway. For a piece of a program, falling back means running it twice, partly in JavaScript and then in the interpreter. That is safe only because evaluation has no side effects.
  4. The answer's type is known. Converting an answer back needs its type: a Float 1.0 and an Int 1 are the same JavaScript number, and without a type a tuple's labels are guessed from its properties. A view's answer is always Html.
  5. The inputs are small. Views draw small models, so recursion stays shallow. JavaScript has no tail calls and a stack of thousands to tens of thousands of calls, depending on the browser, where the interpreter keeps its stack on the heap. A List.map over 100,000 elements works in the interpreter and overflows compiled; today that falls back, correct but slow.
  6. Three shortcuts are for livelits only: a livelit's model is a parameter, so a slider step does not recompile; each view's answer is collected by its projector; and Html goes straight to the page's DOM without becoming Hazel terms. In general, every edit changes the code, so it is compiled again, and new code starts cold in the JavaScript engine. Compiling is quick (the Witch's largest livelit definition, 62,000 nodes: 6 ms to translate, 9 ms for the browser to parse), but what to cache by, and what to make a parameter, come back as questions.
  7. The program is finished. Holes, type holes and type errors go to the interpreter by rule (above). A program being edited usually has holes, so compiled code helps only its complete parts. That argues for compiling pieces rather than whole programs.

What is new in the general case#

  1. Divergence and long runs. The step budget bounds a freeze. But its units are calls and time, not the interpreter's steps, so compiled code may finish where the interpreter would time out, or the reverse. If the same answers include the same timeouts, the limit needs a definition in the language that both count the same way. A piece of a program that draws nothing belongs in the worker, where a long run freezes nothing.
  2. The boundary costs. Converting values in and out builds Hazel terms and makes new ids. ^report(45) found a livelit's render about 40 times slower with that trip in and out than compiled alone. Small pieces that cross often lose most of the gain, so pieces must be large, or values must stay in JavaScript between calls.
  3. What the interpreter records: probes, the stepper's steps, traces, test results, and the ids that tie a value to the code that made it. Compiled code records none of them. A piece holding a probe or a test, or shown in the stepper, stays with the interpreter.
  4. Evaluating around holes, Hazel's central feature: a program with holes still runs, and its result holds the holes. Compiled code cannot; it stops.
  5. Run-time type checks. Where a value passes through the unknown type ?, the interpreter checks it as the program runs; compiled code has no types to check with. Values entering a compiled piece typed ? would need checking on the way in.
  6. Every builtin twice. Each of Hazel's builtins written in OCaml has a twin written by hand in JavaScript, and a general compiler meets them all. Looking for this report found one that differed: string_length (above, now fixed).
  7. Security. Compiled code runs through new Function with the page's full access. For livelits, that is slides we wrote; for any piece of any program, including one opened from a shared link, a bug in how the compiler escapes text would let a program run its own script in the page. A page whose security policy forbids eval cannot run it at all.
  8. Two implementations to maintain. Every new language feature must either compile or fall back, and the consistency check must cover it.

Three ways to go#

  1. Whole closed programs, in the worker, with the interpreter as the fallback: close to what we have, without the livelit shortcuts, and unable to freeze the page.
  2. A fragment interface: compile a closed function whose free variables are typed parameters, convert its inputs once, and keep its values in JavaScript.
  3. Mixed mode, the one chosen: the interpreter calls compiled functions as it calls builtins, for functions that are complete, free of probes and worth compiling. The first two are steps toward it.

Mixed mode#

Mixed mode keeps the interpreter in charge of the program, so holes, probes and the stepper work as they do now, and gives its complete functions compiled speed. A first step is built (^ticket(766), below). The sketch it follows:

  • What is compiled: a function whose body is complete (no hole, type hole or type error), holds no probe, test or stepper filter, and whose free variables are builtins or other compiled functions, with its whole type declared. The declared type converts the answer back. ^ticket(762) found that declaring it also makes the interpreter's own steps 5 to 7 times cheaper.
  • How it is called: a new kind of value beside a builtin. Applying it converts the argument to JavaScript once, runs the compiled function under the step budget, and converts the answer back by the declared type. It runs in the worker, where the interpreter runs, so a long call freezes no page.
  • Falling back, one call at a time: on any stop (the budget, an invalid operation, undefined, an argument that will not convert because it holds a hole), the interpreter applies the original Hazel function to the same argument. Evaluation has no side effects, so running a call twice is safe. A program with holes elsewhere still runs its complete functions compiled, and the interpreter evaluates around the holes.
  • Probes and the stepper: putting a probe in a function takes that function out of the compiled set at the next compile, and the rest stay compiled. The stepper either runs on the interpreter alone or shows a compiled call as one step, as it shows a builtin's.
  • The boundary: compiled functions call one another directly in JavaScript, without crossing. A large value passed again and again (a list) can be converted once and remembered by the identity of the interpreter's value.
  • Checking it: the consistency sweep runs each evaluator test a third way, mixed, and compares with the interpreter alone.
  • Where it hooks in: the interpreter applies a builtin through one lookup by name (Transition.re, in Builtins.forms_init), and a builtin's answer is a term the interpreter goes on evaluating. So a compiled function can be a builtin made at run time, with no new kind of value. A compiled function bound by a let becomes such a builtin. When the call finishes, the builtin returns the answer. When it stops, it returns the application of the original Hazel function to the same argument, and the interpreter evaluates that as it would have anyway. The call already shows in a probe's call stack and in the stepper as a builtin's does.

The first step, built on 2026-11-17

Mixed mode's first step is on its own branch, trial/766-mixed, beside the prototype: the interpreter runs the program, and calls each top-level function and module member with its whole type declared as compiled JavaScript. On 0e56bdbd0a (CI run 44137711359, green), the consistency check found 6 evaluator programs with a function to compile (7 functions), and all 6 gave the interpreter's answer; 29 other functions were left to the interpreter because their whole type is not declared, which bears on the question of which functions to compile. Measured on larger programs (below): a recursion compiled whole runs hundreds of times as fast; the Petri net rule 7 times (22 times on the branch's own run, where the interpreter took 463 ms rather than 121: these are single runs, and noisy); the I Ching 5 times, since only 13 of its functions compile so far (its readings call other modules' members, Lines.becomes, which the rewrite does not see yet); and a one-line function called 500 times from interpreted code is slower than not compiling it, each call's crossing costing more than its work.

  • Which functions: a let at the top of the program, or a member of a module there, that binds a function whose whole type is declared (let f : A -> B = fun ...), with no unknown in it. Each is compiled with the functions accepted before it that are in scope there, and the type aliases among them, so it can call them. One that names anything else, an earlier let that is not such a function, is left to the interpreter, and the reason kept.
  • How the interpreter reaches it: the program is rewritten before it runs. The interpreter still evaluates each such definition to its own closure, then hands the closure to a builtin made at run time, which keeps it and gives back a second builtin, the compiled function. The rest of the program sees that builtin under the function's name. The interpreter's one change is where it looks a builtin up: a table filled at run time, after its fixed one.
  • A call: the argument is carried into JavaScript, the compiled function runs under a budget (50 million calls or 1 s), and the answer comes back by the declared result type. On any stop it falls back for that call alone: the interpreter applies its own closure to the same argument, as it would have anyway. An argument holding a hole, an invalid operation, the budget, or an answer that does not carry back each make a fall back.
  • Checked: the consistency sweep runs every evaluator test a third way, mixed, against the interpreter alone, and reports how many agree. Hazel-jit's own tests check nine programs: recursion; a call to an earlier function; a hole elsewhere, the function still compiled; a hole in the argument and a division by zero, each falling back; lists and constructors; a whole Float; and a module's members.
  • Not yet: no setting in the app, and no hook where the worker evaluates. The stepper shows a compiled call as one builtin step, and the rewritten definitions lose their probes.

Step counts and probes, as the interpreter's#

Compiled code can count exactly the steps the interpreter takes, in every program it compiles, with care in three places. With those counts it can make the interpreter's own probe samples, with two limits. Nothing found so far makes either impossible: the costs are a little run time, a tie to the interpreter's internals, and the work. This answers Matthew and Cyrus's two questions of 2026-11-13 (^ticket(767)). Not built yet.

What the interpreter counts. Its count goes up by one at every transition, whichever of its 36 kinds: those that interpret the program (a variable looked up, a let bound, a function applied, an operator, a case, a projection) and those that are bookkeeping (a closure wrapped, parentheses removed, a cast). It goes up one more after each pattern match. The count is the same with or without incremental reuse: a reused result adds the steps it took when it was first computed, so that probe samples stay where they were. Each probe sample is stamped with it: the span of steps from its start to its end.

The counts, measured. For 57 small programs, each a construct apart from the last, the interpreter's count is regular enough to read off (^ticket(767)'s calibration, CI run 44131334098). A literal is a step. An operator or a pair of parentheses adds one. A let adds three of its own: binding, its pattern, and completing the closure around its body. Each level of a simple recursion, if n == 0 then 0 else f(n - 1), adds exactly 16 (18, 34, 50, 66 for f(0) to f(3)). A declared Int -> Int adds one cast step to each call. Some counts need the interpreter's bookkeeping to explain: true && false takes 4 and false && true 3. The whole table:

Why compiled code can match it. hazel-jit translates the program construct by construct and runs it in the same order as the interpreter: arguments first, left to right. Most constructs take a fixed number of steps of their own, apart from their parts: an operator one; a let one, and one for its pattern; an application one, one for its pattern, and the closure's bookkeeping. So the compiler can add, wherever code runs straight through, the steps the interpreter takes there. That is one addition for each straight run of code, about what today's budget counter costs (^ticket(763)). Then the budget and the interpreter's step limit are one number, in one unit.

Where it needs care: the "if not, why not".

  1. Casts carried by functions. A function that has passed through a typed boundary carries the cast with it, and each call through it takes the cast's steps too. How many depends on where the function value has been, not on the code that calls it. Compiled code erases types, so its functions would carry the steps their casts cost, as a number on the JavaScript function.
  2. Casts pushed into code not yet run. A cast around a list or tuple literal is pushed into its parts, and each part then takes steps of its own. This is fixed by the code, so the compiler can follow it, but only by following the interpreter's cast rules exactly.
  3. The rules live in the interpreter's code, not in a specification. There are 36 kinds of step, the extra step after a pattern match, and steps that rebuild a term and evaluate it again under the same id. Some of this is bookkeeping that changes when the interpreter does: a cast through a whole value became one step, for speed, this autumn. So the counts can be held equal only by checking, as values are. The consistency sweep would compare each evaluator test's count with the interpreter's, and a difference would fail CI.

The programs hazel-jit does not compile at all (holes, stepper filters, tests) stay with the interpreter, counts and all. A question for the team: count every step, or only those that interpret the program? Probe samples' spans are in every step today, so to make the same samples compiled code would count them all.

Probes, given the counts. A sample records where (the expression), when (its span of steps), the value, the variables the probe refers to, and the call stack: for each call, the application, the function's name and where it was defined. Compiled code knows the expression at compile time, the steps with the counts above, and the value and variables as JavaScript values. For the call stack it would keep a stack of its own, a frame pushed and popped at each call, paid for only in a program with probes. The way to share the probe machinery rather than write it twice: compiled code emits the same events the interpreter emits as it runs (a span opened, a call entered, a span closed), at the same steps, and the interpreter's own code turns them into samples.

The two limits. First, a sample's value has to come back as a Hazel value, which needs its type at the probe: elaboration has it. A function value comes back only if hazel-jit made it, and not a recursive one. Second, converting each sample's value and variables is the costly part, so it should happen when the page shows a sample, not at every step. The stepper is another matter: counts say how many steps a compiled call took, but the stepper shows the terms in between, and compiled code has none, so it stays the interpreter's.

The way there. (1) The sweep prints each evaluator test's count from the interpreter beside one from compiled code under these rules: how many match exactly, and where they differ. (2) Casts carried by functions. (3) The budget in steps, as one with the interpreter's limit (^ticket(763)). (4) In mixed mode, a compiled call adds its steps to the interpreter's count, so a program's count is the same mixed or not. (5) Probes: the events from compiled code, checked against the probe tests' samples.

Compiled ahead of time, for older phones#

A third use, now a working prototype: compile a hazeljs app's Hazel when the site is built, and ship the JavaScript, so that an older phone loads neither Hazel's interpreter nor its build of the program, and every call runs compiled. On the older Android phone, the I Ching compiled this way is ready to cast at 0.8 s instead of 3.7 s, and a reading takes under a millisecond instead of 86 to 113 ms. It gives hazeljs's answer on all 8,102 checked, in 33 kB instead of 2.8 MB. Since the oracles' 0.0.13 both of them, the I Ching and the Tarot, run compiled by default: the Tarot's 6,400 deals checked are hazeljs's too, and a Celtic Cross takes 0.008 ms instead of 46, in Node. The idea is Matthew Hammer's, on 2026-11-16, after trying the two hazeljs oracles (an I Ching and a Tarot, whose rules are Hazel run by hazeljs in the page) on an older Android phone in Firefox: painfully slow to draw each card or line, and on each key press in the I Ching's question.

What a page like that costs, measured on a laptop:

  • Hazel's library, hazel-lib.js: 2.8 MB of JavaScript (650 kB compressed), 174 ms to load in Node.
  • Building the program (parsing, the statics, elaboration), once per page: 621 ms for the I Ching and 499 ms for the Tarot in Node, 0.4 to 0.9 s in the browser.
  • Each call, interpreted: a cast 0.4 ms by coins and 1.2 ms by yarrow; a Tarot deal 7 ms for one card, 47 ms for a Celtic Cross, 105 ms for a year ahead.
  • Hazel's editor in each listing of the rules: a whole Hazel app, 7.2 MB of JavaScript and about 49 MB of memory, 1.9 s to load empty. The I Ching's page opened five, the Tarot's four.

The editors went first. Since the oracles' 0.0.8, a listing stays text until its button opens the editor, and the I Ching's page, Hazel ready to cast, holds 28 MB. Since 0.0.9, each oracle measures a device's speed and gives a line to compare devices with. The phone's first line, from the I Ching (Firefox 160 on Android, eight cores): Hazel was ready 3.7 s after the page opened, its build of the program 2.9 s of that; a cast took 3 ms by coins and 9 ms by yarrow, a reading 113 ms, and drawing the reading 149 ms to the next frame, since the page asked Hazel for the reading at every redraw. A key press in the question took one frame, 17 ms, with no editor open. The same work in Node on the laptop: the build 600 ms, a cast 0.6 and 1.5 ms, a reading 20 ms, so the phone is about five times slower. In 0.0.10 the I Ching declares every function's whole type (a reading 13 ms on the laptop, the build 480 ms) and asks for the reading once for each set of lines. The phone's line from 0.0.11, still interpreted: the build 2.5 s, a reading 86 ms, and drawing the reading one frame, 17 ms, where it was 149.

Compiling ahead of time would take the rest. hazel-jit would run on the app's Hazel modules when the site is built, and the page would load the compiled JavaScript instead of the library: no build at load, and each call compiled. ^report(50) measured a Petri net rule at 7.19 ms interpreted against 0.011 ms compiled, in Node. Hazel's library and its editor would load only when someone edits the rules, and then the interpreter runs the edited program, as it does now.

The oracles' programs are what hazel-jit compiles best: closed, complete, every function's whole type declared, no probes. So this is the first path above, done before the page loads rather than in it. The prototype, the oracles' 0.0.11, has the four pieces it needs:

  • A build step: a test on hazelgrove/hazel's branch trial/765-iching-aot compiles the I Ching's program as hazeljs joins it (the preamble, each module as module Name = { ... } in, the page's tail) and prints the JavaScript; the oracles' tools/make-compiled.py wraps it, with hazel-jit's runtime from the same commit, into i-ching/compiled.js. For now the compiler runs in CI, as nothing else builds hazel-jit; inside hazeljs, it would be one call in the site's own build.
  • Values at the edge: hazel-jit's values in JavaScript are not hazeljs's (a constructor is {c, v} rather than {tag, value}, a list is a chain of cells rather than an array), so the two exported functions get a small adapter, written from their declared types.
  • The same answers: node/compare-compiled.mjs runs both, compiled and hazeljs: every set of six lines with every pattern of changing lines (4,096), the readings of fewer lines, and 4,000 casts by coins and by yarrow. None differs. Three agreement tests in hazel-jit's own CI check the same program against the interpreter.
  • Saying which engine answered: the page, opened with ?compiled (or by a link under ⚙️ Advanced), says "compiled Hazel" on each line and reading. Editing the rules loads hazeljs and runs them as before.

  2. Who reviews the fix for modulo by zero (hazelgrove/hazel#2825)? Our lean: Anyone who knows the evaluator; it is small. It decides: Whether the interpreter still crashes on int_mod(7, 0).

Mixed mode#

  1. Which functions get compiled? Our lean: Let-bound functions with their whole type declared (let f : A -> B = fun ...), complete, with no probe. The elaborated type of any function would reach more, but it can hold unknowns, and the answer is converted back by that type. It decides: How much of a program runs compiled, and whether Hazel should nudge people to declare types; ^ticket(762) says that pays in the interpreter too.
  2. What does the stepper show for a compiled call? Partly answered 11-13: a compiled call counts the steps it would have taken. Our lean, still: mixed mode off while the stepper is open, since the stepper shows terms and compiled code has none. It decides: Whether stepping a program ever skips steps.
  3. Probes in compiled code: what is a probe's sample when the code that made it has no steps? Answered 11-13: compiled code counts the interpreter's steps, and with them makes the interpreter's samples (below). Until then, a probe takes its function out of the compiled set. It decides: The design of probes, the last of ^ticket(761)'s limits.
  4. Main thread or worker? Our lean: Mixed mode in the worker only, where the interpreter runs; the main thread keeps only livelit views, as now, under the step budget, which answers Cyrus's concern. It decides: Whether a long compiled call can ever freeze the page.
  5. Falling back runs a call again from the start. Is that safe for good? Our lean: Yes while evaluation has no effects. Is any effect planned (a livelit updating its model, randomness, input and output)? It decides: Whether one-call-at-a-time fallback stays correct.
  6. A program with a type error elsewhere: compile its sound functions? Our lean: Yes, per function: a value that does not fit the declared type is caught where it crosses, and that call falls back. Today a single error anywhere keeps the whole program interpreted. It decides: How often a program being edited, so often with an error somewhere, runs compiled.
  7. One step budget or two? Answered 11-13: one, in the interpreter's steps, which compiled code will count exactly. Compiled code today has its own, 50 ms or 50 million calls a run. It decides: What a budget means to a user, and what the stepper and probes count.

What compiled code must match#

  1. String length in graphemes: intended? Our lean: Keep it. Compiled code now counts as the interpreter does, with a fast path for ASCII. It decides: The meaning of string_length and string_sub for text beyond ASCII.
  2. Labeled tuples as JavaScript arrays carrying their labels: fine? Our lean: Fine inside compiled code. Labels named length, __proto__ or starting with $ are stored under $ + label. hazeljs gives a labeled tuple to JavaScript as an object, so the boundary converts. It decides: The shape of values between Hazel and JavaScript, in hazeljs and in mixed mode.
  3. The evaluator's ill-typed tests (27 stop at a failed run-time check; 3 fixpoints over _): keep them on a known list? Our lean: Keep them: they test the interpreter's casts, which compiled code never needs, since it compiles no program with type errors. It decides: Whether the consistency sweep keeps a list of known exceptions.

Landing and scope#

  1. How does hazel-jit reach dev? Our lean: In small PRs, as ^report(53) proposes: the two fixes above; then the compiler with the consistency sweep in CI and no user-facing change; then mixed mode behind a setting; then livelit views on the main thread. It decides: The order of review, and when anyone outside the prototype branch sees compiled code.
  2. Should hazeljs ship the compiler? Our lean: No: a tool at a site's build time, with only the runtime (about 17 kB) shipped to pages. hazeljs's library is already 2.8 MB. It decides: How an app like the oracles gets compiled code without CI's help.
  3. Undeclared result types cost a step 5 to 7 times (^ticket(762)): fix in elaboration? Our lean: Yes: put the result's ascription once around the body, where the typed form has it. It changes where the interpreter inserts its run-time checks, so it needs an owner who knows elaboration. It decides: Whether every Hazel program, not only compiled ones, gets the speed.

Met by an app#

The astrology oracle (hazeljs-oracles 0.0.15, ^ticket(768)) is eleven modules of numeric code, the Sun, Moon and planets from Meeus's and Schlyter's series, run by hazeljs. Writing it met two problems in the interpreter's side of Hazel, filed this morning.

  1. An answer that is a function grows past gigabytes (hazelgrove/hazel#2832): fix Evaluator.finish? Our lean: Yes. finish substitutes the environment into the answer, so a function that reaches earlier modules copies their closures into it, nested; leave a closure in the answer as a closure, and substitute only for display. Compiled code never meets it: a compiled function is a JavaScript function. It decides: Whether a hazeljs page can take functions from a program of many modules. The astrology page cannot today, so it builds the whole program again for each chart, about 1.3 s.
  2. Float literals print with six decimals (hazelgrove/hazel#2831): print them so they read back? Our lean: Yes, the shortest form that reads back as the same number. Today a literal with more decimals sends its module to the recovering parser, whose cost grows much faster than the module. Compiled code already prints floats exactly, and evaluation compares them by value, so the interpreter and compiled code agree on them; only parsing and the terms' own equality (six decimals) are affected. It decides: Whether numeric programs can write constants as they are; the astrology rules write long ones as ratios.
