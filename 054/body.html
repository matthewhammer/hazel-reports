Same Answers as the Interpreter

hazel-jit compiles a livelit's view, and a slide's whole run, from Hazel to JavaScript, so that a slider's step can show in the picture within a frame (reports 050 to 052). On Friday 2026-11-13 Matthew Hammer and Cyrus Omar met about its next steps. The main one: what the compiled code computes must be what Hazel's interpreter computes, and CI must check it. Here is the plan from that meeting, change by change, and where each change stands. This report is revised as the work goes on.

What hazel-jit is

hazel-jit translates an elaborated Hazel program to the text of a JavaScript function, and the page runs that function on its own thread at a livelit's event, to draw the livelits before the interpreter's answer comes back. Hazel's interpreter, in a web worker, still runs every program, and its answer is still the program's result: the probes, the tests and the result panel come from it. So far hazel-jit has been a measurement of how fast compiled Hazel could be (a step of the Witch's slider in 2 to 3 ms, report 050). The meeting's point is that it must also be correct, because whatever it draws, a user reads as what Hazel computed.

A form the compiler does not handle raises an error with its reason, and the page then waits for the interpreter's run, as it did before hazel-jit. So a limit costs speed, never correctness. A compiled run that stops part way (an invalid operation, undefined, or the step budget) is handled the same way. These fallbacks are what keep hazel-jit's answers the same as the interpreter's: where the two would differ, hazel-jit gives no answer and the interpreter's is shown.

The same answers, checked in CI

Every one of the evaluator's {{checks}} test programs now also goes through hazel-jit in CI. {{compiled}} compile, and each gives the interpreter's answer, apart from {{not_a_value}} known ill-typed tests, and those the page never compiles. A new difference fails the build. (Ticket 756.)

The check is a sweep in the evaluator's tests: each test hands its program to hazel-jit, runs the JavaScript, and compares the value with the interpreter's: numbers exactly (floats within a relative 10-9), lists, tuples, labels and constructors by structure, and a function only as being a function. A compiled run that stopped at an invalid operation agrees with an interpreter result stuck at the same error (below). The {{not_a_value}} ill-typed tests are listed by name, and anything else that parts from the interpreter fails its test. The end of each run prints a report in CI's log: how many were compiled, how many agreed, and why the rest were not compiled.

Exact integers

Int and Nat are now exact in compiled code, as the interpreter's are: an integer is a JavaScript number while it is a safe integer (up to 253 − 1), and a BigInt past that. (Ticket 757.) The interpreter's Int and Nat are arbitrary-precision integers (Jane Street's Bigint), and hazel-jit had made them JavaScript numbers, which round past 253: 253 + 1 came out as 253.

Every integer operation normalizes its result back to a number when it fits, so two equal integers are always the same value, and === still compares them. Division rounds toward zero, as the interpreter's does, and stays exact where Math.trunc(a / b) would round. Where plain BigInt everywhere cost a 4.1 times slower fib(25), a 1.5 times slower list walk, and 9.6 times slower model updates, this mix costs 1.6 times, nothing measurable, and 3.7 times (Node, against plain numbers; not a build of the app). On the Witch slide it costs nothing measurable (below). SInt, Hazel's fixed-width integer, stays a JavaScript number: its width is the overflow question.

Divide by zero and other invalid operations

Where the interpreter stops at an error (dividing by zero, a negative power, int_of_string of something not a number), the compiled run now stops too, and the page shows the interpreter's run, which holds the stuck term with its error. (Ticket 759.) Before, 7 / 0 compiled to Infinity.

The stuck term is the same as the interpreter's by construction, since it is the interpreter's. The alternative, making the stuck term in JavaScript and evaluating around it as the interpreter does, would be a much larger piece of work and is not needed for the answers to agree. Writing the tests for this found a crash in the interpreter itself, on modulo by zero (below).

Overflow

Not begun: SInt overflows three different ways today, depending on how Hazel runs, so the plan's "an indet term with that error" first needs one width chosen. (Ticket 758.) The recommendation is 32 bits everywhere, what the browser has always done, with each SInt operation checked in the interpreter and in hazel-jit, and an IntegerOverflow error where the result does not fit. That changes the interpreter too, so it is a decision for Matthew and Cyrus.

In the browser, Hazel runs under js_of_ocaml, where an OCaml int has 32 bits, and SInt wraps silently. A native build of Hazel has OCaml's 63-bit int. hazel-jit has a JavaScript number (checked through hazeljs 0.0.6, which runs Hazel as the browser does):

What stays with the interpreter

By rule, not as a limit, hazel-jit leaves to the interpreter: any program with a hole (now including a type hole, ? in a type), any program with type errors, and anything the stepper shows. (Ticket 760.) Each is written down at the head of the compiler's source, HazelJit.re.

Holes. Empty holes, multiholes, dynamic error holes and invalid text were already not compiled: the interpreter evaluates around a hole, and its indeterminate result is the point of a hole. Type holes are new, from the merge's sweep. A value passed through ? to a function taking [Int] fails a run-time check when it is a list of floats, and the interpreter shows the failed check. Compiled code has no types to check, and a float and an int are both a JavaScript number, so it cannot tell. No slide writes a type hole. Type errors. The first sweep's 30 ill-typed tests (4 : String, 1 + (4 : String), ...) are programs where the interpreter stops at a failed run-time check. Now the page compiles no program with static errors. Checked on the six slides of the Firefox check, the rule stopped none from compiling; the four with compiled runs kept them (the Witch's 28 against 30 reflects when its run was timed, not a program it stopped compiling):

{{tab_slides}}

The stepper's functions, which Matthew asked to have explained. Hazel's stepper shows a program's evaluation one step at a time. Four forms of expression tell it which steps to show: hide P in e (skip the steps matching pattern P), eval P in e (take them without stopping), pause P in e (stop at them), and debug P in e. These are "stepper functions" in the sense Cyrus meant. They only mean something to a run that takes steps, so hazel-jit does not compile them (the reason is "a stepper filter"). Beyond the filters, nothing the stepper shows is drawn from compiled code. The stepper evaluates by the interpreter's own steps, and a livelit inside a probe drawer's stepper, drawn over one of its samples, is now drawn by the interpreter, never from a compiled run's answer (in the code and its tests; not yet checked in a browser).

The other limits, one at a time

Ranked by the first sweep, the limits most often met were missing builtins, partial application, recursion over more than one name, undefined, and other forms of term. The first three are on the hazel-jit branch, undefined passes the fast checks on its own branch, and probes are not begun. (Ticket 761.)

  • Builtins: 17 the runtime lacked, now as the interpreter has them: string_match, string_replace, string_search, string_join, string_escaped, string_capitalize, string_uncapitalize, omit_all_labels, the six compare builtins (int, sint, nat, float, bool and string), and invert_ord. string_sub is the one the sweep still finds.
  • Partial application, f(a, _): the function and the given arguments are evaluated first, in order, then a function of the missing ones.
  • Recursion over more than one name, let (even, odd) = (fun ..., fun ...): each name assigned once, then the tuple of them. This gives the interpreter's answer whenever every part is a function, since a name is only read when a function runs. Any other part stays with the interpreter.
  • undefined, on its own branch (trial/761-undefined, e62f0a855a): seven sweep programs, and more than that. The List builtins written in Hazel (List.head, List.tail and three others) use undefined for an empty list, so every program calling them was not compiled at all. A compiled run that reaches undefined now stops, as for an invalid operation; one that does not reach it costs nothing. With it the fast checks pass, and all seven programs compile and agree: 250 of the 313 compiled, 223 agreed, none differ (CI run 43899240156). One worry did not come true. Hazel gives undefined the hole type, the same as a written ?, so the type-hole rule above might have caught it, but in none of these programs does an ascription around it carry the hole. The full tests are running.
  • Next: "this kind of term" (the forms with no case of their own in the compiler), a fixpoint over a pattern like _, labels that are not names, string_sub, reverse application.
  • Probes are the largest: a probe shows the values that passed through it, and compiled code records none. Today a probe always shows the interpreter's run, which is correct, and never faster. Recording samples from compiled code would mean deciding what a sample is when the code that made it has no steps.

A step budget

Every compiled function now counts its calls and every 16,384 calls reads the clock. A run past its budget (50 ms or 50 million calls) stops, and the interpreter's run answers. (Ticket 763.) Cyrus's concern is that compiled code runs on the page's own thread, so a Hazel function that never ends would freeze the page. The interpreter has a 20-second timer and a limit of 100 million transitions.

Endless recursion turned out to be the smaller risk: it overflows JavaScript's stack in about a millisecond, and that error is caught like any other. The real risk is a run that ends, but late (fib(45)), and the clock catches that. In Node the counter costs 11 to 26%, and 20 to 33% with the clock (not a build of the app). On the Witch it costs nothing measurable in one run (below), well inside a frame. A cheaper counter, at only the calls that can recur, is the next step.

What it all costs

On the Witch slide, the six changes together are not measurably slower than build 45: over a 3 s drag the page's view took 5.4 ms a frame (about 185 fps), against 5.8 (about 172 fps), with hazel-jit's own run 1.1 ms of it. One run each. The spread between single runs (5.4 to 7.3 ms) is as large as any difference, so the numbers show no cost, not a gain. Every build stays far inside the 16.7 ms of a 60 fps frame. The fps assumes that updating the state is free: it is what the view alone allows.

Found along the way

Modulo by zero crashed Hazel's interpreter, on dev too; the fix is a PR to dev, hazelgrove/hazel#2825, waiting for review. (Ticket 764.) int_mod, sint_mod, nat_mod and float_mod answered a zero divisor with an error naming a builtin mod that does not exist, so evaluating it raised an exception instead of showing "Error: Divide by Zero". This dates from at least 2025-07-02. Renaming was not enough: the error's inside was then stepped again, and the error was lost. So the fix also makes a builtin's error final, as an operator's already is. CI passes with it.

A Hazel function that declares what it takes but not what it returns costs 5 to 7 times as much a step at run time, in the interpreter. (Ticket 762.) It was measured in a Tarot deck written in Hazel: a step of take cost 0.36 ms with only its argument types, and 0.07 ms with its whole type. Declaring every type made a deal 3.7 times faster. The cause is not unknown types, but where the ascriptions (the run-time type checks) land: on each case arm's result, in each copy of the body, rather than once around it. This is the interpreter's cost, not hazel-jit's, and it is the kind of check Matthew Keenan asked about in report 053. The next step is to count the checks per call.
