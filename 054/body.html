What hazel-jit is

hazel-jit translates an elaborated Hazel program to the text of a JavaScript function, and the page runs that function on its own thread at a livelit's event, to draw the livelits before the interpreter's answer comes back. Hazel's interpreter, in a web worker, still runs every program, and its answer is still the program's result: the probes, the tests and the result panel come from it. So far hazel-jit has been a measurement of how fast compiled Hazel could be (a step of the Witch's slider in 2 to 3 ms, report 050). The meeting's point is that it must also be correct, because whatever it draws, a user reads as what Hazel computed.

A form the compiler does not handle raises an error with its reason, and the page then waits for the interpreter's run, as it did before hazel-jit. So a limit costs speed, never correctness. A compiled run that stops part way (an invalid operation, undefined, or the step budget) is handled the same way. These fallbacks are what keep hazel-jit's answers the same as the interpreter's: where the two would differ, hazel-jit gives no answer and the interpreter's is shown.

Exact integers

Int and Nat are now exact in compiled code, as the interpreter's are: an integer is a JavaScript number while it is a safe integer (up to 253 − 1), and a BigInt past that. (Ticket 757.) The interpreter's Int and Nat are arbitrary-precision integers (Jane Street's Bigint), and hazel-jit had made them JavaScript numbers, which round past 253: 253 + 1 came out as 253.

Every integer operation normalizes its result back to a number when it fits, so two equal integers are always the same value, and === still compares them. Division rounds toward zero, as the interpreter's does, and stays exact where Math.trunc(a / b) would round. Where plain BigInt everywhere cost a 4.1 times slower fib(25), a 1.5 times slower list walk, and 9.6 times slower model updates, this mix costs 1.6 times, nothing measurable, and 3.7 times (Node, against plain numbers; not a build of the app). On the Witch slide it costs nothing measurable (below). SInt, Hazel's fixed-width integer, stays a JavaScript number: its width is the overflow question.

Divide by zero and other invalid operations

Where the interpreter stops at an error (dividing by zero, a negative power, int_of_string of something not a number), the compiled run now stops too, and the page shows the interpreter's run, which holds the stuck term with its error. (Ticket 759.) Before, 7 / 0 compiled to Infinity.

The stuck term is the same as the interpreter's by construction, since it is the interpreter's. The alternative, making the stuck term in JavaScript and evaluating around it as the interpreter does, would be a much larger piece of work and is not needed for the answers to agree. Writing the tests for this found a crash in the interpreter itself, on modulo by zero (below).

Overflow

Decided on 2026-11-16, Matthew Hammer: a result past an SInt’s bits is an error, a stuck term, as a divide by zero is; and on 2026-11-19, after Cyrus confirmed SInt is a fixed-precision 64-bit integer, its width (Matthew: “Yes, 64 bits”): an SInt has 64 bits everywhere. Done in the interpreter, on a PR to dev (hazelgrove/hazel#2828), and in hazel-jit on the prototype (#2817, since 569d0f186c), all of CI passing. hazel-jit’s own PR (#2859) and the package’s (#2857) start from dev, where an SInt is still OCaml’s int, and still check 32 bits; they move to 64 with #2828. (Tickets 758 and 781; from 11-16 to 11-19, and on the hazel-jit branch from build 48, the width was 32 bits, checked the same way.) Until now SInt overflowed three different ways, depending on how Hazel ran. In the browser, Hazel runs under js_of_ocaml, where an OCaml int has 32 bits, and SInt wrapped silently. A native build of Hazel has OCaml's 63-bit int. hazel-jit had a JavaScript number (checked through hazeljs 0.0.6, which runs Hazel as the browser does):

{{tab_sint}}

Now each of these stops, in all three, at a new error, IntegerOverflow (“Error: Integer overflow (an SInt has 64 bits)”). In the interpreter (#2828, 8b1a1b5543), an SInt holds a Bigint, as an Int does, and every operation is computed exactly and then checked against [−263, 263 − 1] (Atom.sint_fits): sum, difference, product, power (a power of 64 or more is not computed: −1, 0 and 1 repeat, anything else overflows), negation, and the one quotient too big (the least SInt divided by −1). An OCaml int cannot hold 64 bits (it has 32 under js_of_ocaml and 63 natively), and OCaml’s Int64 is emulated under js_of_ocaml, allocating, and wraps silently, so a Bigint it is; the answer no longer depends on the width of the int the interpreter runs on. A value made into an SInt from an Int, a Nat or a Float that does not fit stops at the existing IntegerTooBig. In compiled code (the prototype, #2817), an SInt is held as an Int is: a JavaScript number while it is a safe integer, a BigInt past that; only the BigInt path checks the 64-bit bound (s64), since a sum or product of two safe numbers that stays safe is surely inside it. Timed in Node (one core, 2 million additions and multiplications, seven runs, both orders): the old 32-bit check 6.6 to 6.8 ns an operation; the 64-bit SInt 6.8 to 7.0 below 253, about 43 past it; a plain BigInt every time 17 to 24. Tests check both agree at the 64-bit edges and across 253 (CI: 4,969 tests on #2828, 6,996 on the prototype). Changing the interpreter changes the language, so the interpreter’s half is its own PR to dev, #2828, with tests of its own. Its CI is green; it waits on a review.

Int and Nat cannot overflow (above), and Float follows IEEE 754 in all three.

What stays with the interpreter

By rule, not as a limit, hazel-jit leaves to the interpreter: any program with a hole (now including a type hole, ? in a type), any program with type errors, and anything the stepper shows. (Ticket 760.) Each is written down at the head of the compiler's source, HazelJit.re.

Holes. Empty holes, multiholes, dynamic error holes and invalid text were already not compiled: the interpreter evaluates around a hole, and its indeterminate result is the point of a hole. Type holes are new, from the merge's sweep. A value passed through ? to a function taking [Int] fails a run-time check when it is a list of floats, and the interpreter shows the failed check. Compiled code has no types to check, and a float and an int are both a JavaScript number, so it cannot tell. No slide writes a type hole. Type errors. The first sweep's 30 ill-typed tests (4 : String, 1 + (4 : String), ...) are programs where the interpreter stops at a failed run-time check. Now the page compiles no program with static errors. Checked on the six slides of the Firefox check, neither rule stopped any slide from compiling. The four slides with compiled runs kept them (a count of 28 against 30 reflects when a run was timed, not a program that stopped compiling):

The stepper's functions, which Matthew asked to have explained. Hazel's stepper shows a program's evaluation one step at a time. Four forms of expression tell it which steps to show: hide P in e (skip the steps matching pattern P), eval P in e (take them without stopping), pause P in e (stop at them), and debug P in e. These are "stepper functions" in the sense Cyrus meant. They only mean something to a run that takes steps, so hazel-jit does not compile them (the reason is "a stepper filter"). Beyond the filters, nothing the stepper shows is drawn from compiled code. The stepper evaluates by the interpreter's own steps, and a livelit inside a probe drawer's stepper, drawn over one of its samples, is now drawn by the interpreter, never from a compiled run's answer (in the code and its tests; not yet checked in a browser).

A step budget

Every compiled function now counts its calls and every 16,384 calls reads the clock. A run past its budget (50 ms or 50 million calls) stops, and the interpreter's run answers. (Ticket 763.) Cyrus's concern is that compiled code runs on the page's own thread, so a Hazel function that never ends would freeze the page. The interpreter has a 20-second timer and a limit of 100 million transitions.

Endless recursion turned out to be the smaller risk: it overflows JavaScript's stack in about a millisecond, and that error is caught like any other. The real risk is a run that ends, but late (fib(45)), and the clock catches that. In Node the counter costs 11 to 26%, and 20 to 33% with the clock (not a build of the app). On the Witch it costs nothing measurable in one run (below), well inside a frame. A cheaper counter, at only the calls that can recur, is the next step.

Beyond livelits

Most of hazel-jit's limits come from one assumption: it compiles a whole program that is closed, finished and well typed, and its answer is only a preview, with the interpreter's run as the real answer. Running any piece of a program in JavaScript breaks each part of that. The direction chosen is a mixed mode: the interpreter keeps running the program and calls compiled functions as it calls a builtin. Matthew Hammer asked on 2026-11-16 what it would take to apply hazel-jit to any fragment of elaborated Hazel, and which of its assumptions stand in the way. Of three ways to go, he chose the third: "I like the mixed mode idea a lot."

{{fig_mixed}}

What today's design assumes

  1. The program is closed. Its only free variables are builtins, and a closure carrying its own environment is not compiled. A slide's run starts from nothing, so this has not mattered. A piece from inside a program has free variables bound to the interpreter's values, closures among them: those must be converted on the way in, and an interpreter closure must either be compiled too or be called back from JavaScript.
  2. The compiled answer is a preview. The page draws from it, and the interpreter's answer, arriving later, is the program's result. If compiled code gives the result itself, every remaining difference is a wrong answer, and the consistency check becomes a gate.
  3. Falling back is all or nothing, and costs nothing extra, since the interpreter runs anyway. For a piece of a program, falling back means running it twice, partly in JavaScript and then in the interpreter. That is safe only because evaluation has no side effects.
  4. The answer's type is known. Converting an answer back needs its type: a Float 1.0 and an Int 1 are the same JavaScript number, and without a type a tuple's labels are guessed from its properties. A view's answer is always Html.
  5. The inputs are small. Views draw small models, so recursion stays shallow. JavaScript has no tail calls and a stack of thousands to tens of thousands of calls, depending on the browser, where the interpreter keeps its stack on the heap. A List.map over 100,000 elements works in the interpreter and overflows compiled; today that falls back, correct but slow.
  6. Three shortcuts are for livelits only: a livelit's model is a parameter, so a slider step does not recompile; each view's answer is collected by its projector; and Html goes straight to the page's DOM without becoming Hazel terms. In general, every edit changes the code, so it is compiled again, and new code starts cold in the JavaScript engine. Compiling is quick (the Witch's largest livelit definition, 62,000 nodes: 6 ms to translate, 9 ms for the browser to parse), but what to cache by, and what to make a parameter, come back as questions.
  7. The program is finished. Holes, type holes and type errors go to the interpreter by rule (above). A program being edited usually has holes, so compiled code helps only its complete parts. That argues for compiling pieces rather than whole programs.

What is new in the general case

  1. Divergence and long runs. The step budget bounds a freeze. But its units are calls and time, not the interpreter's steps, so compiled code may finish where the interpreter would time out, or the reverse. If the same answers include the same timeouts, the limit needs a definition in the language that both count the same way. A piece of a program that draws nothing belongs in the worker, where a long run freezes nothing.
  2. The boundary costs. Converting values in and out builds Hazel terms and makes new ids. Report 045 found a livelit's render about 40 times slower with that trip in and out than compiled alone. Small pieces that cross often lose most of the gain, so pieces must be large, or values must stay in JavaScript between calls.
  3. What the interpreter records: probes, the stepper's steps, traces, test results, and the ids that tie a value to the code that made it. Compiled code records none of them. A piece holding a probe or a test, or shown in the stepper, stays with the interpreter.
  4. Evaluating around holes, Hazel's central feature: a program with holes still runs, and its result holds the holes. Compiled code cannot; it stops.
  5. Run-time type checks. Where a value passes through the unknown type ?, the interpreter checks it as the program runs; compiled code has no types to check with. Values entering a compiled piece typed ? would need checking on the way in.
  6. Every builtin twice. Each of Hazel's builtins written in OCaml has a twin written by hand in JavaScript, and a general compiler meets them all. Looking for this report found one that differed: string_length (above, now fixed).
  7. Security. Compiled code runs through new Function with the page's full access. For livelits, that is slides we wrote; for any piece of any program, including one opened from a shared link, a bug in how the compiler escapes text would let a program run its own script in the page. A page whose security policy forbids eval cannot run it at all.
  8. Two implementations to maintain. Every new language feature must either compile or fall back, and the consistency check must cover it.

Three ways to go

  1. Whole closed programs, in the worker, with the interpreter as the fallback: close to what we have, without the livelit shortcuts, and unable to freeze the page.
  2. A fragment interface: compile a closed function whose free variables are typed parameters, convert its inputs once, and keep its values in JavaScript.
  3. Mixed mode, the one chosen: the interpreter calls compiled functions as it calls builtins, for functions that are complete, free of probes and worth compiling. The first two are steps toward it.

Mixed mode

Mixed mode keeps the interpreter in charge of the program, so holes, probes and the stepper work as they do now, and gives its complete functions compiled speed. A first step is built (ticket 766, below). The sketch it follows:

  • What is compiled: a function whose body is complete (no hole, type hole or type error), holds no probe, test or stepper filter, and whose free variables are builtins or other compiled functions, with its whole type declared. The declared type converts the answer back. Ticket 762 found that declaring it also makes the interpreter's own steps 5 to 7 times cheaper.
  • How it is called: a new kind of value beside a builtin. Applying it converts the argument to JavaScript once, runs the compiled function under the step budget, and converts the answer back by the declared type. It runs in the worker, where the interpreter runs, so a long call freezes no page.
  • Falling back, one call at a time: on any stop (the budget, an invalid operation, undefined, an argument that will not convert because it holds a hole), the interpreter applies the original Hazel function to the same argument. Evaluation has no side effects, so running a call twice is safe. A program with holes elsewhere still runs its complete functions compiled, and the interpreter evaluates around the holes.
  • Probes and the stepper: putting a probe in a function takes that function out of the compiled set at the next compile, and the rest stay compiled. The stepper either runs on the interpreter alone or shows a compiled call as one step, as it shows a builtin's.
  • The boundary: compiled functions call one another directly in JavaScript, without crossing. A large value passed again and again (a list) can be converted once and remembered by the identity of the interpreter's value.
  • Checking it: the consistency sweep runs each evaluator test a third way, mixed, and compares with the interpreter alone.
  • Where it hooks in: the interpreter applies a builtin through one lookup by name (Transition.re, in Builtins.forms_init), and a builtin's answer is a term the interpreter goes on evaluating. So a compiled function can be a builtin made at run time, with no new kind of value. A compiled function bound by a let becomes such a builtin. When the call finishes, the builtin returns the answer. When it stops, it returns the application of the original Hazel function to the same argument, and the interpreter evaluates that as it would have anyway. The call already shows in a probe's call stack and in the stepper as a builtin's does.

  • Which functions: a let at the top of the program, or a member of a module there, that binds a function whose whole type is declared (let f : A -> B = fun ...), with no unknown in it. Step counts and probes, as the interpreter's

Compiled code can count exactly the steps the interpreter takes, in every program it compiles, with care in three places. With those counts it can make the interpreter's own probe samples, with two limits. Nothing found so far makes either impossible: the costs are a little run time, a tie to the interpreter's internals, and the work. This answers Matthew and Cyrus's two questions of 2026-11-13 (ticket 767). Not built yet.

What the interpreter counts. Its count goes up by one at every transition, whichever of its 36 kinds: those that interpret the program (a variable looked up, a let bound, a function applied, an operator, a case, a projection) and those that are bookkeeping (a closure wrapped, parentheses removed, a cast). It goes up one more after each pattern match. The count is the same with or without incremental reuse: a reused result adds the steps it took when it was first computed, so that probe samples stay where they were. Each probe sample is stamped with it: the span of steps from its start to its end.

The counts, measured. For 57 small programs, each a construct apart from the last, the interpreter's count is regular enough to read off (ticket 767's calibration, CI run 44131334098). A literal is a step. An operator or a pair of parentheses adds one. A let adds three of its own: binding, its pattern, and completing the closure around its body. Each level of a simple recursion, if n == 0 then 0 else f(n - 1), adds exactly 16 (18, 34, 50, 66 for f(0) to f(3)). A declared Int -> Int adds one cast step to each call. Some counts need the interpreter's bookkeeping to explain: true && false takes 4 and false && true 3. The whole table:

The 57 programs and their counts {{tab_calib}}

Why compiled code can match it. hazel-jit translates the program construct by construct and runs it in the same order as the interpreter: arguments first, left to right. Most constructs take a fixed number of steps of their own, apart from their parts: an operator one; a let one, and one for its pattern; an application one, one for its pattern, and the closure's bookkeeping. So the compiler can add, wherever code runs straight through, the steps the interpreter takes there. That is one addition for each straight run of code, about what today's budget counter costs (ticket 763). Then the budget and the interpreter's step limit are one number, in one unit.

Where it needs care: the "if not, why not".

  1. Casts carried by functions. A function that has passed through a typed boundary carries the cast with it, and each call through it takes the cast's steps too. How many depends on where the function value has been, not on the code that calls it. Compiled code erases types, so its functions would carry the steps their casts cost, as a number on the JavaScript function.
  2. Casts pushed into code not yet run. A cast around a list or tuple literal is pushed into its parts, and each part then takes steps of its own. This is fixed by the code, so the compiler can follow it, but only by following the interpreter's cast rules exactly.
  3. The rules live in the interpreter's code, not in a specification. There are 36 kinds of step, the extra step after a pattern match, and steps that rebuild a term and evaluate it again under the same id. Some of this is bookkeeping that changes when the interpreter does: a cast through a whole value became one step, for speed, this autumn. So the counts can be held equal only by checking, as values are. The consistency sweep would compare each evaluator test's count with the interpreter's, and a difference would fail CI.

The programs hazel-jit does not compile at all (holes, stepper filters, tests) stay with the interpreter, counts and all. A question for the team: count every step, or only those that interpret the program? Probe samples' spans are in every step today, so to make the same samples compiled code would count them all.

Probes, given the counts. A sample records where (the expression), when (its span of steps), the value, the variables the probe refers to, and the call stack: for each call, the application, the function's name and where it was defined. Compiled code knows the expression at compile time, the steps with the counts above, and the value and variables as JavaScript values. For the call stack it would keep a stack of its own, a frame pushed and popped at each call, paid for only in a program with probes. The way to share the probe machinery rather than write it twice: compiled code emits the same events the interpreter emits as it runs (a span opened, a call entered, a span closed), at the same steps, and the interpreter's own code turns them into samples.

The two limits. First, a sample's value has to come back as a Hazel value, which needs its type at the probe: elaboration has it. A function value comes back only if hazel-jit made it, and not a recursive one. Second, converting each sample's value and variables is the costly part, so it should happen when the page shows a sample, not at every step. The stepper is another matter: counts say how many steps a compiled call took, but the stepper shows the terms in between, and compiled code has none, so it stays the interpreter's.

The way there. (1) The sweep prints each evaluator test's count from the interpreter beside one from compiled code under these rules: how many match exactly, and where they differ. (2) Casts carried by functions. (3) The budget in steps, as one with the interpreter's limit (ticket 763). (4) In mixed mode, a compiled call adds its steps to the interpreter's count, so a program's count is the same mixed or not. (5) Probes: the events from compiled code, checked against the probe tests' samples.

Every size and way {{tab_crossing}}

Three ways to hold a list

  1. Cells, today. null for the empty list, {h, t} for x :: xs. A pattern reads .h and .t, and :: makes one cell. Length and nth walk the list, and a page’s array is converted cell by cell on the way in and out.
  2. Arrays. A list is an immutable JavaScript array. Length and nth take constant time and a page’s array crosses as it is, but x :: xs copies xs, and so does a pattern’s tail. Hazel code mostly walks and builds lists a cell at a time, so the time grows with the square of the length.
  3. Hybrid. A list is null, a cell {h, t}, or a segment {a, i}: the elements of the array a from index i on, shared and never changed. A list literal and a page’s array are segments, made with no copy; :: makes a cell as today; a pattern on a segment reads a[i], and its tail is the segment from i + 1. Every operation has one more test than with cells.

Holes in lists

The interpreter already allows both kinds of hole in a list, and the hybrid has room for both. An element can be indeterminate, [1, ?, 3], and the list is still a list literal. A tail can be indeterminate too, 1 :: ?: an indeterminate cons, which the interpreter’s unboxing keeps apart from literals, since a pattern [a, b] might or might not match it. Plain arrays can hold the first kind and not the second. In the hybrid, an element is any value and a cell’s tail is any value, an indeterminate one included; a pattern that meets one is an indeterminate match. That needs compiled code to carry indeterminate values at all (below).

The interpreter’s evaluated lists

In the interpreter, arrays would change a lot for little, as far as we can see now. An evaluated list is a list literal holding an OCaml list, which js_of_ocaml makes a chain of cells, the same shape as hazel-jit’s today. Arrays there would make :: and a pattern’s tail cost a copy, unless the interpreter had a hybrid of its own, and about ninety places in the evaluator alone match on list literals and conses (transitions, unboxing, the stepper’s contexts, substitution). The interpreter’s time goes to its rewriting steps more than to its lists’ shape. Where the shape matters is the crossing between the interpreter and compiled code (mixed mode, and the library), and there every element is converted anyway. So: measure that crossing once the compiled side has its hybrid, before changing the interpreter’s lists.

Terms with holes

Two designs, the second built on the first: fall back to the interpreter for any call that meets a hole, as mixed mode does now; then carry holes through compiled code as indeterminate values that build the interpreter’s residual terms.

  1. Fall back for the call. Mixed mode, on the hazel-jit branch now: the interpreter runs the program around its holes and calls the complete functions compiled, and a call whose argument holds a hole, or that reaches an indeterminate value, is run again by the interpreter, for that call alone. It is correct and built, but a function with a hole in it is never compiled, and a call that meets a hole pays for a compiled try and an interpreted run. Since 2026-11-25, a step between the two, merged into hazel-jit on Matthew’s word (2026-11-26, “Yes, merge”): an argument’s hole crosses into compiled code unopened, a function with a hole in it compiles, and only a call that looks inside a hole falls back; a list of 2,000 built with a hole now runs about 17 times as fast as the interpreter (report 055). Residual terms built in compiled code, the second design, remain.
  2. Indeterminate values in compiled code. A hole compiles to a value, $R.hole(id), that carries what is needed to rebuild its term. Each elimination form checks for one: a + ? gives an indeterminate sum; a case whose scrutinee is indeterminate, where some pattern might match, gives an indeterminate match holding its rules and the values its variables are bound to; applying an indeterminate function gives an indeterminate application. When the answer comes back to the interpreter, these become its residual terms, so the result is the one the interpreter would give. The cost is a check at every elimination form, as the step budget checks at every call, and code to build each residual form. This is what running terms with holes means in full.

Together or apart? Design them together and build them apart. The list’s shape decides where an indeterminate value can sit (an element, a tail), and a cell’s tail is already free to be any value, so holes do not need arrays. Arrays (as the hybrid’s segments) pay at the edges, where a page’s list crosses with no conversion at any size, and cost a little inside, about {{lg_aot}} on these games; how much a program gains is how much of its time is crossing, and for a page that hands Hazel large lists that is most of it. Records must cross for nothing too, or a list of them still costs its length. So the next steps: converters by declared type (the jit’s crossing down to the cells’ line, or to nothing for arrays), records held the page’s way, then indeterminate values; and a sequence type built for splicing, ticket 846, beside them.

A sequence beside List

A sequence held as a treap over views of JavaScript arrays inserts one element anywhere in {{sq_ins_lo}} to {{sq_ins_hi}}, from 1,000 elements to 1,000,000, appends one in at most {{sq_app}}, and takes a page’s array in and out for nothing; an array copied on every edit takes {{sq_arr_ins}} to insert one at a million, and cells {{sq_cell_ins}}. Its costs: reading one element by position takes up to {{sq_get_hi}}, where an array takes tens of nanoseconds, and walking a million after twenty thousand edits takes {{sq_walk}}, about as long as cells ({{sq_walk_cells}}) and five times an array ({{sq_walk_arr}}). This is ticket 846, which Matthew asked for on 2026-11-23: “explore a new builtin sequence type, as complement to List --- Sequence or Seq, for short maybe?”, held as a balanced tree with arrays at its leaves. What matters most to him is a balance that needs no rebalancing, the levels fixing the shape so that an edit never rotates; the caching a content-determined shape allows matters less, so a level may come from any well-spread source.

How it is held. A leaf is a view of an array that is never changed: the array and a start and an end, so that splitting a leaf is two views of the same array and copies nothing. A page’s array is one leaf over it. Between two leaves is a gap with a priority, drawn here from a counter’s hash, and the tree is the one the priorities determine, the highest at the root, as in fumola’s level tree (Pugh and Teitelbaum’s), where a gap’s level comes from its symbol. An insert splits the tree at the position and joins the three parts; a join puts the higher priority on top and never rotates. A leaf of fewer than {{sq_b}} elements that meets another sequence goes into the leaf at its edge when the two fit in {{sq_b}}: a copy of at most {{sq_b}} elements, and no new gap, so the shape stays the priorities’. Every edit gives a new sequence and leaves the old one whole, as a Hazel value must, and so do the other three ways here.

What a closure keeps

Nothing on dev trims an environment. A function value keeps the whole environment it was made in, used or not. A function needs only its free variables, and the statics already know them for every expression, so trimming is possible. dev’s empty holes keep no environment at all, so today they are no exception to it. Compiled code already trims: a compiled function holds only what it captures, and crosses back to the interpreter holding only that.

Matthew asked, 2026-11-23: "is there any aspect of dev that trims Hazel values' environments to only contain relevant values? For empty holes, the whole env is required, perhaps -- but for other terms, esp closed terms, the env can be dropped. We experimented with this as a performance PR, IIRC, but I don't recall the exact context of that work."

An example

Take let big = [1, 2, …, 10000] in let inc = fun x -> x + 1 in inc. The value of inc is a closure: the function, with the environment it was made in, and that environment binds big. inc never reads big, but its value holds it. Holding it costs nothing when the closure is made. An environment is a chain of bindings, shared, so a closure points at the chain and copies nothing. The cost comes later, from whatever walks a value: finishing a result, sending it from the worker to the page, or converting it for a page.

What dev does

  1. A function keeps the whole environment. The interpreter’s rule for a function (Transition.re) wraps it as Closure(env, fun …) with the current environment, whole. A recursive function’s fixpoint keeps it whole too (FixF(p, body, Some(env))). So do the indeterminate forms that need their environment later, such as an if whose condition is a hole, or a free variable.
  2. An empty hole keeps none. The rule for an empty hole leaves its closure out; the line that would add it is commented out, marked “uncomment for hole closures”. So on dev a hole is not shown with its environment, and nothing fills a hole and resumes from it.
  3. Incremental evaluation reads only the free variables. hazelgrove/hazel#2222, “Incremental evaluation”, reuses a term’s last value when its free variables’ values have not changed, and it looks up only those: the term’s co-context, from the statics (IncrEval.restrict_to_co_ctx). That is the trimmed environment, used to decide a reuse. Values do not keep it.
  4. Finishing a result writes the environment into the body. Substitution.in_exp replaces each variable with its value, so a finished value mentions only what it uses. It gets there by copying, though: each function a function calls is copied in, at every level.

The result display never shows an environment, and the stepper evaluates again from the elaborated term, so nothing shown changes.

Kept as a closure, a call takes 0.025 ms instead of 5.31 ms. It keeps the environment whole and unwalked; it does not trim it.

Trimming, as Matthew describes it

  1. A function keeps its free variables, and a closed function keeps nothing. The statics already compute every expression’s free variables (its co-context, Info.co_ctx). The elaborator could record them on each function, and the rule for a function would keep just those bindings. A recursive function also keeps its own name, which its fixpoint binds.
  2. An indeterminate form keeps the free variables of what it has not yet evaluated. An if on a hole needs only its two branches’ free variables.
  3. A hole needs everything in scope, if hole closures come back. A filling may use any variable in scope at the hole, so a hole closure needs the hole’s whole typing context, which is the whole lexical scope. A function whose body holds a hole would then keep its whole environment. On dev today this does not arise, since holes keep no environment.
  4. What it costs, and where it pays. Each closure made gets a small environment of its own instead of a pointer to the shared one. That is a cost at every call of a function that returns a function, a curried function among them. Environments would also stop being shared, so two closures could no longer be seen to have the same environment by its identity. It pays wherever a value is walked: finishing a result, the worker’s message, the library’s crossing to a page, and a Hazel-only value the package holds whole (below).

What the jit does already

Compiled code keeps only captures, and the crossing keeps it that way. A compiled Hazel function is a JavaScript function tagged with the Hazel names it captures and their values, in order ($R.fn(f, k, [values])). Back in the interpreter it becomes a closure whose environment holds those captures alone (HazelJitValue.of_js), with a recursive function’s own name bound again by a fixpoint. Going in, the compiler refuses a closure that carries an environment of its own (“a closure with its own environment”), so mixed mode never converts one. For the npm package, this matters to the next change on #2857: a value with no JavaScript form, such as a hole, a mark or an interpreter’s closure, crosses to a page held whole. Held, it is never walked, so a whole environment inside it costs memory, not time. Trimmed environments would make those held values small too.

Mixed mode

  1. Which functions get compiled? Our lean: Let-bound functions with their whole type declared (let f : A -> B = fun ...), complete, with no probe. The elaborated type of any function would reach more, but it can hold unknowns, and the answer is converted back by that type. It decides: How much of a program runs compiled, and whether Hazel should nudge people to declare types; ticket 762 says that pays in the interpreter too.
  2. What does the stepper show for a compiled call? Partly answered 11-13: a compiled call counts the steps it would have taken. Our lean, still: mixed mode off while the stepper is open, since the stepper shows terms and compiled code has none. It decides: Whether stepping a program ever skips steps.
  3. Probes in compiled code: what is a probe's sample when the code that made it has no steps? Answered 11-13: compiled code counts the interpreter's steps, and with them makes the interpreter's samples (below). Until then, the plan is that a probe takes its function out of the compiled set; today mixed mode, which runs only in the tests, compiles such a function anyway, and its probes record nothing. It decides: The design of probes, the last of ticket 761's limits.
  4. Main thread or worker? Our lean: Mixed mode in the worker only, where the interpreter runs; the main thread keeps only livelit views, as now, under the step budget, which answers Cyrus's concern. It decides: Whether a long compiled call can ever freeze the page.
  5. Falling back runs a call again from the start. Is that safe for good? Our lean: Yes while evaluation has no effects. Is any effect planned (a livelit updating its model, randomness, input and output)? It decides: Whether one-call-at-a-time fallback stays correct.
  6. A program with a type error elsewhere: compile its sound functions? Our lean: Yes, per function: a value that does not fit the declared type is caught where it crosses, and that call falls back. Today a single error anywhere keeps the whole program interpreted. It decides: How often a program being edited, so often with an error somewhere, runs compiled.
  7. One step budget or two? Answered 11-13: one, in the interpreter's steps, which compiled code will count exactly. Compiled code today has its own, 50 ms or 50 million calls a run. It decides: What a budget means to a user, and what the stepper and probes count.

  1. String length in graphemes: intended? Our lean: Keep it. Compiled code now counts as the interpreter does, with a fast path for ASCII. It decides: The meaning of string_length and string_sub for text beyond ASCII.
  2. Labeled tuples as JavaScript arrays carrying their labels: fine? Our lean: Fine inside compiled code. Labels named length, __proto__ or starting with $ are stored under $ + label. hazeljs gives a labeled tuple to JavaScript as an object, so the boundary converts. It decides: The shape of values between Hazel and JavaScript, in hazeljs and in mixed mode.

Our lean: Keep them: they test the interpreter's casts, which compiled code never needs, since it compiles no program with type errors. Met by an app

The astrology oracle (hazeljs-oracles 0.0.15, ticket 768) is eleven modules of numeric code, the Sun, Moon and planets from Meeus's and Schlyter's series, run by hazeljs. Writing it met two problems in the interpreter's side of Hazel, filed this morning.

  1. An answer that is a function grows past gigabytes (hazelgrove/hazel#2832): fix Evaluator.finish? Our lean: Yes. finish substitutes the environment into the answer, so a function that reaches earlier modules copies their closures into it, nested; leave a closure in the answer as a closure, and substitute only for display. Compiled code never meets it: a compiled function is a JavaScript function. It decides: Whether a hazeljs page can take functions from a program of many modules. The astrology page cannot today, so it builds the whole program again for each chart, about 1.3 s.
  2. Float literals print with six decimals (hazelgrove/hazel#2831): print them so they read back? Our lean: Yes, the shortest form that reads back as the same number. Today a literal with more decimals sends its module to the recovering parser, whose cost grows much faster than the module. Compiled code already prints floats exactly, and evaluation compares them by value, so the interpreter and compiled code agree on them; only parsing and the terms' own equality (six decimals) are affected. It decides: Whether numeric programs can write constants as they are; the astrology rules write long ones as ratios.
