Representations, then and now

This report’s

Since report 046 (2026-11-07), hazel-jit lays out records as ReScript and Melange do, as plain objects read by their labels, and does as they do with a named function’s arguments and a function’s calls of itself in tail position; its lists, constructors and options are still its own. Report 046 compiled one small rule (a Petri net’s step, report 043’s) with ReScript, Melange, js_of_ocaml and hazel-jit, and put the four layouts side by side. The table below is that table with hazel-jit as it is on #2859 now (be44756900, with all of today’s changes merged); the cells that changed since 2026-11-07 are shaded.

{{rep_table}}

The names in hazel-jit’s columns: $h and $t are a list cell’s head and tail, $c and $v a constructor’s name and value, $d a named function’s direct form (its tuple’s parts as JS arguments), and $R the runtime compiled code is given ($R.eq, $R.dot). They begin with $ because a record’s label that does is kept under $ and the label ($c as $$c), so no record has these keys, and one key tells a cell or a constructor from a record (decision 2 of ^ticket(847)). ReScript and Melange name a cell’s parts hd and tl and a constructor’s TAG, _0, _1; js_of_ocaml uses arrays, the tag first.

ReScript and Melange come from one family, BuckleScript’s: OCaml’s (or ReScript’s) front end and type checker, then a back end that writes the JavaScript a careful person would write, module by module. js_of_ocaml, which builds Hazel itself, compiles OCaml’s bytecode, a whole program at once, and keeps OCaml’s memory layout: every block an array with its tag first. hazel-jit is a third kind: it compiles Hazel’s elaborated terms in the page, while the program runs, with a runtime of its own.

  • Loops. A recursive definition (FixF) whose body is a function compiles it knowing its own name, and writes its body as statements: an if’s branches, a let’s and a sequence’s last part and a case’s arms pass the tail position on, and a call of itself there gives the parameters their new values and continues a for (;;) loop. A million-deep count now runs compiled, where a JS call each time would overflow the stack (a new test).
  • Each pass its own variables. The function’s variables are declared inside the loop, so a closure made in one pass keeps that pass’s values, as a call’s would (a new test builds three closures in a loop and calls them). Each pass counts a step for the run’s budget, as each call did.
  • JS arguments, for named functions. A function bound to a name (a let, a module’s member, a recursive definition, a builtin written in Hazel) whose parameter is a tuple pattern of unlabeled parts has a direct form, its parts as JS parameters. A call with the tuple written out goes to it with no array: by name where the function is known (fire_at$81.$d(n$84, i$93)), or through $R.c2 to $R.c6, which use $d when the function has one. A function made where it is passed keeps one form, since a builtin calls it as f(x) and making it then costs one function, not two.
  • Everyone else still passes the tuple. The function’s value is still a function of one argument, for a page, the interpreter, a builtin: it checks what the pattern by position checked (a labeled entry read by position is the interpreter’s, ticket 851) and calls the direct form. So nothing outside the compiled code changes, and the package’s converters and the games’ compiled.js files work as they are.
  • As ReScript and Melange do, and no further. Mutual recursion, and a call of another function in tail position, are still calls.

What a call still converts

What each Petri call converts: the net, whose marking is a new array of five Ints every call (five list cells in), whose transitions are the same object every call (remembered, so nothing), and the event; and the command it answers, a chain such as Say(_, Take(_, _, Put(_, _, Done))), built new each call and so converted node by node, from {$c, $v} to the page’s {tag, value}. Where the rest of the cost lies, in general:

  • A list crosses cell by cell, unless it was handed back unchanged: about 6 µs for 1,000 Ints, 62 ms for a million (report 054, A page’s list in and back out).
  • A constructor crosses node by node, since the page holds {tag, value} and compiled code {$c, $v}; a record now crosses as it is.
  • Whatever is new each call misses the converters’ memory: given a fresh copy of every state, the jit took 2.2 times its own time (report 063, A game’s own run of states).
  • Mixed mode, where the interpreter calls compiled functions, converts every call’s argument from the interpreter’s terms into JavaScript and its answer back by the declared type, with no memory between calls. In mixed mode’s first measurements, a one-line function called 500 times from interpreted code was slower than not compiling it (report 054, Mixed mode).

Ways to bring it down, soon

  1. The interpreter keeps compiled values as they are. In mixed mode, a compiled call’s answer stays the JavaScript value, held by the interpreter as a value of a new kind: the JS value and its type. Passed to another compiled function, it goes as it is. Only when the interpreter looks inside it (a case, a projection, an operator, a probe, the answer shown) is it converted, one layer at a time, each layer’s parts kept as they are until they are looked at. A game’s state handed from step to step through interpreted code would then never be converted. The cost: a new form of value in the interpreter, which its steps, its matching and its printing must know, and the way back for the parts it shows.
  2. Mixed mode remembers what it converted. As the package’s converters do for a page: under js_of_ocaml an OCaml value is a JavaScript object, so a WeakMap can lead from the interpreter’s term to its JavaScript value, and a link on the JavaScript value back to the term. A state the interpreter hands back unchanged then crosses with no walk, and only what changed is converted. Less to build than the first, and it covers the case where the interpreter only passes values along.
  3. Constructors in one shape. If the page and compiled code held a constructor the same way, it would cross for nothing, as a record does now. Either way round, pages that keep compiled code would see the change, as they saw the records’.
  4. Lists as arrays at the edge (^ticket(846), how Seq enters Hazel): a page’s array read where it is, not turned into cells first. Lists as cells plus array segments cost 8% in compiled code (report 054), so a type the program asks for, not every list.
  5. The converters call the direct form. A page’s call with several arguments is gathered into one array, which the function’s one-argument form takes apart again; the converters could call $d with the parts.

The first two would show in mixed mode, which nothing in the app turns on yet; the last three in every page’s call through Hazel.jit.
