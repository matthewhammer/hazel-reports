Representations, then and now

This report’s

Since report 046 (2026-11-07), hazel-jit lays out records as ReScript and Melange do, as plain objects read by their labels; its lists, constructors, options, calls and tail calls are still its own. Report 046 compiled one small rule (a Petri net’s step, report 043’s) with ReScript, Melange, js_of_ocaml and hazel-jit, and put the four layouts side by side. The table below is that table with a column for hazel-jit as it is on #2859 now (9ec865976d); the cells that changed are shaded.

{{rep_table}}

ReScript and Melange come from one family, BuckleScript’s: OCaml’s (or ReScript’s) front end and type checker, then a back end that writes the JavaScript a careful person would write, module by module. js_of_ocaml, which builds Hazel itself, compiles OCaml’s bytecode, a whole program at once, and keeps OCaml’s memory layout: every block an array with its tag first. hazel-jit is a third kind: it compiles Hazel’s elaborated terms in the page, while the program runs, with a runtime of its own.

Report 046 ended with five changes to hazel-jit’s output, each something these compilers already do, in the order they would likely help that rule (its section). Where each stands:

{{sugg_list}}

Two changes came from elsewhere, not from that list: field reads compiled in place (where they had gone through a call that read every label of every program), and the $ on the keys of cells and constructors, so that a record is never taken for either. Each change to the layout is a change on both sides of the boundary too: what HazelJitValue reads and writes, and what the npm package’s converters do (#2857).

  • Loops. A recursive definition (FixF) whose body is a function compiles it knowing its own name, and writes its body as statements: an if’s branches, a let’s and a sequence’s last part and a case’s arms pass the tail position on, and a call of itself there gives the parameters their new values and continues a for (;;) loop. A million-deep count now runs compiled, where a JS call each time would overflow the stack (a new test).
  • Each pass its own variables. The function’s variables are declared inside the loop, so a closure made in one pass keeps that pass’s values, as a call’s would (a new test builds three closures in a loop and calls them). Each pass counts a step for the run’s budget, as each call did.
  • JS arguments, for named functions. A function bound to a name (a let, a module’s member, a recursive definition, a builtin written in Hazel) whose parameter is a tuple pattern of unlabeled parts has a direct form, its parts as JS parameters. A call with the tuple written out goes to it with no array: by name where the function is known (fire_at$81.$d(n$84, i$93)), or through $R.c2 to $R.c6, which use $d when the function has one. A function made where it is passed keeps one form, since a builtin calls it as f(x) and making it then costs one function, not two.
  • Everyone else still passes the tuple. The function’s value is still a function of one argument, for a page, the interpreter, a builtin: it checks what the pattern by position checked (a labeled entry read by position is the interpreter’s, ticket 851) and calls the direct form. So nothing outside the compiled code changes, and the package’s converters and the games’ compiled.js files work as they are.
  • As ReScript and Melange do, and no further. Mutual recursion, and a call of another function in tail position, are still calls.

Which change gives what

Nearly all of it is the JS arguments: loops alone take {{sp_loops}} of the base’s time on the games, within the runner’s noise, and both together {{sp_both}}. A second run on GitHub (bench/853-split, run 45641693384) played each game three ways on one runner: the base, loops alone (trial/853-pkg-loops, db27761a79: hazeljs with only 50b70d5a40 merged), and both; every answer the same. Loops alone went from {{sp_lo}} to {{sp_hi}} by game; the games’ own compiled.js took {{sp_aot}} of the base’s time on those runners. On report 046’s Petri rule, on the laptop, the base takes {{ps_base}} µs a call, loops alone {{ps_loops}}, and both {{ps_both}}. The games’ recursive functions mostly walk short lists, so a call of itself saved is little; what loops buy is that a long list no longer overflows the stack. Every call with its tuple written out, though, made an array, and now does not. A game’s number moves between the two runs (Bricks took 0.55 of the base’s time in the first and 0.93 in this one), while the geometric mean holds ({{g853_gm}} and {{sp_both}}).

Speed beside them

This report’s

Only one small rule has been measured with all of them: measured again today, ReScript’s and Melange’s code runs it about four times as fast as hazel-jit’s with the trial’s changes, and the hand-written JavaScript about 2.4 times (today’s numbers). On 2026-11-07 it was about three times and twice; hazel-jit’s Ints have become exact since, and its functions count steps. Report 046’s numbers, in Node 22 on the same laptop:

{{petri_table}}

That hazel-jit had records as arrays, field reads through a call, and an equality too big to inline; and its Ints were plain JS numbers, with no step counted.

The games and activities of hazeljs-examples have hazel-jit’s numbers but none for the other compilers. Report 063 timed every game four ways (on the interpreter, through the jit, compiled ahead of time, and, for five games, in JavaScript written by hand), and report 054 timed each game’s own run of states as its page plays it. Neither has ReScript, Melange or js_of_ocaml: for them each game’s rules must be written again, in OCaml (for Melange and js_of_ocaml) or in ReScript. Five games already have a version in plain JavaScript, written by hand: Checkers, Go, Minesweeper, Mahjong and Solitaire. They come first (What next), so that each has all six: the interpreter, hazel-jit, ReScript, Melange, js_of_ocaml and the hand-written JavaScript, each playing the game’s own run of states in its own layout.

What is still left

This report’s

Five steps, in the order Matthew set on 2026-11-25, each a ticket on the work dashboard; the first three are made and being timed, the fourth is measured, and options unboxed come last, after a decision. Matthew: “let’s keep going, skipping 1 (unboxed options) until all others are done”, with the priority below; and “please document our plan for the day as a ticket, or several that link to each other”. The day’s plan is ^ticket(853), whose first two steps (the loops and the JS arguments, above) are merged; each ticket below links to it and to its neighbours. Steps 1 to 3 are one wave on a trial branch, trial/853-jit-more, each its own commit and its own build of the package, timed one after another on the games’ runners and merged together on Matthew’s word.

  1. Constructors without arguments made once (^ticket(854)). {$c: "None"} and {$c: "Done"} were made anew at each use; now each name is one constant before the program’s code (k$None$26), since a Hazel value has no identity and a page does not change what it is given. Committed (ae29353ff0).
  2. A module’s members by name (^ticket(855)). Common.ready was a guarded property read on every call. dev lowers a module to lets ending in a record of its members, so a let bound to a record written out whose entries are all variables is remembered, and Common.ready compiles to the member’s own variable; a call with its tuple written out then reaches the member’s direct form by name (ready$51.$d(...)). Committed (9dd8fce210).
  3. == against a literal as === (^ticket(856)). $R.eq(i$6, 0) becomes i$6 === 0 wherever one side is a number, string or boolean written out: $R.eq’s first test is that comparison, and its answer for anything else is false, as ===’s is. Constructors keep $R.eq. Committed (0ce95a2e8f), with tests for all three (6801508ed4).
  4. What exact Ints and the step count each cost (^ticket(857)). Both are Hazel’s meaning, so they are measured, not removed: two builds only for the bench, on top of step 3’s, one with Ints as plain JS numbers and one with no step counted. On the Petri rule, on the laptop, exact Ints cost about 7% of a call (1.77 µs against 1.64 without them) and the step count about 21% (1.40 without it); the games’ numbers are coming.
  5. Options unboxed, last (^ticket(858)): Some(t) as t and None as undefined, as ReScript and Melange have them (with a box for Some(None)). None of the 14 games uses an option (only the Petri rule’s pick does), so it would not show on the games; and it changes compiled code’s shapes, which pages that keep compiled code read, as the records did, while the way back would read an option only by its type, which it does not always have. A trial on the Petri rule, and what pages would change, for Matthew to decide.

Alongside, ^ticket(859): this report’s draft of #2859’s description, until Matthew says to post it.

Choices for the description

This report’s

Six things to settle before the description goes on GitHub. Each is a choice for Matthew; the draft above takes the first option of each.

  1. How long the summaries are. Six points each now. Or shorter: three sentences for the executive summary, and the engineering summary’s points as one paragraph.
  2. Which speed to quote first. The draft quotes the games compiled ahead of time against the interpreter (2,392 times as fast, the geometric mean over 45 operations, measured with hazeljs 0.0.11 for report 063). The other candidates: the evaluator tests’ median, 395 times; or one game’s step, Gnome dig’s 82 ms against 0.28 ms through the jit. The first is the broadest, but its build is two days older than the layout this PR has.
  3. Whether the comparison with ReScript, Melange and js_of_ocaml belongs in the PR. It helps a reviewer who knows those compilers; it also invites the question of why hazel-jit doesn’t use one of them (report 046’s answer: none compiles Hazel, and hazel-jit compiles in the page while the program runs). Or leave it to this report and link it.
  4. Whether to say what the sweep costs CI. Every evaluator test runs a second time, compiled, and a third, mixed. Not measured yet: the Fast checks’ time on dev against hazel-jit.
  5. Whether the reports are linked from the PR. The draft links reports 046, 054 and 063 at its end. Another choice is to link this report once, for the details and the history.
  6. The compiler’s header comment, out of date. HazelJit.re opens with the layout of values, and on #2859 it still says a tuple is an array with its labels as properties. Fixed on today’s trial (50b70d5a40), to come with it.
