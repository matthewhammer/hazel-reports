Converting JS Values Directly

^report(34)'s next steps include this one: convert JavaScript values directly into Hazel values at the call boundary, not through syntax that Hazel then evaluates again. This report measures what that saves, in time and in space, with the trial branches that already do it. Asked by Matthew, 2026-11-03 (^ticket(681)).

Short answers. All measured on GitHub's machines in Node, two rounds; the method is at the end.

  1. A call takes 60 to 85% less time. Passing {{cells_64}} cells from JavaScript to a Hazel function took {{t_typed_64}} ms with the package's build and {{f_typed_64}} ms with the trial that converts directly ({{p_typed_64}}). Without a type annotation on the parameter: {{t_untyped_64}} ms against {{f_untyped_64}} ({{p_untyped_64}}).

  2. A call allocates 75 to 85% less memory. At 1,024 cells, a typed call allocated {{a_typed_32}} with the package's build and {{af_typed_32}} with the trial; an untyped call {{a_untyped_32}} against {{af_untyped_32}}.

  3. A function that holds a value stops paying for it on every call. A function Hazel returned, holding {{cells_64}} numbers, took {{h_base_64}} ms and allocated {{h_base_mb_64}} a call with the package's build, growing with what it holds. With the closures trial: {{h_clo_64}} ms and {{h_clo_mb_64}} at every size, about {{h_ratio}} times faster.

  4. A value converted once and passed as a handle costs almost nothing: {{hd_64}} ms a call at every size, against {{hd_conv_64}} ms converted each time, at {{cells_64}} cells.

  5. What is left is the type annotation's check. With the trial, a typed call still takes about {{ratio_typed}} times an untyped one: Hazel checks the converted value against the parameter's type again. That is #2681's work, not this step's.

  6. Next: the three trials have green CI, and wait on Matthew's call on how they go up: lib-floor first (^ticket(539)), then the closures (^ticket(558)) and the handles (^ticket(551)) stacked on it.

The step

When a JavaScript program calls a Hazel function through Hazel's JS library, the argument has to become a Hazel value. Today the library turns it into Hazel syntax, a term with a fresh id on every node, and the evaluator then steps that term back into the value it already was, and checks it against the parameter's type. ^report(25) measured that as the floor every call pays, whatever the function does. ^report(34)'s step 4 is to stop doing that.

Three trial branches each take part of the step. Each is a branch of #2719 with green CI, built by Hazel's own Deploy workflow:

  • lib-floor (^ticket(539)): the converted argument is bound in the environment, and the function is applied to its name, so the evaluator never steps it again.
  • lib-closures (^ticket(547), ^ticket(558)): a function the library returns is the evaluator's own closure, its environment kept apart. Before, the environment was written into the function's body, so a held list became a literal that every call evaluated again.
  • handles (^ticket(551)): Hazel.value(x) converts a value once and returns a handle; a call given the handle binds the stored value, with no conversion at all.

The package's build and lib-floor pay for the whole list on every call, in time and in memory, because the list was written into the function's body as a literal. lib-closures keeps the list in the closure's environment, so a call costs the same whatever it holds. On ^ticket(558)'s laptop measurements, Messed Up Dress Up's World rule, its map held as a tree, went from 90 to 0.75 ms a move at 64×64 the same way.

What this does not show

  • The browser. These are Node's numbers on GitHub's machines. ^report(25)'s and the trials' own laptop numbers agree on the direction and roughly on the size.
  • The game's real rules, beyond what ^ticket(558) measured. The functions here do nothing but return, so the boundary is all there is to measure.
  • What a held value keeps. The driver also reads the heap kept by a held function, but its readings are noisy at these sizes; all three builds keep about the list itself, about 1.9 MB for 4,096 numbers.
  • Correctness. That is CI's: each trial has Fast checks and Full tests green, with tests of its own (curried functions, functions a call returns, handles in a call and in an argument tuple).

How this was put together

  • The driver is bench/boundary.mjs in hazelgrove/hazeljs, run by its Boundary benchmark workflow, which anyone can start. A call's time is the median of at least 15 calls, and of at least 300 ms of them, after 3 to warm up. Its allocation is the median of 7 single calls, each after a forced collection (node --expose-gc --max-semi-space-size=256).
  • The run: 2026-11-03, workflow run 41693524506, GitHub's ubuntu-latest runner, Node 22. Two rounds, each running the four builds one after another; the tables show the mean of the two. The rounds agree within about 10%, except the typed calls at 1,024 cells on the trials (8.8 to 11.8 ms).
  • The builds: the package's is hazeljs 0.0.3's hazel-lib.js from jsDelivr (hazelgrove/hazel at 0d66c36618, #2719). The trials' are Hazel's own Deploy builds from build.hazel.org: lib-floor at 409e8f2116, lib-closures at 7563919f60, and the handles trial at 0220562cee.
  • The data: in this page (script#report-data) and in 040/data/boundary.json, each round's numbers kept.
