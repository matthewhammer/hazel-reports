Gnome World’s Planning, Rivers and Folk, in Hazel

Matthew asked how much of Gnome world is Hazel, and then for more of it, each piece opt-in and off by default: “the villagers walking, the squirrels, the hawks and insects; the rivers held at their level, the pumps and the rain; the speed run’s planning (the order of things, its targets, the dig’s chunks)” (2026-11-28, ^ticket(907)). This report covers the three Hazel modules that do it, how each is held to the page’s JavaScript, what each costs, and the speed run with each switched on.

Outline#

  1. The builds: 0.0.152, and 0.0.153 to 0.0.156, one module each.
  2. How a Hazel piece is held to the page’s: two versions of each piece, the same answers on every push.
  3. The speed run’s planning: the same plan, the order of the things in 95 ms against 3.7, once a run.
  4. The rivers, the pumps and the rain: every tile’s water the same, 0.079 ms a step against 0.009.
  5. The villagers, squirrels, insects and hawks: every creature the same over 900 steps, 0.24 ms a step for all of them against 0.031.
  6. The page’s chances, worked out in Hazel: a draw went from 3.2 µs to 0.7 µs.
  7. The speed run, five ways: each new module alone leaves it about as it was (20.0 s); every Hazel option on, the water among them, and it does not finish in two minutes.
  8. How much of Gnome world is Hazel: 11% of the code became 14%; the drawing is next.
  9. What next, and how this was put together.

In short. Three new Hazel modules take over the speed run’s planning (Plan.hz), the rivers, pumps, rain and drying (Rivers.hz), and the villagers, squirrels, insects and hawks (Folk.hz). Each is off unless chosen under ⚙️ Advanced or by a query (?plan=hazel, ?rivers=hazel, ?folk=hazel). The page’s JavaScript stays the default and is each one’s twin: the world save check runs both from one state on every push and finds the same plan, the same water in every tile and the same state in every creature. For the creatures to match, Hazel works out the page’s own random numbers from its seed, to the bit. Hazel takes from about as long as the JavaScript (the 2 hawks) to 26 times as long (the order of the 12 things, worked out once), and the pieces are small: with one of them on, the speed run takes 19.0 s, 21.6 s or 21.1 s against 20.0 s. With every Hazel option on, the water in Hazel (^report(69)) among them, it does not finish in two minutes. Hazel is now 14% of the game’s own code and 22% of the code that is not drawing. The drawing is 44% of app.js, and it is the next piece to move to Hazel (^ticket(908)).

How a Hazel piece is held to the page’s#

Each piece has two versions, the page’s JavaScript and a Hazel module, and a test runs both from one state and compares every value they leave; the world save check runs those tests on every push to the repository. This is the pattern of Water.hz and Path.hz (^report(69)). The JavaScript stays the default, so a player sees nothing new unless a switch is on; with a switch on, the page hands the Hazel function what it needs, takes back what it returns, and writes that into the world. The tests are WorldTest.planSame, riversSame and folkSame. Each sets the world back after itself, so the tests can run in the middle of a game.

Where a piece reads the world (a tile’s height, a flower in reach, a tree’s limbs), the page reads it and hands it over: Hazel has no arrays and cannot read the page’s, so each call gets the few values it needs as lists and records. Where a piece writes the world, Hazel returns the new values and the page stores them. The first three tests on GitHub, from the world the save check’s tour leaves:

The speed run’s planning#

Plan.hz finds the same plan as the page: the same order for the 12 things, the same 64 tree parts, the same 336 gems nearest first and the same next chunk of the dig. The order costs the most, 95 ms in Hazel against 3.7 ms in JavaScript, but the run works it out once. The order is the shortest tour through the things, found by Held and Karp’s method: for each set of things and each last thing, the shortest way through that set ending there. JavaScript keeps those best ways in an array indexed by the set’s bits. Plan.hz keeps each size’s sets in a balanced tree and builds each size from the one before. In the speed run that one call makes one frame of 117 ms, where the page’s own longest frame is 50 ms. The other three pieces are a filter, a stable sort and a choice, each a millisecond or two in Hazel.

The rivers, the pumps and the rain#

Rivers.hz leaves every tile with the same water as the page’s JavaScript, to the bit, in dry steps and in rain. It takes 0.079 ms a step against 0.009 ms, where a whole step of the speed run takes about 0.3 ms. Each step it holds each river at its level, draws the villages’ pumped rooms down by 0.004, starts a shower when one is due, lets its 24 drops fall, and every half second dries the land’s top. The page still draws the rain’s chances, as it always has, and hands them in. Each amount is rounded as the page stores it, to a 32-bit float, by Veltkamp’s split (^report(69)).

The villagers, squirrels, insects and hawks#

Folk.hz moves all 80 villagers, 14 squirrels, 70 insects and 2 hawks just as the page does. Over 900 steps, with the gnome led past each squirrel and each insect, every value of every creature comes out the same, and so does the page’s random seed. All of them together take 0.24 ms a step in Hazel against 0.031 ms in JavaScript (0.0.156).

  • A villager stands a while, walks within its reach (its room, its stretch of land or its platform), and is busy at what its room is for. The page hands Hazel the land’s height under the columns a walk crosses.
  • A squirrel runs along its tree’s limbs, a graph of 400 to 1,650 points. Near the gnome, it flees by a breadth-first search to the point furthest from the gnome within 30 points. Looking a point up in a list of 1,650 would take as many steps, so the page hands the graph over 32 points to a chunk, made once a tree and kept: a point is then a few dozen steps away. In the test, squirrels fled on 208 of the steps.
  • An insect: a dragonfly darts and hovers over the water; a bee or a butterfly wanders, flies to a flower in reach, rests on it, and flees the gnome. The page hands each bee or butterfly the flowers still standing in its reach and the land’s height at each.
  • A hawk soars in a ring that drifts toward the gnome, flies to the nearest great tree and rests there, and leaves when the gnome comes near. In the test, the two hawks soared, flew and rested (soar 78, fly 1061, rest 661 steps).

Three small changes make the page’s own version give the very numbers Hazel’s does. It takes its distances by Math.sqrt, not Math.hypot, which can differ in the last bit. It rounds as Math.floor(x + 0.5), which differs from Math.round for a few numbers just under a half. And a hawk’s angle comes from Math.atan, worked out as fdlibm’s atan2 does but without its last small correction, because Hazel has atan and no atan2. None of these changes shows on the screen.

The page’s chances, worked out in Hazel#

The creatures’ chances are the page’s own random numbers, worked out in Hazel from the page’s seed: the seed goes in with each call and the new one comes back. Every draw is the page’s draw, so the page’s version and Hazel’s draw the same numbers in the same order. The page’s generator multiplies the seed by 1,103,515,245, adds 12,345 and keeps the last 31 bits. It does this in JavaScript’s 64-bit floats: a product past 253 is rounded to 53 significant bits, ties to even, before the last bits are kept. Hazel’s integers are exact, so Folk.hz rounds the same way itself. It matched the page on every one of 2.3 million seeds tried.

In 0.0.155 a draw took about 3.2 µs: to round, Folk.hz counted the product’s bits one at a time, about 62 steps on numbers past 253, which the compiled code works out as JavaScript BigInts. In 0.0.156 it finds the size by a search over the nine sizes the product can have, and a draw takes about 0.7 µs. The insects, which draw two to six times a step each, went from 0.28 ms to 0.15 ms a step for all 70.

The speed run, five ways#

On one GitHub runner, the speed run as the page plays it takes 20.0 s with the JavaScript, 19.0 s with the planning alone in Hazel, 21.6 s with the rivers, and 21.1 s with the creatures: a run’s noise of a second or two. With every Hazel option on it does not finish in two minutes: after two minutes it had found all 12 things, all 64 tree parts and 251 of 336 gems. The frames come at 16.7 ms (60 fps) median either way, but with every Hazel option on a frame gets through 6 of the game’s steps where it got through 35. With every option on, the compiled Hazel is 45% of the page’s busy time and garbage collection 3.7%; ^report(69) found the water in Hazel alone at about half the busy time, so the water is most of it. The three new modules alone cost little: compiled Hazel is 4.2% of the busy time with the planning in Hazel, 9.9% with the rivers and 9.0% with the creatures, against 3.5% with none of them on (the gnome’s step and the other rules that were Hazel already).

How much of Gnome world is Hazel#

Counted by characters, comments left out of the Hazel, Hazel’s rules went from 11% of the game’s own code (0.0.152) to 14% (0.0.156), and from 18% to 22% of the code that is not drawing. The rules are 1,178 lines in 16 modules; app.js is 728 thousand characters, of which the drawing is 322 thousand, 44%. Switching on a Hazel option changes which code runs, not how much there is. With every option on, the step’s pieces that are still only JavaScript are the gnome’s input and camera, the sound, saving and loading, and the HUD. The drawing is still all JavaScript.

What next#

  1. The drawing in Hazel, one part at a time, each timed against the page’s JavaScript and compared pixel for pixel (^ticket(908), Matthew, 2026-11-28: “let’s start to port the drawing code from JS to Hazel … one component at a time”).
  2. Arrays in Hazel (^ticket(846)): Plan.hz’s table of best tours and Folk.hz’s squirrel graphs both work around the lack of them.
  3. A builtin for JavaScript’s float multiply, or a 53-bit rounding, so the page’s random numbers in Hazel need no search at all.
  4. An atan2 builtin in Hazel, so the hawks’ twin can use the browser’s own.

How this was put together#

The pieces’ times and the random numbers’ costs were measured in the Claude app’s browser pane on the laptop, with Gnome world’s test hooks (WorldTest.planSame, riversSame, folkSame, and calls to the compiled folk_bug alone), its rules built by hazel-jit at load. A piece’s time is the mean over the steps run: three rounds for the rivers and the creatures in 0.0.155, one in 0.0.156. The twins’ lines are from hazeljs-examples’ “world save check” on GitHub, runs 46167673024 and 46167928740. The speed run is hazeljs-examples’ “world speed run, frame by frame” (node/world-frames.mjs), run 46167931157 on one runner (4 CPUs, AMD EPYC 9V74 80-Core Processor; Node v22.23.5; Google Chrome 158.0.8127.36), headless Chrome at 1280×800, each setup a fresh page in turn, up to two minutes each; its log is read with gh run view --log and parsed by parse_frames.py. The code sizes are sizes.py, ^report(68)’s, run on hazeljs-examples at 5631853 (0.0.152) and 97fccb2 (0.0.156). The page is built by gen070.py from data/.
