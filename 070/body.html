Gnome World’s Planning, Rivers and Folk, in Hazel

Matthew asked how much of Gnome world is Hazel, and then for more of it, each piece opt-in and off by default: “the villagers walking, the squirrels, the hawks and insects; the rivers held at their level, the pumps and the rain; the speed run’s planning (the order of things, its targets, the dig’s chunks)” (2026-11-28, ^ticket(907)). This report covers the three Hazel modules that do it, how each is held to the page’s JavaScript, what each costs, and the speed run with each switched on.

In short. Three new Hazel modules take over the speed run’s planning (Plan.hz), the rivers, pumps, rain and drying (Rivers.hz), and the villagers, squirrels, insects and hawks (Folk.hz). Each is off unless chosen under ⚙️ Advanced or by a query (?plan=hazel, ?rivers=hazel, ?folk=hazel). The page’s JavaScript stays the default and is each one’s twin: the world save check runs both from one state on every push and finds the same plan, the same water in every tile and the same state in every creature. For the creatures to match, Hazel works out the page’s own random numbers from its seed, to the bit. Hazel takes from about as long as the JavaScript ({{x_lo_name}}) to {{x_hi}} times as long ({{x_hi_name}}), and the pieces are small: with one of them on, the speed run takes {{plan_real}}, {{rivers_real}} or {{folk_real}} against {{js_real}}. With every Hazel option on, the water in Hazel (^report(69)) among them, it does not finish in two minutes. Hazel is now {{share_new}} of the game’s own code and {{share_nd_new}} of the code that is not drawing. The drawing is 44% of app.js, and it is the next piece to move to Hazel (^ticket(908)).

Since, the same day (revised {{updated}}). Exact integers were most of the creatures’ cost (^report(71)), so in 0.0.157 Folk.hz writes its numbers as Floats under use Float in (Matthew: “Float, use Float in”), and in 0.0.158 Path.hz and Rivers.hz do too, every answer still the same as the page’s. How a Hazel piece is held to the page’s

Each piece has two versions, the page’s JavaScript and a Hazel module, and a test runs both from one state and compares every value they leave; the world save check runs those tests on every push to the repository. This is the pattern of Water.hz and Path.hz (^report(69)). The JavaScript stays the default, so a player sees nothing new unless a switch is on; with a switch on, the page hands the Hazel function what it needs, takes back what it returns, and writes that into the world. The tests are WorldTest.planSame, riversSame and folkSame. Each sets the world back after itself, so the tests can run in the middle of a game.

Where a piece reads the world (a tile’s height, a flower in reach, a tree’s limbs), the page reads it and hands it over: Hazel has no arrays and cannot read the page’s, so each call gets the few values it needs as lists and records. Where a piece writes the world, Hazel returns the new values and the page stores them. The first three tests on GitHub, from the world the save check’s tour leaves:

The speed run’s planning

Plan.hz finds the same plan as the page: the same order for the 12 things, the same 64 tree parts, the same 336 gems nearest first and the same next chunk of the dig. The order costs the most, {{order_hz}} ms in Hazel against {{order_js}} ms in JavaScript, but the run works it out once. The order is the shortest tour through the things, found by Held and Karp’s method: for each set of things and each last thing, the shortest way through that set ending there. JavaScript keeps those best ways in an array indexed by the set’s bits. Plan.hz keeps each size’s sets in a balanced tree and builds each size from the one before. In the speed run that one call makes one frame of {{plan_worst}} ms, where the page’s own longest frame is {{js_worst}} ms. The other three pieces are a filter, a stable sort and a choice, each a millisecond or two in Hazel.

The rivers, the pumps and the rain

Rivers.hz leaves every tile with the same water as the page’s JavaScript, to the bit, in dry steps and in rain. It takes {{rv_hz}} ms a step against {{rv_js}} ms, where a whole step of the speed run takes about {{step_ms}} ms. Each step it holds each river at its level, draws the villages’ pumped rooms down by 0.004, starts a shower when one is due, lets its 24 drops fall, and every half second dries the land’s top. The page still draws the rain’s chances, as it always has, and hands them in. Each amount is rounded as the page stores it, to a 32-bit float, by Veltkamp’s split (^report(69)).

The villagers, squirrels, insects and hawks

Folk.hz moves all 80 villagers, 14 squirrels, 70 insects and 2 hawks just as the page does. Over 900 steps, with the gnome led past each squirrel and each insect, every value of every creature comes out the same, and so does the page’s random seed. All of them together take {{folk_hz}} ms a step in Hazel against {{folk_js}} ms in JavaScript (0.0.156).

  • A villager stands a while, walks within its reach (its room, its stretch of land or its platform), and is busy at what its room is for. The page hands Hazel the land’s height under the columns a walk crosses.
  • A squirrel runs along its tree’s limbs, a graph of 400 to 1,650 points. Near the gnome, it flees by a breadth-first search to the point furthest from the gnome within 30 points. Looking a point up in a list of 1,650 would take as many steps, so the page hands the graph over 32 points to a chunk, made once a tree and kept: a point is then a few dozen steps away. In the test, squirrels fled on {{flee}} of the steps.
  • An insect: a dragonfly darts and hovers over the water; a bee or a butterfly wanders, flies to a flower in reach, rests on it, and flees the gnome. The page hands each bee or butterfly the flowers still standing in its reach and the land’s height at each.
  • A hawk soars in a ring that drifts toward the gnome, flies to the nearest great tree and rests there, and leaves when the gnome comes near. In the test, the two hawks soared, flew and rested ({{hawk_steps}} steps).

Three small changes make the page’s own version give the very numbers Hazel’s does. It takes its distances by Math.sqrt, not Math.hypot, which can differ in the last bit. It rounds as Math.floor(x + 0.5), which differs from Math.round for a few numbers just under a half. And a hawk’s angle comes from Math.atan, worked out as fdlibm’s atan2 does but without its last small correction, because Hazel has atan and no atan2. None of these changes shows on the screen.

The page’s chances, worked out in Hazel

The creatures’ chances are the page’s own random numbers, worked out in Hazel from the page’s seed: the seed goes in with each call and the new one comes back. Every draw is the page’s draw, so the page’s version and Hazel’s draw the same numbers in the same order. The page’s generator multiplies the seed by 1,103,515,245, adds 12,345 and keeps the last 31 bits. It does this in JavaScript’s 64-bit floats: a product past 253 is rounded to 53 significant bits, ties to even, before the last bits are kept. Hazel’s integers are exact, so Folk.hz rounds the same way itself. It matched the page on every one of 2.3 million seeds tried.

In 0.0.155 a draw took about {{rand_old}} µs: to round, Folk.hz counted the product’s bits one at a time, about 62 steps on numbers past 253, which the compiled code works out as JavaScript BigInts. In 0.0.156 it finds the size by a search over the nine sizes the product can have, and a draw takes about {{rand_new}} µs. The insects, which draw two to six times a step each, went from {{bugs_old}} ms to {{bugs_new}} ms a step for all 70.

Which Hazel ran

Every Hazel time in this report is Hazel compiled to JavaScript by hazel-jit, not interpreted. The pane loaded the hazeljs branch’s build from build.hazel.org, commit 0f24cea171 of 2026-11-27, and compiled the rules as the page loaded. Its compiler is hazel-jit’s latest: the hazel-jit branch has gained only its agreement tests since. Gnome world gets Hazel in one of three ways, in this order:

  • Ahead of time. world/rules-aot.json, compiled on GitHub by the “world aot” job after each push, with the library of trial/1126-night (abf653a21d, 2026-11-26). The page uses it only when it was compiled for the very rules text the page has. On each release here, the page’s text was newer than the file until the job’s commit caught up, so the frames job and the save checks compiled at load too (the frames log says “compiled by hazel-jit at load”).
  • At load. The hazeljs branch’s build, build.hazel.org/hazeljs/hazel-lib.js, which compiles the rules in the page: 30 s in the pane on the laptop. This is what ran here.
  • Interpreted. npm’s hazeljs 0.0.4, only when build.hazel.org cannot be reached. It did not run here. Interpreted, the games take about four thousand times as long as through hazel-jit (^report(65)).

The two builds compile alike: both have ticket 891’s integer division and arithmetic folded at compile time. trial/1126-night also has ticket 791’s faster labeled tuples in the type checker, and the hazeljs branch has ticket 896’s interpreted calls. Not in either: the agreement tests of ^ticket(903) (tests only), the bench builds of ticket 853 (Ints as plain JavaScript numbers, options unboxed), and the hybrid lists of hazel-jit-lists.

So the Hazel pieces’ times above are hazel-jit’s, and the gap to the page’s JavaScript is what compiled Hazel still pays. ^report(71) breaks it down. Converting lists into and out of compiled code is from 5% to 70% of a call, most where the calls are small. Exact integers are most of the creatures’ time: Folk.bug’s step for an insect takes 2.3 µs with plain-number Ints against 5.9 µs as compiled. Its next steps were lists as arrays in hazel-jit (^ticket(909)), now built on a trial and measured there, and a number type as JavaScript’s; Matthew chose Floats under use Float in for that (^ticket(910)), and Gnome world’s creatures, way and rivers use them since 0.0.157 and 0.0.158.

What next

  1. The drawing in Hazel, one part at a time, each timed against the page’s JavaScript and compared pixel for pixel (^ticket(908), Matthew, 2026-11-28: “let’s start to port the drawing code from JS to Hazel … one component at a time”).
  2. Arrays in Hazel (ticket 846): Plan.hz’s table of best tours and Folk.hz’s squirrel graphs both work around the lack of them.
  3. Done another way (0.0.157): Folk.hz in Floats, the page’s random numbers as its own steps in doubles, float_mod(s * 1103515245 + 12345, 2147483648), with no rounding to emulate and no BigInts; an insect’s step 0.37 µs where it was 4.7 µs.
  4. An atan2 builtin in Hazel, so the hawks’ twin can use the browser’s own.

How this was put together

The pieces’ times and the random numbers’ costs were measured in the Claude app’s browser pane on the laptop, with Gnome world’s test hooks (WorldTest.planSame, riversSame, folkSame, and calls to the compiled folk_bug alone), its rules built by hazel-jit at load. A piece’s time is the mean over the steps run: three rounds for the rivers and the creatures in 0.0.155, one in 0.0.156. The twins’ lines are from hazeljs-examples’ “world save check” on GitHub, runs {{save_runs}}. The speed run is hazeljs-examples’ “world speed run, frame by frame” (node/world-frames.mjs), run {{run_f}} on one runner ({{m_f}}), headless Chrome at 1280×800, each setup a fresh page in turn, up to two minutes each; its log is read with gh run view --log and parsed by parse_frames.py. The code sizes are sizes.py, ^report(68)’s, run on hazeljs-examples at 5631853 (0.0.152) and 97fccb2 (0.0.156). The page is built by gen070.py from data/.
