Undo, in Time and Space

What does an undo cost in Hazel's editor, in memory and in time? How did we find out, where does the investigation stand, and what comes next? The memory story is ^report(14)'s update (2026-10-14 and 15); the time story is ^report(36) (2026-11-02). This report puts them together and adds one new measurement: the modular editors' outline, rebuilt on every undo and redo, separated from the rest. For Matthew's meeting with Cyrus on 2026-11-04 (^report(37)).

Short answers. Space: one slide (Full Body) in a browser, 12 slider edits, the live heap after each. Time: a program of n definitions in Node, an edit in the middle one, then undos and redos. The methods are at the end.

  1. The undo history kept a whole copy of the editor for every edit, and nothing capped it. On #2597 a Full Body tab kept {{kept_asbuilt}} MB after 12 edits, {{grow_asbuilt}} MB more for each one. Andrew Blinn's compaction of undo snapshots (6010128b7d, on #2469) brought that to {{kept_compact}} MB, level after the third edit: {{kept_ratio}} times less. #2635 has it and kept {{kept_2635}} MB. Dev still keeps whole copies, capped only when a setting that is off by default is turned on (space).

  2. It was found in five steps, after a false negative. A first build that "capped the undo history at 2" changed nothing, so the history was ruled out. But that cap runs only when the setting is on, so the build never applied it. Heap snapshots of a 2.3 GB tab were made to work, and two of them, a few edits apart, showed three copies of one 35 MB structure: Full Body's editor with everything derived from it. Two of the copies hang from the undo history's first two entries (how it was found).

  3. Saving the space costs time, and keeping one entry whole buys it back. A compacted entry has dropped its derived data, so restoring it rebuilds that data. With compaction alone, a redo took about as long as an edit: on #2635, 3.6 to 4.2 s against 1.2 s for an edit. Keeping the newest entry of each stack whole (032fe3aca6, on #2635 since 2026-10-15) brought the latest undo and redo to 0.3 s, for about 1 MB more (the price).

  4. In time, every step grows in proportion to the program. At 6,400 definitions an edit takes {{edit_6400}} ms, an undo {{undo_6400}} and a redo {{redo_6400}}, each followed by about 78 ms of statics (^report(36)). The incremental caches work; the passes around them walk every definition (time).

  5. New: an undo is a redo plus a rebuild of the outline. The outline is the tree of a program's definitions that the sidebar and the agent read; it came with the modular editors (#2469), and dev has none. An undo rebuilds it from scratch every time, about {{outline_3200}} ms at 3,200 definitions: {{share_lo}} to {{share_hi}}% of the undo. A redo finds it in a memo of the last four programs, except when the program is not among them, which is why the last of the probe's redos is as slow as an undo, or slower. Even a redo that finds its outline still costs {{hitx_lo}} to {{hitx_hi}} edits; a restore spends longer than an edit rebuilding the program's syntax, and why is the next question. And in the app, where the sidebar shows the outline, the rebuild moves onto every edit: at 3,200 definitions about {{view_ol_3200}} ms after an edit of {{view_edit_3200}} (the outline).

  6. New: an undo rebuilt the syntax twice, and a one-line fix takes {{fix_undo_cut_3200}}% off an undo and {{fix_redo_cut_3200}}% off a redo at 3,200 definitions. The frame an undo schedules to realize the view counted as an edit, so it rebuilt in full the syntax the undo's own frame had just rebuilt. With it counted as an edit only when it changes the program, a redo costs what an edit does, {{fix_redo_a_3200}} ms against {{fix_edit_3200}}, and an undo an edit plus the outline. On a trial branch, not yet on #2635 (the fix).

  7. Next: put the fix on #2635; make the outline's build touch only what changed; measure what one undo entry keeps as the program grows; decide whether dev gets the compaction before #2469 lands; and the balanced tree of definitions, which would make each step and each entry O(log n) (what next).

Space: what the undo history keeps

The undo history (History.Model in src/web/app/History.re) is two lists, the undo stack and the redo stack. Before every edit, the page as it was goes onto the undo stack. On #2597 as built, each entry is a whole page model: every slide's editor, with that editor's syntax, statics and layout. On Full Body that is about 90 MB per edit, and nothing else keeps it. The lists are meant to stop at 250 entries, but they are cut only when the setting cap_undo_stack is on, and Settings.re sets it off.

{{TABLE_SPACE}}

The capped build levels off once its history is full, but each of its two entries is still a whole page. The compaction keeps no derived data in any entry but the newest, so it levels off at a lower line. #2635, with the same compaction, kept less still; why it is lower than #2597 compacted was not examined. Over 30 edits, #2635 rose to 94 MB at the tenth edit and fell back to 46 MB at the eleventh, and again at the 22nd. The likely cause is the tables of values shared with the evaluation worker, which start over at their cap. That is not confirmed.

Dev today. Dev's History.re at f042cced44 (2026-11-02) still keeps whole page models and cuts them only when cap_undo_stack is on, and its default is still off. Dev's growth per edit has not been measured. Its slides differ from #2597's, so the 90 MB is #2597's figure, not dev's.

How it was found

^report(14) first ruled out every cache and table it could switch off, each in a build of its own. One of those builds was meant to cap the undo history at 2 states. It changed the 250 in capped_undo_stack_size, but the cut that uses it runs only when the setting is on. So the build kept every state, grew 92 MB per edit like the others, and the history looked innocent. When a cap changes nothing, check that its code runs before ruling it out. Then, in five steps, each one taking a suspect off the list:

  1. Not what the browser holds. Over six edits the heap grew from 400 to 900 MB, while the page's event listeners (609), DOM nodes, detached ones included (47,923), observers and timers stayed exactly the same.
  2. Not on #2635. The same sampled heap profile, over the same four edits, keeps 37.5 MB on #2635, against 390 MB on #2597, and almost none of it in types, statics, terms or layout.
  3. A heap snapshot, at last. On this tab the usual tool killed the renderer at once. The lead was ValueHash's memo of hashes, a WeakMap of roughly two million entries: a test page with a WeakMap that size never finished its snapshot. A probe build keeps that memo only within one synchronous run. The tab still grew 68 MB per edit, and a snapshot after six edits completed: 2.3 GB of JSON in 75 seconds.
  4. Two snapshots, one session. V8 keeps each object's snapshot id for the life of the tab. So the objects in a snapshot after edit 6 that a snapshot after edit 3 lacks were made by edits 4 to 6: 12.2 million objects, 257 MB. A dominator tree of the second snapshot (29 million nodes, 4.6 s, computed by a small C program) shows three copies of one 35 MB structure: Full Body's editor with its derived data. Two hang from the first and second entries of the undo history. The third is the one view in the projector view cache, which is replaced, not added to.
  5. Confirmed by a build that always cuts the history to 2 states, whatever the setting: {{kept_cap2}} MB after 12 edits, against {{kept_asbuilt}}, in two runs.

The fix was already written. Andrew Blinn had met the same growth on the modular editors, on a much larger program, and fixed it in 6010128b7d (2026-08-26): each page model saved for undo drops its derived data, and the cap always applies. That is why #2635, which has #2469 merged in, did not grow.

What a compacted entry keeps

On #2635 (History.re at 1d17541aaf), pushing an entry compacts the one below it:

  • Dropped: the syntax, replaced by a small shared placeholder marked out of date; the statics; the evaluation states and results.
  • Kept: the zippers, the editor's own form of the text and the caret. The code's own comment adds that compacted entries still hold frozen typing contexts and the master segments, and that a deep stack of them runs out of memory on large programs. That is why the cap of 250 stays.
  • The newest entry of each stack stays whole, and is compacted only when the next one is pushed above it. That is at most two whole page models.
  • Restoring a compacted entry rebuilds its syntax against the live editor's parse and layout caches (Page.carry_over), which hit for every piece the step did not change. Statics and results wait for the typing debounce, as after a keystroke.

So a compacted entry is smaller, but not free. How much it keeps at n definitions, and how much of it consecutive entries share, has not been measured (below).

How the compaction works

An example first. Start with a page A, make three edits, to B, C and D, then undo twice and redo once. In the table a whole entry is in bold, and a compacted one, its derived data dropped, is plain.

StepUndo stack, top firstThe pageRedo stack, top firstWhat the step costs
Start—A—
EditAB—an edit
EditB, AC—an edit; A is compacted as B goes on top of it
EditC, B, AD—an edit; B is compacted
UndoB, ACDC was whole: no rebuild
UndoABC, DB was compacted: its syntax is rebuilt; D is compacted
RedoB, ACDC was whole: no rebuild

The rules behind the table, as History.re on #2635 (243874eecd) applies them:

  1. An edit puts the page as it was onto the undo stack, whole. The entry that was on top is compacted (compact_head). The stack is then cut to its newest 250 entries, always: dev's cut runs only when the setting cap_undo_stack is on. The redo stack is emptied.
  2. An undo takes the top entry off the undo stack, and it becomes the page (Page.carry_over). The page as it was goes onto the redo stack, whole, and the entry that was on top of the redo stack is compacted.
  3. A redo is the same, the other way round.
  4. A tentative step, one that can still be taken back, keeps the redo stack it emptied. Taking the step back puts that stack back.

Compacting a page (compact) touches only its scratch slides and documentation slides. Tutorials, exercises and the configuration slide are never compacted. In each editor of those slides it:

  • keeps the zipper: the editor's text and its caret;
  • replaces the syntax (its tiles, terms and layout) with a placeholder, a single hole marked out of date. Each placeholder gets its own empty caches for layout and terms, because restored editors sharing one cache would keep evicting each other's entries;
  • empties the statics and the evaluation states;
  • keeps of the result only what autosave keeps, such as the stepper's position or a proof's progress. The value itself is evaluated again.

Compacting is cheap: a few new records per editor. What it frees is the derived data that no other entry holds. The work comes later, in a restore. Page.carry_over rebuilds the restored page's syntax from its zipper, using the live editors' parse and layout caches, which hit for every piece the step did not change. The restored page keeps the live statics and results until the typing debounce analyzes it again, as it would after a keystroke. That is why the code counts an undo or a redo as an edit.

The price in time

An entry without its derived data has to rebuild that data when it is restored. ^report(14)'s update timed an edit, an undo and a redo in the browser on Full Body, five runs per build: seconds from the key press to the picture changing.

{{TABLE_TIMES}}

With the compaction alone, every redo on #2597 took about as long as an edit, and half the undos did too. On #2635 a redo took about three edits. Keeping the newest entry whole gave back the latest undo and redo: on #2635 every one was done within 0.3 s, the check's own polling interval, and the memory kept over 12 edits was the same within about 1 MB. On #2597 it cost 49 MB more (208 against 159). An undo further back than the newest entry still rebuilds.

Open question: could entries be compact from the start?

Could the history never hold derived data that it later has to drop, or never need to drop it? The question has two readings, with different answers.

Push entries already compacted. This saves almost nothing, since compacting is a few new records per editor. And it loses the one fast path: the newest entry is kept whole so that the latest undo and redo restore without rebuilding. With every entry compacted, a redo on #2635 took about three edits (above).

Keep the derived data, shared. The real prize is an entry that keeps its derived data at the cost of only what its own edit changed. Then nothing would be compacted, and no restore would rebuild anything. Zippers are persistent already, so the text and caret of consecutive entries could share most of their pieces, though that has not been checked. The derived data is where it gets hard:

  • Whole-program passes build new structure on every edit. Rebuilding the top-level term, statics' walk down the chain of definitions, the outline and layout's walk each touch every definition (below). So what they build is new in every entry, O(n) of it, even after a one-character edit.
  • The caches are changed in place. The layout and term caches are hash tables, updated as they are used, so two entries cannot share one. That is why compaction gives each restored editor caches of its own.
  • Statics may already be close. DefStatics analyzes one definition at a time and keeps the analyses that did not change. In ^ticket(666)'s probe of 2026-11-03 on Full Body, after a one-number edit, 1 of its 167 top-level definitions had a new analysis. Whether consecutive entries then share the other 166 in memory has not been measured.
  • Results come back mostly as new objects. The values the page decodes from the evaluation worker are new objects, except the larger parts it already holds. In the same probe, none of the 192 blocks of Kids' Choice's result came back as the objects decoded the time before, and 60 of Full Body's 137 did. Entries could share results only as far as decoding keeps those identities.
  • What a compacted entry still holds is not yet understood. The code's comment names frozen typing contexts and master segments. Whether consecutive entries share them is the first thing to measure (below).

The balanced tree of definitions in What next is this idea taken all the way. Each node keeps its own derived summaries, a snapshot is a root that shares every node the edit did not touch, and an undo is a swap of roots, with nothing to compact and nothing to rebuild. The challenge is that every whole-program pass above would have to work on that tree, one path at a time.

Time: what a step costs as the program grows

^report(36) measured an edit, an undo and a redo against the size of the program, in Node, on #2635 after dev's merge day. A program of n definitions, let v0 = 0 in let v1 = v0 + 1 in …, an edit in the middle one, then undos and redos, each through the app's own update loop. In short:

  • Every step is linear in the program, a slope of 1.10 to 1.16 on a log-log plot from 800 to 6,400 definitions. At 6,400: an edit {{edit_6400}} ms, an undo {{undo_6400}}, a redo {{redo_6400}}, and about 78 ms of statics after each.
  • The incremental work is constant. Whatever n, a step parses 1 or 2 definitions again, measures 1 or 2 chunks of layout and compares 2 definitions' heads in statics. What grows is the walks around that work: rebuilding the top-level term (38% at 3,200 definitions), statics' walk down the chain of definitions (20%), the outline (15%, on undo and redo only) and layout's walk (6%).
  • The undo history itself costs almost nothing in time: an entry is pushed and popped at the head of a list.
  • Two fixes, now on #2635, took 31 to 46% off at the two largest sizes. The auto-probe had rebuilt the whole top level's skeleton on every frame (394552d5d0), and completion suggestions were computed after every typed digit (bfa36a6ede).

Figures, tables and code are in ^report(36).

The outline's part, separated

What the outline is. Outline.of_source builds the tree of a program's definitions, which the sidebar's code map and the agent's view read. It came to #2635 with the modular editors, #2469; its first commit is 99b9e25d7d (2026-10-23). Dev has no outline, so on dev an undo does not pay for one.

Why an undo rebuilds it, and a redo mostly does not. Restoring an entry schedules a second frame, RealizeView, which asks for the program's outline. The outline is memoized on the last four programs, found by the segment's identity and then by Segment.same_program. An undo restores a program that is not among them, so the outline is built from scratch. Each undo leaves its outline in the memo, so after the probe's four undos it holds the four programs the redos will restore, except the last: the program from after the edits, which no undo built, since in the probe an edit never builds an outline (nothing draws the sidebar). So the first three redos find their outline and the last one rebuilds it. ^report(36) noticed that the last redo was slow and could not say why; this is why. In the app the sidebar asks for the outline after edits too, which changes which steps pay for it (below).

How it was separated. From the step times by position, in ^report(36)'s release-build runs after the fixes: an undo's outline is what the undo costs beyond a redo that finds its outline. And from a profile that tells the kinds apart: the probe again (58dae0b427), with one named function per kind of step, built so the profiler can name each function's source and profiled twice at each size. In the profile the outline is {{pshare_lo}} to {{pshare_hi}}% of the undo steps' time and {{pshare_redo_lo}} to {{pshare_redo_hi}}% of the redo steps', the redos' share being their one rebuild in four.

  • An undo is a redo plus the outline. The rebuild is {{share_lo}} to {{share_hi}}% of an undo from 1,600 definitions up, about {{outline_3200}} ms at 3,200, and it grows with the program like the rest of the step.
  • A redo rebuilds it only when its memo misses. In the probe that is the last redo, as slow as an undo or slower; in use, it would be any undo or redo to a program the memo no longer holds.
  • Without the outline, a restore still costs {{hitx_lo}} to {{hitx_hi}} edits. In the profile, a redo spends about 1.8 times an edit's time rebuilding the program's syntax (CachedSyntax.mk), {{redo_syn_3200}} against {{edit_syn_3200}} ms of profile at 3,200 definitions: a restore rebuilds it against the live caches. It is not only the compaction: the newest entry keeps its syntax whole, and ^report(36) found it restores no faster. Every whole-program pass under it costs 1.8 to 2 times an edit's: the restore rebuilt the syntax twice (below).

With the sidebar, every edit pays for the outline

The probe draws no view, so nothing asks for the outline after an edit. In the app the sidebar's code map does, whenever it is shown, as it is in the deck's screenshots. So the probe was run once more asking for the outline after every step and once before the edits, as the sidebar's view would, timed on its own (UNDO_VIEW_OUTLINE, 5544ca12a3; the dev-profile build without the profiler, one run per size, so read the ratios).

{{TABLE_VIEW}}

Milliseconds, medians: edits 2 to 4 (the first edit of a run is slower), undos and redos 1 to 3.

  • Each edit rebuilds the outline, about as much again as the edit itself: {{view_ol_3200}} ms after an edit of {{view_edit_3200}} at 3,200 definitions, {{view_ol_6400}} after {{view_edit_6400}} at 6,400. The edit changed the program, so the memo misses.
  • Then an undo finds its outline, since the edits left it in the memo, and costs what a redo does: {{view_undo_3200}} and {{view_redo_3200}} ms at 3,200. The fourth undo, to the program before the edits, is out of the memo's four and rebuilds it.
  • So the outline is a cost of every step that changes the program, on the edit when the sidebar shows it and on the undo when it does not. Making the outline's build touch only what changed would take it off both. Today its top level walks every definition: Outline.level visits each span of the top level, reusing the entries below an unchanged one.

An undo rebuilt the syntax twice, and the fix

Found. The probe read PerfTimer's editor-syntax total in every frame (ab7dfd0188). An edit is one frame with one syntax pass, about 40 ms at 3,200 definitions. An undo or a redo is two frames, and each ran a full pass of about the same cost. The second frame is RealizeView, which the restore schedules. It returned through Updated.return, whose is_edit defaults to true, so its calculate marked the restored program's syntax out of date and rebuilt it again. The probe's own counts said so all along: a restore parsed 2 definitions in full and measured 2 chunks, an edit 1 and 1.

The fix (ed4d484671; on #2635's head as 9df1b2601e, pushed for CI to the branch trial/665-realize-not-edit, not to #2635): realizing the view counts as an edit only if it opened or closed a cell, that is, only if it changed the program.

let realized = realize(~info_map, code.view, code);
realized
|> return(~is_edit=realized.program !== code.program, ~historic=false);

Not yet measured

  • Space against the size of the program, on #2635. What a compacted entry and a whole entry keep at n definitions, and how much consecutive entries share. Zippers are persistent, so an entry after a small edit could share most of its pieces with the one before; that has not been checked.
  • Dev's growth per edit, on its own slides, today.
  • The sidebar's own cost beyond its outline: drawing its rows. The probe times only the outline it reads.
  • An undo in the browser with evaluation and drawing: Node runs no worker and builds no view or DOM.
  • Sharing across the worker boundary, which an undo also crosses when it re-evaluates (^ticket(666)).

What next

  1. Make the outline's build touch only the definitions that changed, so that neither an edit with the sidebar shown nor an undo pays a walk of every definition: about {{view_ol_3200}} ms per edit and {{outline_3200}} per undo at 3,200 definitions. A cheaper first step for undo alone: keep the outline with its undo entry.
  2. Put the fix for the second syntax pass on #2635 (9df1b2601e), once its CI is green, and measure an undo again in the browser.
  3. Measure space against size on #2635 in Node: the heap after a forced collection with 0, 1, 10 and 100 undo entries, at each size, compacted and whole.
  4. Decide dev: a small PR with the compaction and an always-on cap now, or wait for #2469 to bring them (the 2026-10-15 call was to wait).
  5. Try the top level as a balanced tree of definitions (^report(36)'s Figure 5). A snapshot of a persistent tree is its root: it shares every node the edit did not touch, so an entry would keep O(log n) new nodes, and an undo could be a swap of roots, with its derived data kept.
  6. Time an edit and an undo in the browser on Full Body, with evaluation and drawing.

For the meeting

  • Dev's undo history still keeps every edit's whole editor state. Should dev get the compaction now, or with #2469?
