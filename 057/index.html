What the Livelits PR Compiles

Matthew Hammer asked, on 2026-11-18, to what extent hazelgrove/hazel#2819 uses hazel-jit: for livelit views only, or for anything else. This is the answer, read from the pull request's code, with a section for each use, written for his conversation with Cyrus Omar today about what makes livelits responsive, and how it reaches dev; the team's next mergeathon is tomorrow, 2026-11-19.

Outline#

  1. In short: in the app, hazel-jit serves livelits only, four ways; outside it, a command, tests and a browser check.
  2. In the app: livelit views, livelit updates, the slide's whole run, and the worker's request held.
  3. Outside the app: the command line, a measuring page, the tests, the Firefox check.
  4. What #2819 does not have: everything since the morning of 2026-11-09, the step budget and the consistency check among it.
  5. What makes livelits responsive: the ten changes ^report(52) ranked, which of them are hazel-jit, and which #2819 holds.
  6. Reaching dev: ^report(52)'s nine increments, brought up to date; for tomorrow's mergeathon; and what to decide with Cyrus.

In short#

In the running app, #2819 uses hazel-jit only for livelits, but for more than their views: their updates, and each slide's whole run, which it compiles only to draw livelits sooner. The program's result, probes, tests and the stepper always come from the interpreter. Outside the app it adds a command, tests and a browser check. Read from the pull request's code at c419e01559 (2026-11-09), behind the Compiled views setting, which is on by default there.

  1. Livelit views. A livelit's view function is compiled and run on the page's own thread with the livelit's model, and its answer drawn straight into the page, never made into a Hazel value; handlers that take a payload run compiled too.
  2. Livelit updates. The definition's update function is compiled too: on an action, a new model comes back as a diff against the old one; any other answer goes to the interpreter.
  3. The slide's whole run. The slide's program is compiled once, each livelit's model a parameter; at a livelit's event the whole program runs as JavaScript with the new model, and every livelit is drawn from that run before the worker's run returns. Its answer is used only to draw livelits.
  4. The worker waits. When the compiled run has answered an event, the page holds its request to the interpreter for 400 ms, so a drag costs the worker one run, after its last step.

Outside the app: ./hazel jit FILE.hz to compile a file, check it against the interpreter, and count what it does not compile; a page that times values carried into JavaScript; the HazelJit tests; and the Firefox check that drives the slides and times them. Not in #2819: all the work since its head on the morning of 11-09, which is on the prototype branch (build 50, hazelgrove/hazel#2817).

In the app#

All four uses sit behind one setting, Compiled views (jit_views, on by default on #2819), and each falls back to what the page did before hazel-jit when it meets something it does not compile. The setting sets HazelJitValue.enabled; turned off, nothing is compiled, and every livelit is drawn through the interpreter's run, as on dev.

1. Livelit views, compiled#

A livelit's view, a Hazel function from its model to HTML, is compiled once per definition and called on the page's own thread whenever the livelit is drawn: 3.0 ms a render of the Witch's picture against 87 ms through the interpreter. (^report(46), in Firefox; ^report(52), ingredient A4.)

  • How. LivelitProj asks HazelJitValue.view_of_def for the definition's compiled view, and call_view runs it on the model, carried into JavaScript. HazelJitDOM.go draws the answer, the JavaScript values the compiled code made, straight into the page's virtual DOM: every view command (Pure, Bind, whose continuation is the compiled function, Editor, EvalSplice, ResultView) and every element, attribute and handler, as HazelDOM draws them from a Hazel value.
  • Handlers. A handler crosses into Hazel only when its event comes: a click's message is carried back then; a handler that takes a payload is the compiled function, called on the payload in JavaScript, and only its answer, the message, carried back.
  • When it gives up. A form hazel-jit does not compile, or an answer that is not well formed, raises Unsupported, and the page draws through Hazel as before. So do apps whose messages transform the program's syntax.
  • Measured. The Witch's picture: 87 ms a render on the interpreter, 3.0 ms compiled (^report(46)). A Polygons render in Node: 14.1 ms to 0.38 (^report(45)). In a drag, a livelit drawn from JavaScript takes about 1 ms, against 4.6 with nothing compiled (builds 30 to 39, ^report(52)).
  • Code. 606 lines added outside the compiler, and the compiler's own 4,328 at that time (^report(52)'s count).

2. Livelit updates, compiled#

The definition's update, compiled, runs on the model and the action; when it answers Pure(new model), the new model comes back as a diff against the one it was given, so every part it did not change stays the very same Hazel value. Any other command goes to the interpreter. (^ticket(715), ^report(45)'s second step; HazelJitValue.call_update, called from LivelitProj.)

  • Why a diff. Carrying a whole answer back costs time in its size. The compiled code builds a new model functionally, so a part it did not touch is the same JavaScript object, and the diff stops there without looking inside; the patch keeps the old Hazel value for it.
  • When it gives up. A command other than Pure, or a diff that does not fit the model's type, is an error, and the update runs on the interpreter as before.
  • Measured. Not on its own in ^report(45) to ^report(52), which timed slider steps and drags; a slider's step reaches the model through the compiled run (below) more than through the update.

3. The slide's whole run, compiled#

This is what makes a slider's step show in about 20 ms: the slide's program, compiled once with each livelit use's model as a parameter, answers a livelit's event in 2 to 3 ms as JavaScript, and every livelit draws from that answer before the worker's run comes back. (^ticket(722), ^report(52)'s ingredients A2 and B3; HazelJitRun.)

  • How. The page tells HazelJitRun the program it draws livelits from (note_program, from ProjectorView); it is compiled soon after, or at the first event that needs it. At an event (step), the program runs with the new model given to its parameter, no new code, and each livelit's view answer is kept for the page to draw straight from JavaScript.
  • Compiled once. A new program is compared with the compiled one with the models left out (erase); while only models change, the compiled function is kept. Comparing takes about 1 ms a step (build 17); compiling again took 126 to 141 ms (build 8).
  • When it gives up. A form hazel-jit does not compile becomes a stub that throws if the run reaches it (HazelJit.survey); then, or on any other failure, there are no answers, and the page draws from the run's samples as before.
  • Measured. A step's picture 1.33 to 1.71 s on build 3, 208 to 236 ms on build 5 when the run was compiled (^report(49)); in Node, a slider's step 684 ms on the interpreter, 2.3 to 2.5 ms compiled (^report(45)).
  • What rides on it. Two changes that need the compiled run to have answered: draw first, edit after the paint (A3: the step's picture 152 to 195 ms on build 11, 19 to 24 on build 12), and a drag redraws only what changed (A5: a 3-second drag 9.8 fps on build 5, 57.6 on build 12).
  • Its answer is only for livelits. The result panel, probes and tests come from the interpreter's run in the worker, as always.

4. The worker's request, held#

When the compiled run has just answered a livelit's event, the page holds the request it would send the worker for 400 ms, replacing it by any newer one, so a drag costs the worker one run, after its last step, not one a step. (^report(50)'s fourth step; WorkerClient.hold_if_answered, asking HazelJitRun.take_answered.)

  • Why. The page's livelits are already drawn from the compiled run; the worker's answer would only draw them again, to the same picture, and the page would spend each step decoding it.
  • The cost. Probes, tests and every other cell still get the worker's answer, later: 400 ms after the last step, plus the worker's run.

Outside the app#

Four tools, none of which a user of the app meets.

  • The command line: ./hazel jit FILE.hz compiles a file, with --check runs it both ways and compares, and counts by reason the forms it would not compile (HazelJit.survey; src/CLI/Cli.re).
  • A measuring page: the data experiment times carrying a value into JavaScript (DataExperiment, HazelJitValue.to_js).
  • The tests: test/Test_HazelJit.re, each compiled program run both ways and its answer compared with the interpreter's.
  • The Firefox check: .github/workflows/jit.yml and scripts/jit_slides.py drive six slides in Firefox on GitHub's machines and time each slider step and drag, compiled views on and off. ^report(52) calls it the ruler.

Reaching dev#

User-defined livelits are not on dev yet, and #2819 is 1,680 commits ahead of dev, the whole livelits stack with hazel-jit on it; so hazel-jit's livelit uses reach dev after the livelits do, in ^report(52)'s increments, carrying the correctness work done since. Livelits going into dev was settled with Cyrus on 2026-11-05; how, in what pieces and in what order with hazelgrove/hazel#2469, is still open. dev has LivelitProj today, for the built-in livelits; the user-defined ones, whose views and runs hazel-jit compiles, come with hazelgrove/hazel#2597's stack.

To decide with Cyrus#

  1. Which comes first for responsive livelits? Our lean: the page work that needs no compiler (A1, B1, B2, B4, B5) lands with or right after the livelits, as it helps every edit; then compiled views; then the compiled run. The run is what makes a step show in 20 ms; views alone make drags and redraws fast.
  2. Compiled views on dev: on by default, or behind a setting that starts off? Our lean: off at first, on once the consistency check and the step budget have run a while in CI.
  3. Is the step budget a condition for compiled code on the page's thread? Our lean: yes; it is Cyrus's concern of 11-13, and #2819 has none.
  4. What becomes of #2819? Our lean: close it in favor of the increments, keeping the preview build for trying.
  5. The compiler before livelits? Our lean: yes, as a library with its check in CI and nothing a user sees, so its review is not tied to the livelits' landing.
