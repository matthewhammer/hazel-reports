Scripting a JavaScript App in Hazel

Messed Up Dress Up, a game for kids written in plain JavaScript, lets its players rewrite some of the game's rules in Hazel while they play. It does that through hazeljs, Hazel packaged as a JavaScript library. This report explains how the game does it, and how a JavaScript developer could do the same in their own program: the pattern, the steps, a worked example in another domain, run in Node, and what it costs today. Matthew asked for it on 2026-11-06, for his meeting with Cyrus on 2026-11-11 (^report(42), the agenda, item 5). The first readers in mind are a group in Cambridge who simulate Petri nets with JavaScript tools of their own, so the example is a Petri net. As of 2026-11-06, with hazeljs 0.0.4 from npm.

The pattern

Your app keeps its state and its screen, and Hazel only decides. On an event, the app calls a Hazel function with a typed view of its state and the event, and carries out the command the function returns, which is plain data (Figure 1).

Many JavaScript programs are organized around events: a click, a key, a timer, a message. In this pattern, some of those events are handed to a function written in Hazel. The JS side builds two values: one describing what happened (the event), and one describing what the handler may see (a view of the app's state). It calls the Hazel function with both, and gets back a value describing what to do (a command). Hazel never touches the page or the app's objects; its answer is data, and the app acts it out. We call a program built this way a Hazlet; Messed Up Dress Up is the first one (^report(39)).

Why write a handler in Hazel at all? Three reasons, each of which the game uses:

  • Types for the vocabulary. The app declares what a rule is told and what it may answer, as Hazel types. A rule that answers with the wrong thing is a type error before it ever runs, and the error names the module it is in.
  • Feedback in the middle of an edit. Hazel analyzes and runs programs that are not finished: a hole (?) is a part not yet written, and Hazel counts holes and unfinished brackets per module rather than failing. An editor can show the person writing a rule exactly what is wrong, and where, at every keystroke.
  • Rules that people other than the app's developers can change, without access to the app's code: in the game, kids rewire the castle's traps.

How Messed Up Dress Up does it

In the game's 📜 Scripting tab, the game's logic for five rooms is a Hazel program made of modules: 📚 Common, helpers every room can use, then one module per room. A red lever pulled in the castle's trap room is the event Pull(L). The game builds the room's view of its state, a Globals record (the levers, how the pits are wired, the game's random draws, and more), and calls TrapRoom.on_event. The rule answers a Cmd, a chain of commands such as Flip(L, SetPit(0, true, Done)): flip the lever, then open pit 0. The game carries out each command the way its own code would, with its animation.

All of it is in one file of the game, js/25-scripting.js (read at the game's 0.0.491). The pieces, in the order an event meets them:

Doing the same in another app: our Petri net example

Six steps: declare the vocabulary as Hazel types; let users write modules against it; build the program with Hazel.runProgram; call the Hazel function only while the build is ok, and your own JS handler otherwise; carry out its commands; and show its errors by module.

To see what a second app takes, we did it ourselves, as another user of hazeljs would: we took the pattern out of the game and built a small app around a Petri net, in a repository of its own, matthewhammer/hazeljs-petri-example (version 0.0.1). Its rules and its net are files (rules/*.hz, net.json), read both by its page and by a Node script, so the same rules run in both. This is what we did, in the order we did it, and what tripped us; the code is cut from the files that ran. The next section runs the result on this page.

  1. We installed hazeljs. npm install hazeljs, then import Hazel from "hazeljs" in Node; in the page, <script src="https://cdn.jsdelivr.net/npm/hazeljs@0.0.4/hazel-lib.js">, which defines window.Hazel. We pinned the version: the package is a prototype, and its API may change in any release.

  2. We wrote the vocabulary first, as Hazel types in the program's preamble (rules/preamble.hz), which every module sees: what a rule is told (Net), what can happen (Event), and what a rule may answer (Cmd). The answer is a chain of commands, each with the rest after it, ending in Done, so the page can walk it in order, log it, and refuse a command it does not know.

    {{PREAMBLE}}

    Sum types go here, not inside a module: a type's constructors are in scope only where the type is. This is also where another group's nets would differ first: tokens that carry data, weights, a guard, a clock.

  3. We split the rules into modules, as the game does: helpers in Common, the handler in Rules, each a text (and a file). A module's text is its members, with no in; one module sees the ones before it, by name (Common.fire).

  4. We built the program with Hazel.runProgram, once per change of text. The tail is what the program gives back: here, the handler, held to its type.

    {{JS_BUILD}}

  5. We kept our own JS handler, and call Hazel's only while the build is ok; ours answers while a rule has errors, holes or unfinished brackets. Hazel still runs a program around its errors, so the page can log what Hazel would have said, but where an error stopped it, the value is a printout ({hazel: "..."}), not something to act on.

    {{JS_FALLBACK}}

  6. We acted out the commands, and showed the errors by module. Values cross the boundary as plain JS: a labeled tuple is an object, a list an array, a constructor {tag, value}, a function a JS function. The page keeps control: it refuses a command that would take a place below zero, and one it does not know.

    {{JS_PERFORM}}

What tripped us. Three things, none of them in the game's way of doing it, which is why a second app was worth building:

  • Key order, a bug in hazeljs 0.0.4. We first passed the net's view as {transitions, marking, draw}, and every answer came back {hazel: "..."}. When a JS object's keys come in another order than its Hazel type's fields, and a field is a list, the value gets stuck at the type's annotation. So we build the view in Net's own order, {marking, transitions, draw}, until the library converts by label.
  • Hazel's editor frames are particular about where they run: they take messages only from a few sites (localhost and this one), so the app has to be served from one of them, and a frame off the screen does not draw, so it reports its height as 0 until it is scrolled to.
  • No randomness or clock in Hazel: the page passes a random draw in with the view, as the game passes its draws, which also makes every call repeatable.

For your own kind of Petri net. Most of what makes one group's nets differ from another's goes in three places: the vocabulary, the helpers, and the net's file. Coloured nets (tokens that carry data, which some groups call types): a place's tokens become a list of Hazel values of that place's type, and a transition's guard and output become Hazel functions, so Hazel's type checker checks the colours as they are written. Weights, inhibitor arcs, priorities, timing: a field in net.json, a case in Common, a word in the vocabulary. And which enabled transition fires is the rule's choice (Step), so a scheduling policy is a few lines of Hazel, swapped without touching the app. The repository's plan has what comes next for it, more nets among them, and a site of its own.

A worked example: a Petri net

It carried over to a new domain on the first try. The firing rule is about 30 lines of Hazel in two modules, and it ran as written; in 2,000 random steps, the two processes were never both inside the shared section (the runs). The net runs on this page too, its rules in Hazel's own editor, every edit built by hazeljs from npm (try it).

The net is the classic small one for mutual exclusion: two processes, each idle or busy, and one lock. To become busy, a process takes the lock; to become idle again, it gives the lock back (Figure 3). The JavaScript app keeps the marking (the tokens in each place), and draws it. The rule decides what an event does: Fire(i) fires transition i if it can, and Step fires one of those that can, chosen by a random draw the app passes in.

  • In Rules, change fire_at(n, i) to fire_at(n, "one"). The status lists the type error by module, and the log shows the page's JS answering until you change it back.

What it costs

A call costs about {{call_med}} ms, against {{js_us}} µs for the same handler in JS: fast enough for each click, but not yet for a simulator's inner loop. Building the program takes {{build_lo}} to {{build_hi}} ms, and rebuilding after an edit {{rebuild_lo}} to {{rebuild_hi}} ms (Node, three runs).

{{TABLE_COST}}
  • A call is {{call_lo}} to {{call_hi}} ms (medians per run): the view and the event converted into Hazel values, the rule evaluated by Hazel's interpreter, the command converted back. That fits well inside a click or a key, and inside one frame of an animation; the game measured about the same, 3.5 ms of a 13.7 ms lever pull (^report(39)). It does not fit a simulator's inner loop that fires millions of transitions: 2,000 steps took about 7 s of Hazel here.
  • The annotation in the tail is not the cost. ^report(25) found that a call into Hazel re-checked a function's type annotation on every call, which #2681 removes (not in 0.0.4). Building with the tail unannotated changed nothing measurable here (the table's fourth column). Where a call's time goes in this example is not measured yet; ^report(25)'s other finding, a floor for crossing the boundary that grows with the argument, is the likely part, since every call here passes the whole net.
  • Building takes {{build_lo}} to {{build_hi}} ms, and rebuilding after an edit {{rebuild_lo}} to {{rebuild_hi}} ms, about the same whether a module changed or not. Fine for a build after a pause in typing; too slow for every keystroke on the main thread, which is why the game rebuilds only once typing has paused for 600 ms.
  • The package is 2.8 MB unpacked, about 650 kB compressed: one file, Hazel itself compiled to JS.

Making the calls themselves faster is the subject of an experiment on the same agenda: compiling Hazel functions to JavaScript (^report(42), item 2).

Limits today

  • A prototype. hazeljs is at 0.0.x, built from a draft library on two of Hazel's pull requests, #2711 and #2719, not from Hazel's main branch. The plan is for it to track that branch; a pull request to Hazel's README says so (#2812).
  • No editor in the package. It analyzes and runs text. Hazel's own tile editor in a frame, as the game and this page use it, comes from a branch build of Hazel, and takes messages only from a few sites. Planned: the editor in the package.
  • Key order matters, by mistake. An object whose keys are in another order than its type's fields gets stuck when a field is a list (what tripped us). To be fixed in the library.
  • Messages written for Hazel's developers, which an app will want to rewrite, as the game does.
  • No undo, and no history, in the library: the app keeps its own. Planned: undo in the editor.

What next

  1. Ask the group in Cambridge, through Cyrus, what their tools would want a Hazel rule to decide, and what their nets look like (sizes, colours, timing), before building more of the example.
  2. Measure where a call's 3 ms goes in this example: the boundary's conversions against the rule's own evaluation, and how both grow with the net's size.
  3. Once hazel-jit, the compiler of Hazel to JavaScript being designed for livelits' views (^report(42), item 2), can compile this rule: put the JS it makes beside the page's own handler, the JS a person would write, and compare the two, the code side by side and the time per call. How close does the compiled rule come to the hand-written one?
  4. A small helper in hazeljs for the pattern itself: give it the preamble, the modules and the handler's type, and get back a handler that falls back to yours while the rules are not ready.
