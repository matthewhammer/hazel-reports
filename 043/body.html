Scripting a JavaScript App in Hazel

Messed Up Dress Up, a game for kids written in plain JavaScript, lets its players rewrite some of the game's rules in Hazel while they play. It does that through hazeljs, Hazel packaged as a JavaScript library. This report explains how the game does it, and how a JavaScript developer could do the same in their own program: the pattern, the steps, a worked example in another domain, run in Node, and what it costs today. Matthew asked for it on 2026-11-06, for his meeting with Cyrus on 2026-11-11 (^report(42), the agenda, item 5). The first readers in mind are a group in Cambridge who simulate Petri nets with JavaScript tools of their own, so the example is a Petri net.

Short answers. As of 2026-11-06, with hazeljs 0.0.4 from npm.

  1. The pattern: your app keeps its state and its screen, and Hazel only decides. On an event, the app calls a Hazel function with a typed view of its state and the event. It then carries out the command the function returns, which is plain data (Figure 1).

  2. Six steps. Declare the vocabulary as Hazel types. Let users write modules against it. Build the program with Hazel.runProgram. Call the function only when the build is ok, and your own JS handler otherwise. Carry out its commands. Show its errors by module (the steps).

  3. It carries over to a new domain on the first try. A Petri net's firing rule is about 30 lines of Hazel in two modules, and it ran as written. In 2,000 random steps, the two processes were never both inside the shared section (the example).

  4. A call costs about {{call_med}} ms, against {{js_us}} µs for the same handler in JS. That is fast enough for each click, but not yet for a simulator's inner loop. Building the program takes {{build_lo}} to {{build_hi}} ms, and rebuilding after an edit {{rebuild_lo}} to {{rebuild_hi}} ms (Node, three runs; Figure 4).

The pattern

Many JavaScript programs are organized around events: a click, a key, a timer, a message. In this pattern, some of those events are handed to a function written in Hazel. The JS side builds two values: one describing what happened (the event), and one describing what the handler may see (a view of the app's state). It calls the Hazel function with both, and gets back a value describing what to do (a command). Hazel never touches the page or the app's objects; its answer is data, and the app acts it out. We call a program built this way a Hazlet; Messed Up Dress Up is the first one (^report(39)).

Why write a handler in Hazel at all? Three reasons, each of which the game uses:

  • Types for the vocabulary. The app declares what a rule is told and what it may answer, as Hazel types. A rule that answers with the wrong thing is a type error before it ever runs, and the error names the module it is in.
  • Feedback in the middle of an edit. Hazel analyzes and runs programs that are not finished: a hole (?) is a part not yet written, and Hazel counts holes and unfinished brackets per module rather than failing. An editor can show the person writing a rule exactly what is wrong, and where, at every keystroke.
  • Rules that people other than the app's developers can change, without access to the app's code: in the game, kids rewire the castle's traps.

How Messed Up Dress Up does it

In the game's 📜 Scripting tab, the game's logic for five rooms is a Hazel program made of modules: 📚 Common, helpers every room can use, then one module per room. A red lever pulled in the castle's trap room is the event Pull(L). The game builds the room's view of its state, a Globals record (the levers, how the pits are wired, the game's random draws, and more), and calls TrapRoom.on_event. The rule answers a Cmd, a chain of commands such as Flip(L, SetPit(0, true, Done)): flip the lever, then open pit 0. The game carries out each command the way its own code would, with its animation.

All of it is in one file of the game, js/25-scripting.js (read at the game's 0.0.491). The pieces, in the order an event meets them:

Doing the same in your app

Each step below shows the worked example's code (next section), cut from the file that ran.

  1. Install. npm install hazeljs, then import Hazel from "hazeljs" in Node; or, in a page, <script src="https://cdn.jsdelivr.net/npm/hazeljs@0.0.4/hazel-lib.js">, which defines window.Hazel. Pin the version: the package is a prototype, and its API may change in any release.

  2. Declare the vocabulary as Hazel types, in the program's preamble, which every module sees: what a rule is told, what can happen, and what a rule may answer. Make the answer a chain of commands, each with the rest after it, ending in Done: the app can walk it in order, log it, and refuse a command it does not know.

    {{PREAMBLE}}

    Declare the sums here, not inside a module: a type's constructors are in scope only where the type is.

  3. Let your users write modules against it, each a text: helpers in one, the handler in another. A module's text is its members, with no in; one module sees the ones before it, by name (Common.fire).

  4. Build the program with Hazel.runProgram, once per change of text. The tail is what the program gives you: here, the handler, held to its type.

    {{JS_BUILD}}

  5. Call the handler only when the build is ok, and keep your own JS handler for the rest of the time, while a rule has errors, holes or unfinished brackets. Hazel still runs a program around its errors, so you can log what it would have said, but where an error stopped it, the value is a printout ({hazel: "..."}), not something to act on.

    {{JS_FALLBACK}}
const handlerOf = b => b.ok ? b.handler : jsHandler;

  6. Carry out the commands, and show the errors by module. Values cross the boundary as plain JS: a labeled tuple is an object, a list an array, a constructor {tag, value}, a function a JS function.

    {{JS_PERFORM}}

Two more things the game learned. Hazel has no clock and no randomness: pass them in as part of the view (the game's draws, the example's draw), which also makes every call repeatable. And keep the boundary in one place: if your app's own state uses strings where the rules use sums, convert both ways in one wrapper, as the game's scriptTyped does.

A worked example: a Petri net

The net is the classic small one for mutual exclusion: two processes, each idle or busy, and one lock. To become busy, a process takes the lock; to become idle again, it gives the lock back (Figure 3). The JavaScript app keeps the marking (the tokens in each place), and draws it. The rule decides what an event does: Fire(i) fires transition i if it can, and Step fires one of those that can, chosen by a random draw the app passes in.

What it costs

{{TABLE_COST}}
  • A call is {{call_lo}} to {{call_hi}} ms (medians per run): the view and the event converted into Hazel values, the rule evaluated by Hazel's interpreter, the command converted back. That fits well inside a click or a key, and inside one frame of an animation; the game measured about the same, 3.5 ms of a 13.7 ms lever pull (^report(39)). It does not fit a simulator's inner loop that fires millions of transitions: 2,000 steps took about 7 s of Hazel here.
  • The annotation in the tail is not the cost. ^report(25) found that a call into Hazel re-checked a function's type annotation on every call, which #2681 removes (not in 0.0.4). Building with the tail unannotated changed nothing measurable here (the table's fourth column). Where a call's time goes in this example is not measured yet; ^report(25)'s other finding, a floor for crossing the boundary that grows with the argument, is the likely part, since every call here passes the whole net.
  • Building takes {{build_lo}} to {{build_hi}} ms, and rebuilding after an edit {{rebuild_lo}} to {{rebuild_hi}} ms, about the same whether a module changed or not. Fine for a build after a pause in typing; too slow for every keystroke on the main thread, which is why the game rebuilds only once typing has paused for 600 ms.
  • The package is 2.8 MB unpacked, about 650 kB compressed: one file, Hazel itself compiled to JS.

Making the calls themselves faster is the subject of an experiment on the same agenda: compiling Hazel functions to JavaScript (^report(42), item 2).

Limits today

  • A prototype. hazeljs is at 0.0.x, built from a draft library on two of Hazel's pull requests, #2711 and #2719, not from Hazel's main branch. The plan is for it to track that branch; a pull request to Hazel's README says so (#2812).
  • No editor in the package. It analyzes and runs text. Hazel's own tile editor in a frame, as the game uses it, comes from a branch build of Hazel.
  • Messages written for Hazel's developers, which an app will want to rewrite, as the game does.
  • No undo, and no history, in the library: the app keeps its own.

What next

  1. Ask the group in Cambridge, through Cyrus, what their tools would want a Hazel rule to decide, and what their nets look like (sizes, colours, timing), before building more of the example.
  2. Measure where a call's 3 ms goes in this example: the boundary's conversions against the rule's own evaluation, and how both grow with the net's size.
  3. Put the example in a web page: the net drawn, the two modules in editors, the errors under each, and the app's JS answering while a rule is unfinished.
  4. Try the example's rule with hazel-jit, the compiler of Hazel to JavaScript being designed for livelits' views (^report(42), item 2), as a second measure of the best case.
  5. A small helper in hazeljs for the pattern itself: give it the preamble, the modules and the handler's type, and get back a handler that falls back to yours while the rules are not ready.
