What Still Falls Back

hazel-jit compiles Hazel to JavaScript, and wherever it compiles a program it now gives the interpreter's answer, checked in CI (report 054, The same answers, checked in CI). This report starts from that check, on build 50, and turns to the other side of it: every case where the interpreter still does the work, because hazel-jit does not compile the code or stops part way and falls back. It sorts those cases four ways: limits to lift now; decisions still open; holes, a project for John, kept apart from the rest; and stuck terms, later, which share machinery with holes. It also sets out the two uses of compiled code, livelit views and mixed mode, and how counting the interpreter's steps answers the worry about programs that never end.

Two uses, and programs that never end

hazel-jit began as a way to draw livelits within a frame, on the page's own thread, and is becoming a way to run any complete function, called by the interpreter in its worker. A compiled run that never ends cannot freeze the page today, because its stack overflows within a millisecond or its budget stops it; once compiled code counts the interpreter's own steps, it will also stop where the interpreter stops, so even a run out of steps gives the same answer.

The first use: livelit views

A livelit is drawn by a view function written in Hazel, over the livelit's model. Dragging a slider changes the model and calls for a new picture at every step. Hazel's interpreter runs in a web worker, and a run there, with the round trip, takes longer than a frame on a large slide. So hazel-jit compiles each view function once, with the model as a parameter, and the page runs the JavaScript on its own thread at each step: a step of the Witch's slider in 2 to 3 ms (report 050), and 6.5 ms a frame, about 154 fps, over a whole drag on build 50 (report 054, What it all costs). Report 052 added a slide's whole run, compiled. The compiled answer is a preview: the interpreter still runs every program, and its answer is the result, with the probes, the tests and the result panel. When hazel-jit does not compile something, or a compiled run stops, the page waits for the interpreter, as it did before hazel-jit.

The latest idea: mixed mode, for all evaluation

Mixed mode (ticket 766, chosen after the meeting of 2026-11-13) keeps the interpreter in charge of every program, so holes, probes and the stepper work as they do, and gives its complete functions compiled speed. Each function bound at the program's top, or in a module there, whose whole type is declared (let f : A -> B = fun ...) is compiled, and the interpreter calls it as it calls a builtin: the argument goes into JavaScript, the compiled function runs, and its answer comes back by the declared type. If the call stops for any reason, that call alone falls back: the interpreter applies its own closure to the same argument. Here the compiled answer is the answer, not a preview. It runs in the tests only, so far, with no setting in the app. On build 50, in Node:

Programs that never end

Cyrus Omar's concern, at the meeting of 2026-11-13: "We need a way to limit compiled hazel functions that diverge --- we need a step limit. esp if we continue to optimize by including certain jit-compiled hazel functions into the main thread". The interpreter has its own limits (report 054: a 20-second timer and 100 million transitions), but compiled code does not run through it.

Today, a budget of calls and time. (Ticket 763, on the prototype since build 46.) Hazel has no loops, so a program that never ends recurses forever. Every compiled function counts its calls, and every 16,384 calls reads the clock; a run past its budget stops, and the interpreter's run answers. Livelit views have 50 ms or 50 million calls a run, and a mixed-mode call a second or 50 million calls. Endless recursion turned out to be the smaller risk: JavaScript has no tail calls, so it overflows the stack in about a millisecond, and that error is caught like any other. The real risk is a run that ends, but late (fib(45)), and the clock catches that. In Node the counter costs 11 to 26%, and 20 to 33% with the clock. So a compiled run holds the page's thread for about its budget at most: the clock is read every 16,384 calls, and a builtin call, once begun, runs to its end. What it does not give is the interpreter's answer: a run the interpreter would finish, compiled code may give up on, and the reverse, because the two count different things.

Next, the interpreter's own steps. The meeting asked compiled code to count the steps the interpreter would take (ticket 767), and report 054 found it can: step counts and probes, as the interpreter's. hazel-jit translates construct by construct and runs in the interpreter's order, and most constructs take a fixed number of steps of their own, so the compiler adds the right number for each straight run of code, about what today's call counter costs. Then:

  • One limit, in one unit. The budget becomes the interpreter's step limit (decision 9, answered 2026-11-13). A program that never ends stops at the same step both ways, and so does a long one, so "ran out of steps" is part of the same answer, and the consistency check can cover it as it covers values.
  • In mixed mode, a compiled call adds its steps to the interpreter's count, so a program's count is the same mixed or not, and the interpreter's limit stops it wherever its steps are taken. Mixed mode is to run in the worker (decision 6's lean), where a long run makes results late but freezes nothing.
  • On the page's thread, steps alone do not bound time: a step that calls a builtin on a long list or string is one step, and a frame is 16.7 ms. So the lean is to keep the clock there too, set by the frame, beside the step limit (decision 20). If the clock stops a view, the page waits for the interpreter, whose answer is the same, as now.
  • What it cannot do is tell a program that never ends from one that ends late; no limit can. A step limit bounds both, and the same way in both, which is what the same answers need.

The work: casts carried by functions, and the interpreter's own bookkeeping, are where counts need care, and a check in CI compares each evaluator program's count with the interpreter's (report 054 lists the steps). Probes follow from the counts.

Limits to lift

Of the evaluator's 313 programs, compiled code does not handle {{not_handled}}, and none of them meets a limit worth lifting: they are holes, ill-typed tests, unbound names and stuck terms, which the next sections take up. The limits that cost the most are elsewhere: tests in the slides (28 of 129), static errors anywhere in a program, the stack's depth, and how far mixed mode reaches. The aim is to run compiled wherever the answer can be the interpreter's, and fall back only where it cannot. Holes and stuck terms are kept out of this section on purpose, so that work on them can go on apart.

At run time: the stack, and the budget

  1. The stack. JavaScript's stack holds thousands to tens of thousands of calls, depending on the browser, where the interpreter keeps its stack on the heap. A List.map over 100,000 elements works in the interpreter and overflows compiled; today that falls back, correct but slow. The common case is the list builtins, which the runtime could write as loops; a general fix (a trampoline, or code that keeps its own stack) costs every call.
  2. The budget. A run past its budget falls back, correct and slower. With step counts it becomes the interpreter's limit (above), and for a view, a frame's clock too.

How far mixed mode reaches

  1. Whole types declared. 29 of the evaluator's functions were left out because only part of their type is declared. The elaborated type of any function would reach more, but it can hold unknowns, and the answer is converted back by that type (decision 3). Declaring whole types pays in the interpreter too: 5 to 7 times cheaper a step (ticket 762).
  2. Across modules. A module's member that calls another module's member is not compiled yet, so the I Ching's rules do not compile whole.
  3. The crossing. Converting values in and out costs more than a one-line function saves (500 calls of sq, 21.8 ms mixed against 20.6 ms interpreted, build 50). Convert a large value once and remember it, and leave very small functions to the interpreter.
  4. In the app. No setting yet, and no hook where the worker evaluates.

What the interpreter records

Tests (above), probes and the stepper. A probe shows the values that passed through it; today a probe always shows the interpreter's run, correct and never faster, and in mixed mode a compiled function's own probes record nothing (decision 5: until step counts land, a probe should take its function out of the compiled set). With the interpreter's step counts, compiled code can make the interpreter's own samples, with two limits (report 054, steps). The stepper shows the terms between steps, and compiled code has none, so it stays the interpreter's, by rule.

Holes in compiled code

Holes are John's project, drawn so that it touches as little of the rest as it can: values with holes cross into compiled code and out again unopened (report 055), and code with holes stays with the interpreter, by the rule of 2026-11-13. The only thing it shares with the limit work is one contract: compiled code stops with $R.indet, and that call falls back.

Where holes stand. No code with a hole or a type hole is compiled: 25 of the evaluator's programs, and 57 of the slides' as the first thing they meet (above). That is the rule, and it stays: the interpreter evaluates around holes, and its indeterminate results are the point of them. Where holes meet compiled code is mixed mode, where a value with a hole in it arrives as an argument: today to_js cannot carry it, so the call falls back whole, even when the function never looks at the hole (swap(1, ?), the length of [1, ?, 3]).

The project (report 055, The idea, ticket 769): carry such a value as an opaque JavaScript object; let compiled code store it, pass it and return it; stop the run wherever compiled code would look inside it; and give back the very term that went in. JavaScript will not stop by itself (a pattern test on an opaque object is simply false), so the checks have to be written, and the lean is a second, checked version of a function, compiled the first time a hole arrives, so that calls without holes cost what they cost today.

Its edges. To keep it apart from the limits Matthew is lifting:

  • Its own branch, from the newest prototype build, merging each new build in (no rebases of shared branches).
  • Its files: the boundary in HazelJitValue.re (to_js, of_js, the table of opaque terms); one runtime helper for the check, in HazelJit.re's runtime; the checked version as a flag on code generation; mixed mode's choice of version in HazelJitMixed.re; and its tests in a group of their own beside the mixed-mode tests.
  • Where it meets the limit work: the checks sit in code generation for patterns (the empty list's v === null and a constructor's v.c === ..., HazelJit.re lines 570 and 618 on build 50), equality, arithmetic and a tuple's parts. The limit work touches patterns too (a splice pattern, above). So each check is one call to the runtime helper, written at those sites and nowhere else, and Matthew tells John before reshaping them.
  • Not in it: code with holes, step counts, the limits above, stuck terms (below), and how hazel-jit reaches dev.
  • Measured by what already runs: the mixed sweep counts calls that fall back because an argument does not carry (one on build 50), the timings above come from the quick tests on every push, and the Witch slide's frame time from the Firefox check (on the prototype branch's pushes, or started by hand), so the checks' cost shows.

Before code: the four questions of report 055 (decisions 22 to 25), with Cyrus and Matthew, first of all where the work lives. A warm-up PR to dev, independent of all this, is decision 17's float printing (hazelgrove/hazel#2831).

Later, a second step that waits on stuck terms. Opaque values fall back when looked inside: inc(?) still goes to the interpreter, to make ? + 1. Compiling it, so that the run goes on around the hole as the interpreter's does, means making that term in compiled code, which is the next section's machinery.

Stuck terms in compiled code

Where the interpreter's answer would hold a stuck term, compiled code stops, and the interpreter's run answers: correct, and costing speed only when it happens. Making those terms in JavaScript instead, and evaluating around them, takes the same machinery as compiling around holes, so it is one piece of work for both, Matthew's, after more of the limits.

Where compiled code stops today (build 50; each stop is $R.invalid or $R.indet in HazelJit.re's runtime, and in the evaluator's tests only the two stuck projections end this way):

{{tab_stops}}

Two more kinds of stuck term are kept out by rule rather than stopped at: a failed run-time check in an ill-typed program (25 evaluator programs; the page compiles no program with a static error), and a free variable (24). Overflow is the example to start from: since 2026-11-16 an SInt result past 32 bits is an error, a stuck term, in the interpreter (report 054, Overflow). Compiled code checks every SInt result and stops; the interpreter's answer then holds the operation, its operands and the error.

Why stopping is not enough for good. For livelit views, the page waits for the interpreter, which is fine. In mixed mode, a call that stops is run again from the start in the interpreter, so an error deep in a long call costs the call twice. A program being edited meets errors often. And holes need the same thing: ? + 1 is a stuck term too.

What it takes, in order of difficulty:

  1. A stuck term as a JavaScript value. Where an operation fails, compiled code builds the term the interpreter would: the operation (known when compiling, with its id in the source), its operands carried back to Hazel by their types (the operation says them: an SInt sum has SInt operands), and the error. of_js gives it back as is. Overflow and divide by zero need only this, since their operands are values.
  2. Going on around it. An operation that meets a stuck term builds a larger one ((7 / 0) + 1), as the interpreter's evaluation does around anything indeterminate; a tuple or list holding one is still a value with a stuck part. This is the step that ? + 1 needs, and where an opaque hole of report 055 and a stuck term become one kind of value.
  3. Control that meets it. A case on a stuck term, an if on one, a call of one: the interpreter's answer holds the rest of the code, the arms, with the environment they close over. Compiled code has erased both, so it must give back the source of the arms and the values of their free variables, carried back to Hazel. This is the hard part, and the reverse of the limit on a closure with its own environment.
  4. Ids and steps. The interpreter's stuck terms carry ids that tie them to the source, which compiled code knows when compiling; and building them must count the interpreter's steps too.
  5. The check. Once compiled code makes stuck terms, the consistency check should compare them with the interpreter's, not only that both stopped (decision 18).

Overflow first, then the other invalid operations, then going on around them, then control. The first two are Matthew's after more limits are lifted; the second step of the holes work builds on the second and third.
