The Witch’s Run, Compiled, in the Page

What happens to one step of a slider when the slide's whole program, compiled to JavaScript by hazel-jit, runs in the page at the slider's event, instead of the page waiting for Hazel's worker to run it? ^report(45) measured the compiled run in Node: 2.3 to 2.5 ms a step on the Witch slide, against the interpreter's 684 ms (the whole run, compiled). This report is the same idea in the app, in Firefox, on 2026-11-08 (^ticket(722)), toward Matthew's goal for small edits that morning: "a floor of 60FPS for small edits (sliders changing), just like in JS".

Outline

  1. A step, run compiled: the slide's run answers a step in {{first}} ms in Firefox, and the picture showed at the page's first redraw in {{n_early}} of {{n_steps}} steps.
  2. Where a step's time goes now: the page's own work, {{own}} ms to its first redraw; the worker still runs and redraws everything again.
  3. The steps back: on a slider's return to its starting value the run answered as quickly, but its answers were drawn once and dropped; not yet explained.
  4. What the Node numbers assumed: a slide's program, as the page holds it, has no livelit views in it; the compiled run now folds them in itself.
  5. The same drawings: on all {{n_slides}} polygon slides, compiled and not, no differences.
  6. What it costs: the edited program compiled again after every step, {{recompile}} ms on the page's thread.
  7. Four runs: what each change did, in order.
  8. What next, and how this was put together.

Where a step's time goes now

The page first redraws {{own}} ms after the slider's event, and nearly all of that is its own work: the whole slide's view, twice ({{view_before}} ms), its layout ({{calc_before}} ms), and the program's syntax and statics ({{statics_before}} ms). The compiled run is the sliver at the start. Meanwhile the worker still runs the program ({{worker_slices}} s of work), and when its answer comes back the page draws every view again ({{views_after}} ms), to the same picture.

{{fig_edit}}

So the compiled run removes the wait for the worker, but not the work the page does for any edit: a slider's new model is a change to the program's text, and the page treats it as one, statics and the whole slide's view included. For a step that changes one livelit's model, under the conditions ^report(46) listed (compiling the run), none of that is needed: the compiled run's answers say what every livelit shows.

The steps back

On the {{n_steps}} steps, the compiled run answered every event, {{late_first}} ms on the two steps back to a slider's starting value. But on those two, only {{drawn_late}} livelits were drawn from its answers (one redraw's worth), against {{drawn_early}} on the steps away, and the picture waited for the worker: {{pic_late}} s. Not yet explained. A lead: the page treats the run's answers as current while the slider's optimistic entry lasts (the entry that holds the model the slider was just given, until the worker's run shows it), and that entry is retired when the program shows a model the slider has held before, which on a step back is its starting value. The next step is to keep the answers until the worker's answer for this step arrives, whatever value it holds.

What the Node numbers assumed

The compiled run first never ran in the app: the page compiled the slide's program, but none of its livelit uses had a model to hand a new value to (0 of {{w_livelits}} on the Witch). A slide's program, as the page holds it, has no livelit views in it. Statics folds a livelit's view into the run only for a use that is probed, and a slide is elaborated with only its cells' own probes (Program.probe_ids, then DefStatics.calc_auto); the page draws each livelit by running its view itself. ^report(45)'s measurement in Node elaborated the slide with every use probed (hazel jit --views), so its 2.3 to 2.5 ms ran a program the page never holds. The same assumption is in ^report(46)'s speculation (compiling the run), which says the run samples every livelit's view today; on these slides it does not.

A slider's use, as a slide's program holds it (elaborated):

match Drawing.^slider("neck", 0, 60).expand {
| Functional(f) => f(28)
| Macro(_) => ?
}

As the compiled run folds it, before compiling (in Hazel, with the two calls of hazel-jit's runtime written in):

let %model = $R.param(the 28's id, 28) in
let _ = $R.sample(the use's id,
          Drawing.^slider("neck", 0, 60).view(%model)) in
match Drawing.^slider("neck", 0, 60).expand {
| Functional(f) => f(%model)
| Macro(_) => ?
}

The fold is the one Statics makes for a probed use (UserLivelit.instrument_view), made by the compiled run on its own copy of the program, so the worker's run is unchanged. A macro livelit, such as the Witch's ^picture, is expanded when the program is elaborated and holds no definition to call view on; the page now notes each use's definition as it draws it, and the fold uses that. With both, every livelit use on every polygon slide is folded in ({{w_folded}} of {{w_livelits}} on the Witch).

What it costs

After each step the program's text has a new literal, so the page compiles the program again: {{recompile}} ms on the page's thread, once a step, between the first redraw and the worker's answer. The new program differs from the old only in the literal that is already the run's parameter, so the old compiled code, given the new value, is the new program's. Keeping it would remove this cost.

What next

  1. Keep the compiled run's answers until the worker's answer for the same step arrives, whatever value the slider returns to, so the steps back draw the picture as early as the steps away (the steps back).
  2. Do not compile again when only a parameter's literal changed: {{recompile}} ms a step on the page's thread (what it costs).
  3. For a step that changes only livelit models, skip the page's whole-program work: statics, and the whole slide's view, most of the {{own}} ms before the first redraw; draw only the livelits whose answers changed.
  4. Do not run the worker, or do not redraw from its answer, when the compiled run has answered: it spends {{worker_slices}} s and the page then draws every view again, to the same picture.
  5. Make hazel jit --views elaborate a slide as the page does, so its numbers in Node measure the program the app compiles.
  6. Put a dated note in ^report(45) and ^report(46) where they assume the run samples every view.

How this was put together

  • The build: a release build of trial/694-view-jit (hazelgrove/hazel, the livelits line with hazel-jit), at the four commits in four runs; the numbers in the sections above are from the last run that fired, {{main_run}} at {{main_commit}}.
  • The check: scripts/jit_slides.py in Firefox on GitHub's machines (.github/workflows/jit.yml, ubuntu-latest): each polygon slide loaded with compiled views on and off, its events run and timed, the drawings compared; on the Witch, four slider steps each way (neck 28 to 30 and back, arms 55 to 65 and back) on a fresh load, each timed from the slider's input event by watching the page for the slider's and the picture's elements to change, with the page's own timeline and the worker's (Util.BenchMarks) for where the time went. One run of four steps each way: say so beside any comparison; GitHub's machines vary from run to run (the steps with nothing compiled took 1.15 to 1.66 s in one run and 1.90 to 2.24 s in the next), so compare within a run.
  • The counts are the page's own (HazelJitValue.count, read as globalThis.hazelJit), including each reason the compiled run was not used, added for this work after the first run showed nothing.
  • The code: HazelJitRun (the run compiled with the livelits' models as parameters, the fold, and the step), its call in LivelitProj at a livelit's event and in its view, and ProjectorView telling it the program; hazel-jit's parameters and samples in HazelJit.
